Choose and run a vLLM recipe on DGX Spark or Station
You will choose a recipe for your device, run its commands, and test the model's API and tool calling.
Along the way, you will see how the recipe uses memory, batches requests, and selects the code that runs the model.
Once the endpoint works, you can tune it for your workload, save the launch command, and use it with a client such as Hermes or OpenShell.

Step
2
Read the settings that shape the service
First, check how the recipe divides memory between weights and requests.
The model weights take up part of the device's memory.
Serving also needs space for runtime work and the KV cache, which holds attention keys and values from tokens already processed.
Longer requests and more requests in flight compete for that space.
Setting
Why it is in the recipe
Checkpoint precision and
--quantization
Set how model weights are stored and run. Lower precision can reduce weight memory use; the checkpoint and backend must support it.
--gpu-memory-utilization
Sets the fraction of GPU memory vLLM budgets for its executor. A higher value can leave more room for KV cache, with less headroom for other use.
--max-model-len
Caps the total input and output tokens in a request. A large limit needs enough cache to serve long requests.
--max-num-seqs
Caps the number of sequences processed in one iteration. More active sequences can raise throughput and memory use.
--kv-cache-dtype
Sets KV-cache precision separately from weight precision. A supported lower-precision cache can hold more tokens in the same memory.
--cpu-offload-gb
Places some model weights in host memory. This can make a large model fit, with performance tied to host memory and the CPU–GPU link.
See the
vLLM serve options
and
quantized KV-cache guide
for details.
Next, check how the recipe schedules work and reuses it.
vLLM first processes the input prompt, called
prefill
, then generates output tokens, called
decode
.
The best settings depend on prompt length, output length, and the number of clients.
Setting
Why it is in the recipe
--max-num-batched-tokens
Sets the token budget for one scheduler iteration. With chunked prefill, smaller values can help active replies keep moving; larger values can process more prompt tokens at once.
--enable-chunked-prefill
Splits long prompt processing into chunks that can share batches with decode work.
--enable-prefix-caching
Reuses cached work for shared prompt prefixes, such as repeated system prompts or document text. It saves prompt work when the prefix matches.
--speculative-config
Uses a draft model or native prediction heads to propose tokens for the main model to check. The gain depends on the model and workload. Preserve any draft-checkpoint settings.
Read more about
scheduling and tuning
,
prefix caching
, and
speculative decoding
.
Then, keep the recipe's model-specific runtime settings together.
Load formats, attention and MoE backends, compilation settings, and environment variables select code paths supported by that image and model.
Keep them for the first run so you have a working baseline.
For agent use, also keep the model's tool-call and reasoning parsers.
--enable-auto-tool-choice
allows the model to choose a tool, while
--tool-call-parser
reads its tool-call format.
--reasoning-parser
separates reasoning from the final answer; the model's chat template and request settings control whether it thinks.
See
tool calling
and
reasoning outputs
.
Success:
You know which settings control capacity, scheduling, and the response format your client will receive.

Step
5
(optional) Tune the service for your workload
First, record a baseline with representative requests.
Use the prompt lengths, output lengths, and client count you expect to serve.
Record time to first token, output tokens per second, and memory use.
For multiple clients, distinguish each client's generation rate from total throughput.
Then, change one setting and repeat the same workload.
Set
--max-model-len
to cover your actual input and output needs
Try
--max-num-seqs
and
--max-num-batched-tokens
to balance concurrency and latency
Compare repeated-prefix workloads with prefix caching, or test the recipe's speculative-decoding variant
Keep the settings that improve your target measure, then rerun the chat and tool tests
Memory capacity, request length, and concurrency form a shared budget.
A context limit of 262144 tokens and
--max-num-seqs 8
do not guarantee that eight full-length requests fit at once.
Read the KV-cache capacity and concurrency estimates in startup output, then test the load you intend to run.
Success:
You have measured settings that suit your workload and still pass the functional checks.
