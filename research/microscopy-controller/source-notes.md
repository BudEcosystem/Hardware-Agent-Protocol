# Original controller-source critique

Reviewed on 2026-11-06. This lane read 31 complete source/test files (15,216 lines) and 765 lines comprising selected complete functions in Gently's 4,018-line device layer. Tests were read, never executed. No hardware, image acquisition, live controller or microscope HTTP service was used. Counts describe reading, not test outcomes. Exact files, line ranges and SHA-256 values are in `selected-files.json`; full repositories are not claimed read.

**Pins and historical distinction.** The old physical-AI corpus already contained OpenFlexure server `143c2add6ac7fcbf3c1094e1f3e82000f14d4dae` and Gently `bd7680e1aec0a8fb3e8865e5011d1d227d39d6e5`. Official current-head queries returned those same commits. This review extended source coverage without rewriting the older ledger. The latest listed releases are different commits: OpenFlexure `v3.0.0-beta1` → `4aa9ef70403b5e6fd9cd71712f937700947c2609`; Gently `v1.0.0rc1` → `80eebfffefb9f70926522c955c12667ed8e71243`. Reviewed default-head behavior must not be attributed to those release artifacts.

Sangaboard firmware `1657c416980ec0e3510ae2ccdd28f8757d993878` and pySangaboard `ae9188125b8f3718e74dd0245fd37b021236f48c` were newly acquired as shallow source-only clones. Firmware releases/tags API responses were empty, while its source version is `1.0.4-dev`. PyPI reports sangaboard 0.4.1; the reviewed Python source is a separate commit pin, not an assertion that a downloaded wheel was inspected. `pins.json` links official queries and preserves this separation.

**Sangaboard motion and serial boundary.** The selected firmware stage path updates `current_pos` while emitting coil phases. It cannot establish actual sample displacement, and a power loss can invalidate continuity: normal completion calls `EEPROM.put`, whereas stop does not; Pico persistence additionally uses delayed commit. Nonblocking `done.` comes from `start_move` before completion. `zero` changes counters without reference seeking. The default configuration does not compile endstops. The optional endstop module contains seeking, retreat and slower final seeking phases; all are entered through shared motion state. Clearing `stage_moving` in `stage_stop` leaves homing flags set, so the next endstop loop can launch the next phase. The final homing phase also starts a retreat before emitting `done.`. These are exact source-level concerns, not hardware reproduction or an audit of every build configuration.

The command and motion paths reviewed have no authority epoch, operation deduplication key, expiry or retained terminal operation record. A second move can replace current move state. pySangaboard serial queries flush incoming data, serialize through a reentrant lock, and normally set timeout to `None`; the initial version probes' two-second timeout does not bound later queries. Absolute motion is implemented by reading a counter and issuing a relative displacement. Closing a serial handle is not a physical stop. An HMS bridge must explicitly commission its port because automatic port discovery can transmit identification queries.

**OpenFlexure motion, calibration and cancel.** The base stage applies axis signs and models backlash using issued-position differences. Compensation can add reversal trajectories and move otherwise unchanged axes. The selected tests confirm intended decomposition and coordinate conversion using dummy stages/mocks, including a no-displacement zeroing test. They do not measure backlash, missed steps, clearance or emergency stopping. Sangaboard adapter tests cover firmware-version checks only.

Camera-stage mapping records image displacements and motor counters, fits a 2×2 image-to-step matrix, rejects some high-residual fits, and writes raw calibration data. Its image coordinate ordering is `(y,x)`; conversions round motor targets. It is useful empirical registration, but does not identify a metrological stage frame, SI scale or full uncertainty budget. Stored matrix existence controls `calibration_required`. It lacks a validity relationship to changed objectives/crops/mounting. The motion-detection probes are powers of two through 16,384 steps, followed by repeated traversals; calibration itself is significant motion. The per-axis `finally` returns to the initial position with cancellation blocked. Mapping tests exercise simulated/recorded fixtures and numerical fits; the referenced fixture data were not independently audited here.

SmartScan distinguishes saved scan result from the UI phase `Complete`. On cancellation, it records cancellation and returns to the starting point with cancellation blocked; with sufficient images it may continue stitching. The outer action also returns after ordinary exceptions. SmartScan's tests use mocked motion and explicitly expect return-to-start on cancellation. They establish intended software behavior, not a stationary stop. Scan workflow tests distinguish saved images from successful focus and cover a failed stack being treated as background. Thus a saved tile count alone is not an adequate scan success predicate.

Fast autofocus and looping autofocus use cancellation-blocked sweeps. Looping can recenter repeatedly, extending the visited absolute range beyond one sweep. JPEG stream timestamps and host `time.time()` movement endpoints feed linear position interpolation. The stage trajectory, transport latency, ramping and relative clock uncertainty are not measured by that calculation. The separately updated camera `FocusFoM` is not coupled to a particular JPEG frame. Smart-stack capture samples cached stage position, obtains its standard image, and later measures a low-resolution JPEG; a metric/image identity relationship must not be invented.

The base camera collects metadata before capture, retries timeout failures up to five times, and can log metadata-writing errors without failing the image save. This means one successful caller-level capture may hide multiple exposure attempts or lack metadata. Its gallery change hash uses size and timestamp, not image-content integrity. Camera and metadata tests validate formatting, save behavior and mocked state; they do not validate sensor timestamps, exposure synchronization or physical settling.

**Gently driver and manual-control boundary.** Stage Status completion follows MMCore `waitForDevice`; the Z tolerance member is not used to verify final target error. Z read failures become 0.0 with a fresh host timestamp. The device-layer nudge helper catches wait errors and still reads/returns a position; the HTTP handler can consequently emit `success:true` after an unsuccessful move. A proposed adapter must preserve failure rather than trusting that success field. Relative nudges also require reconciling independent manual movement between read and command.

The XY envelope comments describe measurements on a particular rig, including joystick overshoot. The startup path pushes four ASI limit properties and reads each back, aborting startup on limit failure; it explicitly enables the joystick. Those are valuable controls but no ownership fence. Writes are sequential, without rollback if a later one fails. The numeric readback comparison lacks a finite-value check; a NaN readback can evade an absolute-error comparison. No numerical fault test was run to demonstrate this, and no device response containing NaN was observed.

Acquisition configures scanner, piezo, camera and illumination, then reads images until the driver stops/buffer drains. It does not compare the final array count with requested slices. Timestamping occurs after host retrieval, not at sensor exposure. Error cleanup wraps several calls in one `try`, so an early stop/reset failure skips later cleanup, including laser-off. Its inspected failure tests inject acquisition-start failure with functioning cleanup, leaving this case uncovered. Ophyd Status timeout and cancelling an asyncio task do not establish that a background driver thread stopped. Selected shutdown code acknowledges in-flight thread calls cannot be aborted and can outlive its task deadline; it is not a physical stop protocol.

There is also an explicit source/test mismatch: bottom-camera implementation intentionally does not manipulate LED state, while two tests in `test_dispim_device_safety.py` still require LED Open/Closed when `use_led=True`. These tests were not executed, so this is not a test-run failure report. Offline focus validation uses manual focus traces and, by default, the last trace sample as its reference. Empty inputs give zero error statistics with `n_sweeps=0`; they must not be read as successful validation. Its synthetic unit tests check arithmetic, not physical autofocus.

**Primary controller documentation.** The Micro-Manager ASITiger page was read completely. It warns that `UseFastSequence=Armed` short-circuits normal sequence behavior and `Busy()`. Its generic serial-command property also suppresses repeated identical values by default; that behavior is not operation-level idempotency. Four ASI command pages were read from web-tool renderings: SETLOW, STATUS, JOYSTICK and RDSTAT. SETLOW says limits persist automatically across a power cycle; therefore Gently's omission of SaveCardSettings should not be read as evidence of volatile limits. STATUS defines its busy report around serial-command motion. JOYSTICK controls manual input separately. The rendered docs do not prove the exact installed adapter/card behavior.

Direct ASI raw/HTML acquisition received HTTP 403. Those response bodies remain in the acquisition ledger as failed retrievals, never as manuals. The retained web-tool rendering is explicitly distinguished from origin bytes. HALT, SETUP, WHERE, PC and BACKLASH were attempted but not fully acquired/read; no stop-latency or stop-priority claim relies on them. No access restriction was bypassed. No ASI firmware binary, MMCore implementation or installed device adapter was audited in this lane.

**Camera manual and paper.** Picamera2 release 7, build `f7f16579351f` (2026-10-27), was acquired in full but read only in the declared request/metadata, queue and SensorTimestamp sections. Completed requests couple images and metadata; borrowed requests require release to avoid buffer starvation. The sensor timestamp denotes first-pixel readout on a boot-relative clock. `flush` accounts for exposure when selecting a sufficiently new request; queue suppression alone only establishes later frame arrival. Neither proves all rows were captured at one measured pose. This API offers a stronger acquisition seam than separate image and metadata calls, subject to actual deployed versions and clock/sensor qualification.

The existing arXiv 2109.06842v2 PDF was fully reread, including references; all eight figures were inspected on pages 2, 4, 5, 6, 7, 9, 10 and 12. Official version history still lists v2. Its sparse-edge example is a direct counterexample to treating maximum JPEG size as universally focused. The comparison uses different historical and smart-stack cohorts and assesses peak placement, not independent diagnostic accuracy or collision safety. Figure 6 clarifies iterative movements and fitting; figure 8 shows concentration within the central stack positions. The paper's 2021 fourth-order fit/lag method must not be conflated with the current 2026 implementation's quadratic checks. Its step/backlash numbers and timing results do not qualify an unknown retrofit. The original dataset and analysis were not downloaded or rerun.

The older Web-of-Things paper and Gently architecture notes supplied context through the pre-existing reading ledger; this lane does not add new full-reading claims for those items. The new binding document is our proposed interpretation and qualification plan, not an upstream contract or a new HMS production capability.
