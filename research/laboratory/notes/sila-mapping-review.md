## What the mapping actually specifies

The normative mapping uses HTTP/2, Protocol Buffers and gRPC wire semantics. Use of the gRPC library itself is optional if a custom implementation obeys the same wire protocol. Ordinary client-initiated access exposes every feature on one IP/port. The reverse method lets the instrument, still the logical SiLA server, act as the gRPC client and open a bidirectional stream to a logical SiLA client. Requests identify features/commands by fully qualified names inside that stream. This is a connection arrangement, not a transfer of device ownership. (pp. 16–23)

A cloud `requestUUID` correlates responses with a request, with a fresh ID recommended for each request. The document specifies no deduplication table, durable replay window or recovery lookup by that ID. It must remain distinct from the server-generated command execution UUID, the server UUID, and the binary transfer UUID. Protocol package names include the feature's major version but exclude its minor version, so a package name alone does not identify exact feature semantics. (pp. 18–19, 26–27)

Unobservable commands are one request and one response. Observable commands use initiation, status subscription and result retrieval, with an additional intermediate-results subscription when the feature declares it. The confirmation returns an execution UUID and optionally its validity duration. `_Info` is a stream; one-shot status reads consume its first message and cancel that subscription. Progress is encoded as a fraction from zero to one, despite the conceptual definition using percentages. An execution error produces `finishedWithError`; retrieving its result then raises the execution error. (pp. 28–44)

The mapping has no generic physical stop or command-cancel operation. Cancelling `_Info`, `_Intermediate`, a property stream, or one of the reverse-connection subscription messages cancels observation of data. It must not be normalized to cancelled physical execution. A device-specific stop command may exist in a feature, whose definition and implementation must be examined separately. (pp. 35–49)

Subscriptions provide an initial current value and subsequent changes on a best-effort basis. The base property payload contains the declared value, not a universal acquisition timestamp, sequence, clock uncertainty, quality or sensor provenance. There is no generic cursor replay or retained event-gap recovery contract. The mapping supports useful live access but not a complete scientific observation envelope. (pp. 21, 44–49)

All command parameter fields are mandatory and the server must reject absent fields. SiLA scalar types are wrapped in messages, while list types map to repeated fields. Constraints, including units and numeric bounds, do not appear in the protobuf representation; the server must enforce them separately from the feature definition. `Any` contains XML type metadata plus serialized payload and excludes custom data types that require external feature context. (pp. 28, 53–55, 66–71)

Metadata is carried in binary gRPC headers, with qualified names transformed to lowercase/hyphenated keys; reverse connections carry corresponding metadata messages. Header-size limits still apply, and binary transfer cannot be used for metadata. The affected-call query identifies the feature/command/property scope of each metadata definition. The mere presence of a header is not evidence that the device enforces its proposed meaning. (pp. 50–53)

Binary values larger than 2 MiB require the separate transfer mechanism; chunks are at most 2 MiB. Upload reserves storage, associates a parameter identifier and relevant metadata, accepts indexed chunks in arbitrary order, then passes a transfer UUID to the command. The server may restrict use to the associated command; the specification does not make that restriction unconditional. Download supports offset/length requests. Binary UUIDs have finite advertised validity and explicit deletion; these references do not constitute durable, content-addressed scientific artifacts. No content digest is supplied by the generic message definitions. (pp. 56–65)

For ordinary access, SiLA validation, execution and framework errors use gRPC `ABORTED` with a base64 serialized error message. Native gRPC errors are treated as connection errors. Reverse access sends the SiLA error within its message stream. A generic status-code handler loses the distinction between invalid parameters, not-accepted execution, partial physical failure and a result that is not ready. `ABORTED` is not the semantic equivalent of a successfully aborted physical process. (pp. 71–74)

TLS is mandatory. The mapping distinguishes implicit acceptance of already trusted certificates from explicit handling of untrusted ones. It specifies an optional server UUID certificate extension and discovery of self-signed trust material through DNS-SD TXT records. DNS-SD uses the server UUID as the service instance name and `_sila._tcp.local.`; functionality is subsequently discovered through the service feature. Advertised names/descriptions may be truncated to fit TXT record limits and should remain display hints. (pp. 74–77)

## Gaps and conflicts retained for resolution

1. **Receipt knowledge is not mapped into a durable handshake.** Core Part A p. 84 requires starting an observable command only once the server is sure the client received its UUID. Part B's initiation RPC/message definitions and p. 35 diagram contain a confirmation response but no client receipt acknowledgement or commit phase. Core's p. 52 diagram also returns the UUID before starting execution without such an acknowledgement. This does not prove that implementations violate the requirement, but neither specification supplies a crash-durable client identity/commit mechanism that establishes it. A client can also receive the UUID and crash before journaling it. Do not infer safe automatic retry after an ambiguous initiation.
2. **Discovery policy conflicts across parts.** Core p. 85 allows disabling server discovery. Mapping p. 75 forbids disabling any part and requires it enabled by default for every server. A deployment must document which interpretation/implementation it follows, rather than certify both contradictory statements.
3. **Private-address certificate acceptance needs explicit interpretation.** Mapping p. 74 forbids implicit acceptance of untrusted certificates; p. 75 then requires acceptance for private IP setups without restating the explicit-trust condition. Treat this as unresolved wording requiring an explicit trust/commissioning policy, not permission to silently trust every device advertising a CA on a private subnet.
4. **Time precision is inconsistent.** Core time/timestamp definitions include milliseconds; Part B pp. 54–55 protobuf messages only encode integer seconds. The retained PDF confirms that the missing field is not a text-extraction problem. Conversion cannot silently invent millisecond precision. Actual pinned proto artifacts may resolve the issue and remain to be checked.
5. **Illustrative mapping text contains mismatches.** The metadata key example uses `SiLAService/Metadata/AuthorizationToken` even though core forbids client metadata on the service feature. The reverse subscription table describes a property-parameter field while its proto contains metadata, and uses `PropertyValue` where the message inventory also lists `ObservablePropertyValue`. An empty `CancelPropertySubscription` needs a clearly tested subscription-correlation rule; the generic recommendation for fresh request UUIDs is not sufficient by itself to explain it. Several code examples contain missing punctuation or response/parameter-name mistakes. Use pinned normative schema/proto artifacts and interoperability tests before choosing exact wire behavior.
6. **Future items leak into the definition index.** Quantity, client UUID, optional response and property-filter terms appear in the copied index, while no complete operative mapping for them appears in this version. An index entry is insufficient evidence of supported wire behavior.

The introductory REST comparison is non-normative, partly attributed to a secondary tutorial, and contains overgeneralized assertions about JSON, HTTP connections and streaming. It is not a comparative benchmark or reliable basis for a performance requirement. No performance numbers or hardware qualification follow from this source.

## HMS design consequences — original analysis

An HMS SiLA adapter should retain three distinct IDs: durable HMS operation identity, native server identity plus incarnation evidence, and the native command execution UUID. Journal the binding and deadline before initiating; persist the returned UUID immediately; preserve an uncertain result for the gap between physical dispatch and durable confirmation. Retry only when the chosen implementation supplies tested deduplication or evidence that no effect could occur. A cloud correlation UUID does not close this gap.

Fetch and pin exact feature XML alongside generated protobuf descriptors. Compile explicit bound/enum/unit/metadata checks from that XML rather than trusting protobuf decoding alone. Prove that a missing scalar, explicit zero, an empty list and an invalid constraint are distinguished according to the selected feature. Reject or explicitly profile conversions that lose timestamp precision, integer range, list nesting, units or custom-type meaning.

Expose transport cancellation and physical stop as different capabilities. Continue tracking accepted operations after a subscription closes, using the admitted disconnect policy. A native command that continues while HMS authority changes requires local coordination and a tested stop/hold mechanism; simply cancelling the RPC or dropping its stream supplies neither.

Copy required result data into an HMS artifact store before native binary lifetimes expire, retain hashes and acquisition provenance, and make retention failure visible independently from instrument execution success. Bound outstanding chunks and storage allocation. Because reverse connection messages, status and binary chunks share a stream, test queue/backpressure under bulk transfer rather than assuming HTTP/2 multiplexing makes urgent control independent.

Authenticate enrollment independently of mDNS, TXT names or advertised certificates. Preserve SiLA's discovery service behavior within the selected profile while applying site-level network access controls and HMS authorization at the adapter. Do not weaken secure enrollment to work around the conflicting wording. Map raw SiLA error classes and identifiers as well as the HMS outcome, retaining possible physical effects rather than treating every `ABORTED` as no effect.

Necessary tests include lost confirmation; client crash before UUID persistence; expiry before result retrieval; stream cancellation while motion continues; reset with reused logical server identity; malformed/missing wrapped fields; metadata scoped to the wrong call; binary expiry/deletion during a download; incomplete upload used in a command; unit and time conversion loss; reverse-stream subscription correlation; and congestion delaying control/status. None were executed in this review.
