# SiLA 2 v1.1 core and mapping review

This review covers the locally retained March 2022 SiLA 2 Part A and Part B documents. Source statements below refer to these versions, not to a claim about the newest implementation. The [core PDF](https://sila-standard.com/wp-content/uploads/2022/03/SiLA-2-Part-A-Overview-Concepts-and-Core-Specification-v1.1.pdf) is 92 pages; the [mapping PDF](https://sila-standard.com/wp-content/uploads/2022/03/SiLA-2-Part-B-Mapping-Specification-v1.1.pdf) is 91 pages. Copyright belongs to the SiLA consortium; both documents identify CC BY-SA 4.0 licensing. Original research conclusions and proposed HMS behavior are distinguished from upstream requirements.

The complete retained text, including tables, glossary and references, was read sequentially. Relevant diagrams and numeric tables were inspected as page renders. [Coverage and hashes](../reading-sila-full.json) record exact LF-addressable intervals and figure scope; [mapping-specific notes](sila-mapping-review.md) retain the separate Part B analysis. Reading these two PDFs does not establish conformance, implementation behavior, or reading of the externally linked Feature XML, schemas, standard feature index, libraries or referenced standards. The core contents list names future-consideration sections that are absent from the retained PDF body; the body ends at the normative-end marker on page 92. Page footers say v1.0 while covers and headers say v1.1; this inconsistency is preserved.

## Core findings

**Architecture and descriptions.** Part A pp28–35 makes client/server a role rather than a hardware class, permits a server to be software or a physical instrument, and allows parallel clients and vendor-specific queuing choices. Every server exposes the SiLA Service Feature; v1.1 additionally specifies Connection Configuration Service and server-initiated connection support. Feature collections and the set of operations affected by metadata remain fixed for a server lifetime. The diagrams on pp20–23 illustrate layered orchestrators that expose higher-level features while consuming instrument features. This supports a hub or embedded agent topology without requiring the same compute stack on every endpoint.

Feature definitions describe behavior, conditions and dependencies as well as types. Part A pp38–41 explicitly requires state transitions and ordering requirements to be documented. Much of that behavior is prose, so generating a typed client does not automatically produce a machine-checkable precondition or an assessed operating envelope. A generic HMS importer must retain such requirements as unresolved until a profile or commissioned adapter implements them.

**Execution identity and retention.** Part A pp48–52 distinguishes unobservable calls from observable executions. An observable initiation returns a server-generated execution UUID and optionally a validity duration measured from the server's response initiation. Omitted duration means validity for the server lifetime. Updated expiry may extend but not shorten the previously promised absolute validity. States advance through waiting, running and success/error termination; progress and estimated remaining time are estimates. Results can be retrieved while the UUID remains valid, but expiry permits removal of results and associated resources. This duration is a result/handle validity contract, not a maximum physical execution time or an authority lease.

Accepted observable work must continue after connection loss (pp33,84), while event delivery stops and clients must reconnect/resubscribe. Unobservable work can execute after all parameters arrive while its response is lost. The server UUID persists across lifetimes (p29), whereas execution UUID semantics are scoped to a server instance and lifetime. Therefore a stable server UUID alone is insufficient evidence of continuity after restart.

Part A p84 also requires the server to start an observable command only after it is sure that the client received the execution UUID. This is stronger than merely returning a reply. The p52 sequence diagram shows UUID return followed by execution start, with no application receipt acknowledgement; Part B's initiation mapping likewise supplies no explicit durable receipt/commit exchange. The requirement must not be ignored, but these documents alone do not demonstrate how an implementation meets it during disconnect or client crash. HMS must require implementation evidence or a strengthened application handshake and retain ambiguous dispatch when receipt cannot be established. Even receipt in client memory is not persistence in the HMS journal.

**Properties and streams.** Part A pp53–57 makes all properties read-only and prohibits side effects from reading. A mutating setting uses a command. Observable properties send their current value at subscription and then changes; failure to determine a value raises an error and ends the subscription. Intermediate command responses are explicitly unsuitable for information that must be delivered (p46). Initial value delivery is useful, but it does not establish acquisition time, sensor independence, complete historical delivery, or sequence continuity. Part B describes best-effort subscriptions. Resubscription restores present state, not missed events or scientific acquisition completeness.

**Metadata, locks and authority.** Part A pp58–60 requires expected client metadata before parameter validation, ignores unexpected metadata, and disallows metadata on the SiLA Service Feature. Observable-command metadata applies only to initiation, not status/result/intermediate-response access. The Lock Controller and Authorization Service are feature examples, not mandatory core resource fencing. The core neither defines a universal monotonic fencing generation nor establishes that queued native work rechecks current ownership. HMS must verify the supported metadata feature and affected operations; adding an unknown token to a header can be ignored. Later result access also needs independently established protection rather than assuming the initiation token is checked again.

**Errors and cancellation.** Validation, defined/undefined execution, framework and connection errors are distinct (pp80–84). Defined errors carry stable feature-scoped identifiers that an adapter should preserve. An execution error can follow partial physical work, so it is not equivalent to rejection before dispatch. Cancellation in these core interaction descriptions concerns subscriptions; no universal physical command-cancel operation or canceled execution state is supplied. A separate feature may implement stop, pause or termination, but its definition and physical evidence must be inspected. Closing a gRPC stream cannot be promoted to physical cancellation.

**Types, units and compatibility.** Part A pp63–75 defines signed 64-bit integers, binary64 real values, constrained types, ordered homogeneous lists and structures. Direct lists of lists are disallowed. `Any` carries both type and value but cannot refer to custom types; `Void` appears only within `Any`. Unit metadata includes a label, affine conversion and SI dimension exponents, and wire values remain in the declared label's unit. XML-schema regular expressions and embedded XML/JSON schema constraints cannot be assumed to map directly to every WoT validator.

HMS must retain exact integer values, require explicit finite physical arguments, and test affine conversion instead of performing unchecked casts. An SI dimension is not complete physical meaning: rotational frequency and angular velocity require a quantity convention as well as inverse-time dimensions. The p74 Fahrenheit example rounds its offset to 255.37; it should not become an exact conversion fixture. Part A p70 maps numeric constraint values to `xs:double`; bounds near 64-bit extremes warrant schema/library inspection because binary64 cannot represent every int64 value exactly. This is a precision question, not evidence that an implementation has already failed.

Feature identifiers include originator/category/name/major version, but omit the minor version (pp76,87). Uniqueness comparison ignores letter case. Keep the native identifier, full version, exact definition digest and binding generation separately. A registry must not merge incompatible definitions because their major-version identifier matches. Adding parameters can remain within a major version; Part B's missing-field validation means actual compatibility needs fixtures rather than version-label optimism.

**Security and discovery.** Part A pp85–86 mandates encryption, recommends authentication and authorization features, and makes audit trails optional. These are different assurance levels. Its discovery contract targets local ad-hoc networks; global registries remain outside this document. Private addressing, a name or a persistent UUID does not independently establish the commissioned physical device. A capability to configure reverse/cloud connectivity changes the trust and routing boundary even when normal feature calls remain the same.

## Cross-part issues to preserve

1. Part A p85 permits disabling discovery; Part B p75 forbids providing that option. Do not claim both clauses satisfied by an arbitrary deployment. Record chosen behavior and seek upstream clarification before conformance claims.
2. Part B pp74–75 rejects implicit acceptance of untrusted certificates but then requires acceptance on private-address networks. The HMS boundary must use explicit trust enrollment; network location is not sufficient identity evidence. This deployment choice may be stricter than one reading of the mapping and must be disclosed.
3. Part A p64 includes milliseconds in Time and Timestamp, but the Part B pp54–55 message examples have no fractional-second field. Pin the actual schema and reject a mapping that silently discards required resolution.
4. Part B p51 places example authorization metadata under SiLAService, while Part A p58 excludes metadata there. Treat it as an inconsistent example, not permission to override the core rule.
5. Observable UUID receipt assurance is required in the core but not concretely resolved by the depicted mapping. Test client/server crash windows and record the implementation's mechanism.
6. Reverse property subscription examples differ in their value-message names and parameter/metadata descriptions, and empty cancellation messages need a tested correlation rule. Preserve these ambiguities until pinned protobuf artifacts and an implementation establish the selected wire behavior.

These issues are reasons for narrow, tested bindings. They are not claims that every SiLA implementation is insecure or unreliable.

## Original conclusions for HMS

Reuse SiLA's typed feature vocabulary, read-only properties, asynchronous status/result interfaces, error identifiers, unit metadata and capability discovery. Preserve native gRPC and reverse-connection semantics behind an HMS adapter. Put durable caller identity, commissioned resources, timing bounds, result authorization, material identity and independent physical evidence in HMS's operation layer. A transparent bridge cannot manufacture those guarantees when the native server lacks them.

The first useful adapter should operate a known instrument feature with explicit exclusive control, supported completion evidence and bounded result retrieval. It should retain a durable mapping from HMS operation to SiLA server UUID, observed session continuity, feature digest and native execution UUID. Qualify uncertain initiation, result expiry, queue authority changes and disconnect continuation before expanding supported features. Scientific sample lineage belongs in the workflow/material profile; a barcode response example is not a complete sample-state protocol.

Remaining work includes acquiring and pinning `sila_base`, actual Feature XML/XSD/protobuf files and one reference implementation; inspecting LockController/AuthorizationService/connection-configuration features; verifying errata/version history; and running adversarial interoperability tests. No SiLA client, server or physical instrument was executed in this review.
