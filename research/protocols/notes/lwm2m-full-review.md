# Full review of retained OMA LwM2M Core 1.2

The retained source is the approved **2020-11-10 Core 1.2**, not an assertion about the newest release. Raw PDF SHA-256: `8761e79d322b3ad8d0cfc492943cbd86fdffc754cb520a24414a462b7a1fcefd`. Extracted text SHA-256: `3b32586ef3e0facaa971a59cccf27386fed38325d239360b27cd8966f7512323`.

All 11,164 LF-delimited lines were read in 26 complete bounded outputs, including the final unterminated form-feed. All 154 pages' extracted prose, table content, examples and appendices were included. All 28 semantic figures were inspected in rendered PDF pages, along with the visibly clipped MQTT table on page 128. The [coverage record](../reading-lwm2m-full.json) supplies range hashes and image hashes; the [supplementary acquisition manifest](../../constrained/lwm2m/manifest.json) records official-source URLs, retrieval status, raw/text paths and hashes. The original 7,501–8,000 read was truncated and was excluded; complete replacement reads cover 7,501–7,750 and 7,751–8,000.

## Proposed HMS rules and relation to the core

The [binding proposal](../../../docs/lwm2m-binding.md) applies these claims to `spec/02-execution.md` and `spec/03-registry-runtime.md`. HMS should keep authenticated enrollment, presence, commissioned binding, endpoint execution session and operation/resource authority separate. This follows the existing HMS record split and avoids promoting native registration state into a physical authority lease.

Native field descriptions can supply units, types and operation support. They do not supply every HMS completion predicate, clock bound, resource conflict, interruption policy or delegated limit. An adapter must declare what is absent, then add only commissioned and enforceable semantics. Unknown optional native fields can remain interoperable without becoming executable HMS affordances.

A durable HMS gateway operation service is needed where endpoint Execute lacks persistence or correlation. It records intent before dispatch and ambiguous outcomes after possible delivery. Endpoint-side deduplication/fencing cannot be inferred from server persistence. Multiple authorized native servers also require explicit ownership coordination or a physically exclusive gateway; ACL ownership alone does not solve stale-controller or queued-command execution.

Telemetry needs separate acquisition, receipt and clock-quality evidence. Retained offline data, repeated pmax values, best-effort composite omissions and observation resets must remain visible. Firmware and bootstrap belong to the existing HMS maintenance privileges and binding-invalidation rules. The native firmware state machine is useful evidence but cannot stand in for artifact verification, installation commissioning or safe physical recovery.

These are design conclusions, not requirements claimed to originate in OMA. No protocol parser, runtime, device firmware, timing test or conformance test was implemented or executed by this review.

## Conflicting evidence, corrections and limits

1. **Native atomicity is real but scoped.** Write-Composite explicitly promises atomic resource writes. A claim that LwM2M provides no atomic operations would be wrong. HMS must preserve that contract while avoiding unsupported physical rollback or cross-device simultaneity claims. Read-Composite explicitly has weaker semantics.
2. **Native security is substantial but different.** Bootstrap credentials, transport/application security hooks and per-server ACLs exist. Calling LwM2M unauthenticated or permissionless would be wrong. Endpoint Client Name alone is unauthenticated, native ACL scope is coarser than HMS actor/action limits, and some configurations intentionally grant full native rights.
3. **Time and lifecycle are not wholly absent.** SenML historical times, Location Timestamp, firmware State/Update Result/Last State Change Time, and firmware Cancel exist. HMS should preserve them. They are not generic action histories or clock uncertainty bounds; firmware cancellation has a restricted phase.
4. **The 2020 document has known editorial defects.** Execute examples contain spaces forbidden by its own grammar; its OSCORE reference points to RFC8259. The 1.2.2 revision-history section explicitly reports that 1.2.1 fixed these, clarified argument uniqueness, fixed Bootstrap-Pack JSON and corrected smartcard binary examples. Do not use every printed example as a golden fixture. [Core 1.2.2 revision notice](https://www.openmobilealliance.org/RELEASE/LightweightM2M/V1_2_2-20240613-A/HTML-Version/OMA-TS-LightweightM2M_Core-V1_2_2-20240613-A.html)
5. **Further source inconsistencies remain visible.** Figure 6.3.-1 on p54 shows a successful Write to Device Model Number `/3/0/1`, while E.4 defines it read-only. TLV table 7.4.5.2.-3 on p85 disagrees internally about byte counts. Table E.11-2 on p128 clips its description column and gives Will QoS range `0..3`; selected 1.2.2 HTML still prints that range. Do not adopt 3 as a valid MQTT QoS without the actual MQTT transport/protocol rules. These observations are not a complete errata inventory.
6. **Version baseline matters.** Official OMA releases include 1.2.1 and 1.2.2 after the retained 1.2 snapshot. The 1.2.2 release definition lists object-versioning, object 27 enumeration, transport and MQTT-test corrections. Selected current Core sections explicitly protect COSE Object 23, include object versions in Profile ID hashing and clarify object-version link placement. Newer content was not silently substituted into the full-read snapshot. [OMA release directory](https://www.openmobilealliance.org/release/LightweightM2M/), [1.2.2 release definition](https://www.openmobilealliance.org/release/lightweightm2m/V1_2_2-20240613-A/HTML-Version/OMA-ERELD-LightweightM2M-V1_2_2-20240613-A.html)
7. **Coverage is document-scoped.** Full Core 1.2 reading does not include the companion Transport specification, external normative RFCs/3GPP/smartcard standards, object-registry XML files, vendor firmware behavior or the complete 1.2.2 Core. Three supplementary HTML acquisitions are archived; the release directory (53 lines) and release definition (179 lines) were fully read, while current Core has only 334 of 7,893 lines covered in named ranges. Those samples are corrective checks, not current-version conformance evidence.

## Semantic figure review

All 28 figures listed in the Core's Table of Figures were checked against rendered pages. Architecture/interface diagrams distinguish bootstrap from management and reporting; registration sequence diagrams show association updates rather than control-lease transfer. Retry flowcharts distinguish ordered/blocking and independent server attempts, with bootstrap recovery and implementation-dependent nonblocking retries. Object/ACL diagrams show typed fields intersected with server permissions; the object-link diagram depicts references rather than physical hierarchy. TLV nesting is at most three container levels. The p65 reporting example repeats value 76 at pmax without a new-value event. The p122 firmware diagram distinguishes transfer from installation and shows failure/cancel/reset transitions; the p123–124 block exchanges describe transfer only. Smartcard diagrams show file location and mutual-authentication/data-transfer stages.

The p54 read-only Write inconsistency is retained above. Diagram labels and prose cannot override a pinned resource contract. Image files retain complete rendered pages for context, including copyright notices; their hashes and figure IDs are in the reading record.
