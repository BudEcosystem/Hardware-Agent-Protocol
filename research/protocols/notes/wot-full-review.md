# Full reading: WoT Thing Description 1.1 and WoT Discovery

Review date: 2026-11-06 (Asia/Kolkata). This is original analysis for the independent HMS research draft. It does not describe official Anthropic MHS or claim compatibility with it.

The complete archived [TD 1.1 Recommendation](https://www.w3.org/TR/2023/REC-wot-thing-description11-20231205/) and [Discovery Recommendation](https://www.w3.org/TR/2023/REC-wot-discovery-20231205/) were read sequentially, including examples, appendices, change logs, normative references, informative references, and generated footer text. TD contains 17,373 logical extracted-text lines; Discovery contains 5,842. All six TD figures and all five Discovery figures were separately inspected. Raw HTML tables were checked where column relationships mattered. The reproducible coverage record is [reading-wot-full.json](../reading-wot-full.json). Reading the references lists does **not** mean reading every referenced document. WoT Architecture 1.1, the complete binding templates, JSON-LD, the complete context file and the complete TM validation schema were not fully read in this lane.

## Decision emerging from the full documents

HMS should use a conforming TD 1.1 as its externally exchanged device description, with an explicitly versioned HMS execution profile and namespaced extensions or a digest-pinned linked physical contract. The present bespoke description duplicates the part WoT already standardizes: identification, typed interactions, forms, security descriptions and reusable models. Its useful novelty is the physical execution contract. Preserve that contract and the independent invocation envelope; do not preserve a second public discovery vocabulary merely because it was drafted first.

This conclusion is narrower than adopting a complete WoT runtime. A gateway can serve TDs for serial and resource-limited devices. A consumer need not perform RDF processing to parse ordinary TD JSON. Direct authenticated retrieval is a legitimate Discovery path. Neither full semantic search nor an RDF database belongs in the minimum HMS implementation merely because the description uses TD.

## Critique of the interaction model

The property/action/event split is sufficiently general for an Arduino gateway, robot or microscope without naming their drivers in the public schema. The classification is useful because it tells a consumer how to interact, while semantic tags describe what the interaction means. It is deliberately not a physical world model. A commanded position property, a controller estimate and an independently measured position may share a numeric schema; HMS must keep their evidence categories distinct.

The three action flags are particularly easy to misread. `safe` concerns changes to resource state, not physical risk. `idempotent` concerns repeated action semantics, not durable deduplication across a host crash. `synchronous` says the action response contains the result without subsequent status querying. An accepted operation handle is not the completed result of a physical motion. For physical actions that continue after their response, use the appropriate asynchronous description and make the acceptance/result distinction explicit. If an action is deliberately defined only as submission, document that narrow meaning rather than allowing the title to imply completion of the underlying task.

TD already has asynchronous action querying and cancellation vocabulary. Claiming HMS needs to invent these verbs would overstate the gap. The real gap is the execution contract behind them: correlation; stable operation identity; request digests; replay retention; dispatch ownership; intermediate states; cancellation races; partial effects; stop evidence; recovery from lost replies; and unresolved resource claims. Table 28 does not provide a built-in action-status schema for `queryaction` or `cancelaction`. A profile/binding must specify how an invocation instance is selected and what those operations return. Generic query/cancel labels alone are insufficient.

Observation subscriptions also do not promise a current initial value or a race-free transition from snapshot to updates. The profile must state whether it supports replay from a snapshot cursor, subscribe-before-snapshot reconciliation, or explicit possible gaps. Likewise an event's existence is not a durable event journal. These omissions are appropriate for a transport-neutral description standard; they are unacceptable if HMS silently assumes stronger semantics.

## Schema and consumer compatibility

TD's DataSchema is a common subset of JSON Schema, with extension mechanisms. That is materially different from saying every JSON Schema draft is interchangeable. The draft's arbitrary `input_schema` object has no declared translation rules. The migration needs a deliberate, tested projection or a linked schema with a declared dialect and required HMS support. Keep interface-level TD validation separate from the physical envelope's richer validation.

Section 8.2 makes an asymmetric extensibility choice. A consumer must not generate undeclared input data, while a Thing can return extra object properties or extra tuple items and a consumer must accept that additional returned data. A validator that rejects every response containing an unknown field cannot be presented as an unrestricted conforming TD consumer. The HMS layer should preserve or ignore ordinary extra output metadata, while treating an unsupported *explicitly required physical feature* as an execution admission failure. Rejection because required semantics are unsupported is different from rejecting an otherwise valid TD response merely for containing an extra field.

`format` is not a dependable physical constraint: validation is optional and unknown formats are expected to be tolerated. Similarly, `unit` can be a string and does not by itself define conversion, coordinate frame, uncertainty or calibration. The physical contract needs approved quantity/unit identifiers and versioned transformations. Numeric bounds are valuable admissibility information, but do not establish enforcement location, mechanical range, load-dependent limits, interlock behavior or current commissioning validity.

The entire currently served official TD schema was read, including its final brace on logical line 1,493. Its declared version is `1.1-12-March-2025`, and its draft is JSON Schema draft 7. It is intentionally permissive for extensions and does not enforce every normative relationship. For example, its OAuth2 branch requires `scheme` but does not itself require `flow`, although the normative vocabulary makes `flow` mandatory. Root/form security references, semantic term expansion, binding behavior and physical evidence also require checks beyond ordinary shape validation. The official schema is an **informative validation aid**, because TD Appendix B is non-normative. Calling it a normative conformance oracle would be incorrect. ## Forms, authority and downgrade hazards

Multiple forms offer alternative supported bindings; they do not automatically share one authorization or resource owner. If HMS publishes a carefully guarded HTTPS form and an unguarded legacy write form for the same device, a consumer may select the latter. Every effectful form exposed by the HMS service must reach the same admission authority, or its weaker semantics must be expressly outside the HMS execution contract and unavailable through that protected service.

Form-level `security` replaces top-level security rather than adding to it. Therefore inspect effective security on every form, including all alternatives and combo branches. A root bearer definition does not rescue a form that explicitly selects a weaker scheme. Security definitions communicate how credentials are supplied; they do not contain the credentials. OAuth scopes describe access categories, not the full physical authority envelope. A successful authentication exchange cannot establish calibration freshness or permission to move through a shared workspace.

Core `op` values are restricted by affordance type. Adding `hms.execute` to `forms.op` would violate that model. An HMS-specific action name can still use `invokeaction`. Explicit HTTP methods are needed where defaults do not cover the operation; one shared method annotation on a multi-operation form can also be misleading. URI variables are primitive substitutions, not a place to hide an entire operation envelope. Payloads and media types need coherent schema mappings.

## Models, versioning and document supply chains

Thing Models address a real duplication problem: one reusable interface can yield multiple instance descriptions with instance-specific endpoints and security. They do not provide commissioning. A generated TD still needs a binding to the physical asset and deployment. `tm:extends`, partial `tm:ref` imports, optional affordances, placeholders and composition must be resolved under size/depth/cycle limits and pinned dependencies. Automatically fetching arbitrary model references during dispatch would make the execution meaning depend on mutable network resources.

The core version object records a TD instance revision and optional model revision. It must not be reused as a single firmware/calibration/control-generation field. Semantic tags identify types but do not attest implementation. The recommended `type` link has at most one target in the best-practice relation table; compose a reusable TM or use semantic capability annotations instead of pretending a list of unrelated `type` links is a complete model-composition rule.

The original document has examples that deserve scrutiny. The model-overwriting diagram and §9.3.2 recommend preserving model constraints, while examples in §9.5 widen a dimming maximum from 100 to 200. Table 28 maps event unsubscription to `subscription`, whereas the EventAffordance defines `cancellation` for cancellation data. These are observed internal tensions, not newly confirmed official errata. The downloaded errata page does not settle them. Do not elevate a convenient example above the normative assertions or silently copy it into a conformance fixture.

The [TD errata page](https://w3c.github.io/wot-thing-description/errata11.html), read completely, lists five entries as of its 27 August 2026 update. They include the March 2025 correction to allowable inline context maps and later example-tab rendering changes. This shows why a stable public schema URL still needs a retrieved-byte hash. It also shows why hidden tabs must not be mistaken for absent example content. All extracted examples were read here, independently of browser tab visibility.

## Discovery: useful boundary, limited guarantees

Discovery separates introduction URLs from the authorized distribution of richer metadata. This is suitable for HMS: discovery should identify candidates without granting actuation authority. A direct supplied URL is sufficient as the minimum introduction mechanism. A constrained device can expose a small Thing Link to a gateway-hosted TD. A directory is optional; an HMS registry need not claim TDD conformance until its actual API matches the applicable requirements.

For an HTTP TD server, GET, HEAD, response status and media-type behavior matter. A conforming Discoverer also needs to distinguish directory and link TDs, deduplicate traversal without depending solely on optional TD IDs, and avoid loops. Recursive expansion is optional and may stop at any point. Set explicit depth, byte, host and request limits before following links. A search result or link is an untrusted candidate until authenticated enrollment resolves it.

The TDD API standardizes listing, optional CRUD, enrichment, pagination, events and search. It does not provide resource leases or physical authority. `registration.ttl` and `expires` concern the directory entry. A valid registration can describe a disconnected device, and an expired registration does not prove a machine has stopped. Keep HMS presence, description validity, commissioning validity, ownership leases and operation deadlines separate.

Pagination uses collection state information to detect changes, not an automatic transactional snapshot. Directory events use SSE; event IDs and replay are recommended, not a complete mandatory retention protocol. There is no specified atomic handoff from a listing to a watch. Therefore the HMS registry's stronger snapshot/watch requirements still need design and tests. SPARQL is optional; JSONPath and XPath search sections are informative. Adopting an expensive search engine is not necessary for minimal interoperability.

The Discovery appendix schema has an actual trailing space in the `$schema ` key. It was archived unchanged, with that defect recorded. Its TTL schema accepts a number while the ontology figure labels TTL as an unsigned integer. The API Thing Model also contains response objects without `contentType` and explicitly notes that instances need a value even for empty bodies. Generated runtime TDs need correction and validation; examples/templates are not ready-made proof. The current Discovery errata page reports zero entries, which does not establish absence of issues.

Discovery's older LAN-security discussion includes WEP and makes browser/certificate assumptions that should not become HMS's deployment prescription. Reuse the privacy boundary and authenticated metadata distribution architecture; select a current security deployment profile separately. Private asset identifiers should be protected, especially where rotating public discovery IDs is appropriate. Device presence, absence and queries can disclose operational or personal information even when no sensor sample is included.

## What this reading establishes

It establishes a documented basis for reusing TD description structure and Discovery's minimum retrieval model, and identifies precise HMS obligations that remain. It does not establish implemented TD behavioral conformance, complete WoT-suite comprehension, a finished HMS wire binding, operational interoperability, safety certification, or any compatibility with official MHS. The migration decision and acceptance boundary are recorded in [wot-reuse-decision.md](../../../docs/wot-reuse-decision.md).
