## Findings from RFC 7252

1. **Message receipt and effect evidence are different.** An empty ACK acknowledges a CON, not the success of its request (§1.2). A separate response can arrive before that ACK (§5.2.2; figure 20). Clients must handle NON responses to CON requests too (§5.2.3). RST means missing processing context, not a certified reboot or stop; figure 21 illustrates a client forgetting state and rejecting a still-valid response.
2. **Deduplication is bounded and deliberately relaxable.** Message ID is 16-bit and scoped to a source/destination endpoint; §4.5 uses SHOULD and permits repeated processing for idempotent requests and selected non-idempotent semantics. NON suppression is also relaxable. An HMS intent requires a distinct durable key, immutable digest, authenticated replay namespace and expiry floor. CoAP conformance alone does not provide once-only execution.
3. **Message IDs are not ordered application sequences.** §4.4 recommends random initial allocation but does not mandate ascending values. They cannot serve as a stream cursor, ownership epoch or fence. Rejected erratum 5429 specifically attempted to impose ascending allocation; its rejection confirms this was a protocol design choice.
4. **Transport time values are not actuator deadlines.** With defaults, transmit span is 45 s, ACK wait 93 s, exchange lifetime 247 s, NON lifetime 145 s (§4.8.2). Delayed/sleep-scheduled retransmission is allowed within the envelope (§4.2). Acknowledged separate-response timeout is application-defined (§§4.7, 5.2.2). RFC 7252 §4.4 prohibits reuse within EXCHANGE_LIFETIME, whereas §4.8.2 discusses a shorter NON lifetime; the proposed binding conservatively allocates all MIDs using the 247 s default lifetime, adjusted with the configuration.
5. **NSTART does not bound accepted work.** Default 1 limits outstanding interactions until a response or ACK is received (§4.7). It does not bound operations after empty ACK, queue bytes, decode effort, resource occupancy or stop latency. HMS must limit those separately.
6. **REST method semantics constrain hardware mappings.** GET is safe retrieval; GET/PUT/DELETE are idempotent (§§5.1, 5.8). Repeating a setpoint that resets an exposure timer can violate the intended physical idempotency. Effectful acquisition, toggle, relative motion or dispense must not be disguised as safe GET. POST needs an application operation resource and deduplication.
7. **Cache freshness differs from measurement freshness.** Missing Max-Age means 60 seconds (§§5.6.1, 5.10.5). Error responses in both 4.xx and 5.xx classes are cacheable (§§5.9.2–5.9.3), including responses to POST. Max-Age=0 prevents fresh reuse without validation; it does not provide HTTP no-store confidentiality. ETag revalidation does not reacquire a physical measurement. Preserve acquisition time, latency and clock uncertainty separately.
8. **ETag/If-Match are representation mechanisms.** ETag is opaque and resource-local; it can be a checksum, hash, version or time (§5.10.6). If-Match protects against lost resource updates (§5.10.8) but supplies no durable fence, physical interlock or multi-resource transaction.
9. **Proxies are active trust boundaries.** They may serve cached data, rewrite namespaces and translate protocols (§§5.7, 10). A 5.04 indicates missing downstream result rather than guaranteed non-execution. §9 does not specify forwarding differentiated caller authorization through proxies. §11.2 requires cached access control and restricts shared caching of coaps resources. End-to-end HMS semantics must survive every hop explicitly.
10. **Constrained sizes require measurement.** §4.6 suggests 1280-byte IP MTU assumptions, 1152-byte messages and 1024-byte payloads absent better information; these are not evidence that a small MCU or 127-byte link-layer frame can hold the entire HMS envelope. Security, tokens and options consume budget; fragmentation harms delivery probability. Need actual per-profile byte and memory budgets.
11. **URI handling is security-relevant.** Authorization and dispatch must use the same canonical interpretation (§11.1). Percent decoding occurs once; slashes may exist inside segments; empty and trailing segments matter; coap/coaps are distinct origin namespaces (§6, appendix B). A route address is not a persistent physical identity.
12. **Discovery is neither complete nor authoritative.** The server selects what it exposes (§7). Multicast requests are NON, responses may be ignored/delayed/lost, and caches can join the result set (§8; figure 23). Base DTLS modes do not secure multicast. Discovery must yield candidate evidence, not enrollment, complete inventory or a resource lease.
13. **Security and entropy are explicit deployment work.** Group-shared PSKs authenticate group membership rather than one peer (§9). NoSec permits spoofing and cross-protocol attacks; source IP alone cannot authorize effects (§11.5). §11.6 warns against key generation without good entropy and against credential sharing on exposed constrained nodes. An exclusive protected gateway may be the identity boundary, but must say so.

## Current corrections and updates

The official errata snapshot has four Verified, one Reported, one Held for Document Update and four Rejected entries. Status is part of the evidence; a report is not automatically an adopted correction. [Official records](https://errata.rfc-editor.org/search/?rfc_number=7252&presentation=records)

| ID/status | Consequence for HMS |
| --- | --- |
| 4948, Verified technical | Cache keys must include request payload when applicable. Without this, a cached application error for one POST body can be reused for a different valid body. Adopt the correction in any caching route. |
| 4949, Verified technical | Unsupported reserved Location options in a response require rejection of the response, not a 4.02 response to a response. |
| 5078, Verified technical | `ct` must not appear more than once in a discovery link; multiple values use its specified single-attribute form. Discovery remains only a format hint. |
| 4954, Verified editorial | Distinguish content-coding from character encoding and correctly describe Content-Format as media type plus content-coding. RFC 9876 supersedes registration procedures. |
| 9245, Reported technical, 2026-10-30 | §5.7.1's early example says unrecognized critical response options cause 5.02, while the same section's detailed proxy rule uses Unsafe and forwards unrecognized Safe-to-Forward options. Treat the discrepancy as an unresolved implementation-review item; do not claim the proposal was verified. |
| 4895, Held editorial | Clarifies an already-correct parsing rule: trailing slash creates an empty Uri-Path segment. Preserve this distinction. |
| 4946/4947, Rejected | Proposed URI fragment grammar changes were rejected to stay aligned with HTTP. Do not silently apply them. |
| 5284, Rejected | Proposed extra token uniqueness wording was considered redundant. RFC 9175 subsequently supplies material secure-token requirements. |
| 5429, Rejected | Proposed ascending MID constraint is a protocol change requiring consensus, not an erratum. Do not assume such ordering. |

**RFC 9175 is essential to a present secure actuation binding.** Its §2 explains why even DTLS-protected requests can be delayed. Echo permits server-clock or event-relative freshness; freshness use requires integrity protection and may require freshness at each proxy hop. A client responding to an Echo challenge is initiating a refreshed CoAP request, not renewing the HMS operation's immutable latest-start or authority. HMS must preserve the existing intent and refuse expiry. A server validates Echo at request reception; HMS still needs execution-time checks after queue delay. Echo is not a general application deduplication key, and a reachable client is not necessarily authorized. Sections 4/5.1 require safe token use for secure response binding; sequence allocation per new/rekeyed secure connection is the recommended straightforward approach. [RFC 9175](https://www.rfc-editor.org/rfc/rfc9175.html)

RFC 9175's Request-Tag identifies a short-lived block-wise request body, not a durable operation. Whole-body integrity and replay are separate; block-level DTLS integrity alone can still permit mixing delayed blocks. Its §3.8 requires proper ETag use for corresponding response-body integrity. These findings justify a release gate, not a complete block-wise HMS mapping without reading RFC 7959. Erratum 9031 for RFC 9175 is Reported (2026-07-20): the §2.4 phrase about preemptive Echo in successful “requests” should say “responses.” The unambiguous §2.3 already describes successful responses; the proposed binding uses that section without treating 9031 as verified. [Official errata](https://errata.rfc-editor.org/search/?rfc_number=9175&presentation=records)

**RFC 8974 prevents an outdated universal eight-byte-token assumption.** The optional TKL extension represents up to 65,804 bytes, with practical support constrained by implementation and datagram limits. UDP capability discovery is stateful trial-and-error with a safe CON request; tokens are hop-by-hop, and support must be established per hop. Serialized state needs integrity, replay/freshness and privacy protection as appropriate. Stateless intermediaries cannot supply a timeout without retaining request/client state, and must not statelessly use Observe. The document's §5.2 gives a 93 s outstanding-request example; that must not be generalized into an application response bound overriding RFC 7252's separate-response behavior. No errata were listed in the retrieved index. [RFC 8974](https://www.rfc-editor.org/rfc/rfc8974.html)

**RFC 9876 updates wire-format registration planning.** It replaces RFC 7252 §12.3, adds a Media Type column, changes registration ranges/reviews and temporary allocation handling, reserves 64998/64999 for documentation, and keeps 65000–65535 experimental with no operational use. HMS must not invent a production numeric Content-Format. No errata were listed in the retrieved index. [RFC 9876](https://www.rfc-editor.org/rfc/rfc9876.html)

## Design consequence and remaining work

HMS should carry one durable, authorized intent across bindings while CoAP handles compact resource messages. The gateway/controller owns replay floors, operation lifecycle, physical evidence, finite procedure budgets and fenced resources. An MCU need only implement the commissioned local subset, but its advertised bounds must be measured. Protocol retransmission is useful only when the receiving action's duplicate behavior is compatible with the promised effect semantics.

The proposed binding therefore starts with bounded, authenticated unicast requests and explicit operation/status resources, with immutable execution timing, independent capacity limits, conservative cache policy and clear proxy trust. A generic CoAP implementation, protocol ACK, nominal response code or successful key exchange cannot substitute for those application semantics. Missing endpoint capabilities are reported rather than invented by the gateway.

Remaining work includes exact schema/encoding and canonical fixtures; current deployment security profile and cryptographic-library review; complete reviews of any selected extension and its update chain; MCU/MTU/flash/wear/timing budgets; endpoint durable ledger/fence behavior; and fault/restart/physical-outcome validation. No runtime, device-network, radio or actuator execution was performed for this review.
