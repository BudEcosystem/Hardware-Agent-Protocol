## MQTT findings by mechanism

**Encoding and identifiers.** MQTT carries an application payload over an ordered lossless byte stream. Packet framing, UTF-8 validation, reason codes and property cardinality are protocol concerns. Payload Format Indicator and Content Type do not validate an HMS physical schema. User Properties can have repeated names; software must not implicitly treat them as a unique authorization dictionary. Topic matching is exact, with no normalization. Packet Identifiers are reusable nonzero 16-bit protocol identifiers, independently assigned by each direction; DUP is not an application duplicate detector. WebSocket messages are binary but MQTT packets need not align with WebSocket frame boundaries. [MQTT §§1.5, 2, 3.3.1.1, 3.3.2.3, 4.7, 6][mqtt]

**Session and persistence.** Clean Start controls prior-session reuse; Session Expiry controls retention after disconnection. Omitted expiry means zero. The client must reconcile Session Present with its own MQTT state. Session state is not necessarily power-loss durable; §4.1 explicitly discusses administrative deletion and storage failure. Retained messages are outside session state. Session-expiry timing may be delayed while the server is stopped. None of these mechanisms establishes whether a native controller has rebooted or forgotten its operation history. [MQTT §§3.1.2.4, 3.1.2.11.2, 3.2.2.1, 4.1][mqtt]

**Delivery and retries.** QoS1 receiver ownership and QoS2 duplicate suppression concern an individual MQTT exchange. The receiver need not finish onward application delivery before its acknowledgement. Packet IDs can be reused after the exchange. MQTT 5 retransmits unacknowledged QoS PUBLISH/PUBREL packets upon a reconnect with a retained session and prohibits retransmission at other times. Negative PUBACK/PUBREC terminates that exchange. Application-level retry must retain the HMS intent and obey its own durable deduplication rules. Matching subscriptions may cause extra copies, and maximum granted subscriber QoS can be lower than publication QoS. [MQTT §§3.3.4, 3.8.4, 4.3–4.6][mqtt]

**Expiry and size.** Message Expiry deletes a subscriber's queued copy only when expiry passes before onward delivery starts. It is not an execution latest-start deadline; the QoS2 sender specifically stops applying application expiry once it sends PUBLISH, and receivers still complete the QoS2 handshake when applying expiry. A broker may discard an onward message exceeding subscriber Maximum Packet Size and account for onward sending as complete. Thus an upstream ACK alone is particularly weak evidence for the physical endpoint. [MQTT §§3.1.2.11.4, 3.3.2.3.3, 4.3.3][mqtt]

**Retained messages.** RETAIN=1 replaces stored latest state; an empty retained payload removes it; RETAIN=0 does not clear a previous retained message. Retain Handling=2 suppresses subscription-time retained delivery. RAP=0 can hide the publisher's RETAIN bit on live forwards, so a subscriber cannot enforce a no-retained-command policy merely by testing received RETAIN. A broker policy plus compatible subscription settings is necessary for the proposed HMS prohibition. Retained desired-state reconciliation must be a distinct commissioned behavior. [MQTT §§3.3.1.3, 3.8.3.1][mqtt]

**Aliasing and reconnection.** Topic Aliases are directional connection-local compression state, with possible reassignment. No alias mapping carries over a new network connection, even if its MQTT session resumes. Client ID takeover disconnects the previous network client but cannot retract commands already sent to a native driver. Server Reference can suggest another broker, but cannot independently authorize moving credentials or device authority. [MQTT §§3.1.4, 3.3.2.3.4, 4.11][mqtt]

**Ordering and fan-out.** Ordered-topic rules preserve same publisher/topic/QoS ordering on nonshared subscriptions, with duplicate arrivals still possible. They are not a global total order over devices/topics. Shared subscriptions select one client per message within a share, not a resource owner. QoS1 may be reassigned after disconnection; in-progress QoS2 is tied to its original subscriber and is not reassigned if that session expires. A negative subscriber ACK discards the message instead of requeuing it. This is unsuitable as the sole durable physical work queue. [MQTT §§4.6, 4.8.2][mqtt]

**Flow control.** Receive Maximum bounds outstanding QoS1/2 PUBLISH count, not QoS0 traffic, bytes, decode effort, queued native work or execution time. It resets on connection. Protocol control packets can proceed with exhausted send quota, but an HMS stop is still a PUBLISH. Application admission, byte/CPU budgets, stop scheduling and watchdogs need independent mechanisms. [MQTT §§3.3.4, 4.9][mqtt]

**Authorization and revocation.** Security policy is outside the mandatory MQTT conformance body. Authentication and topic permission need explicit deployment configuration; connection identity does not authorize arbitrary parameters inside a command. Reauthentication can overlap normal traffic under existing authorization. UNSUBSCRIBE stops future matching additions but must finish already-started QoS deliveries and may finish buffered work. ACL changes, disconnect and unsubscription cannot certify native queue cancellation. Fence/check authority where the effect will be initiated. [MQTT §§3.10.4, 4.12, 5, 7][mqtt]

**Will and health.** The broker may delay Will publication until restart after its own failure. A delay can intentionally suppress death across a short reconnection. Keep Alive and PINGRESP concern network peers; they do not monitor an actuator task, sensor freshness or a bounded operation. MQTT's keepalive close rule is not a hard end-to-end death-publication bound. [MQTT §§3.1.2.5, 3.1.2.10, 3.1.3.2.2, 3.12–3.13][mqtt]

**Request/response.** Response Topic and Correlation Data route opaque data; they do not authenticate a responder or require result persistence. A requester must arrange subscriptions and permitted routes itself, and responses can have no interested subscriber. Bridge/topic remapping and protocol-version conversion must be evaluated explicitly. Keep required HMS identity/time/authority semantics in a preserved application envelope, not only optional MQTT5 properties. [MQTT §4.10][mqtt]

## Sparkplug findings by mechanism

**Intent and scope.** Sparkplug defines industrial topics, protobuf metrics and session conventions on MQTT3.1.1/5. Devices may be logical groupings across physical equipment. An edge node is a gateway role or a direct MQTT-enabled device; its group/node descriptor must be unique, while device IDs are unique only beneath that edge node. These are useful namespace constraints, not cryptographic enrollment. Security chapters explicitly provide non-normative guidance, not a complete mandatory authentication/authorization profile. [Sparkplug §§1.4, 1.7, 3, 4.1, 7][sparkplug]

**Wire profile.** All ordinary node/device BIRTH, DATA, DDEATH and command publications use QoS0 and no retain. NDEATH Will uses QoS1/no retain; host STATE uses QoS1/retain and JSON rather than the protobuf payload. All edge and host MQTT5 connections use Clean Start=true with zero Session Expiry. The specification's continuously connected or “persistent” node language must not be interpreted as an MQTT durable session. Commands request a metric value, without a standard command operation ID, durable result query or atomic batch contract. [Sparkplug §§2.5, 4.2, 5.3–5.6, 6.4.23–6.4.27][sparkplug]

**Birth/death transitions.** NBIRTH describes the node; devices need their own DBIRTH before their values can be current. NDEATH invalidates node and attached-device data, with host receipt time used for the death event because the Will timestamp was prepared at CONNECT. DDEATH is produced by the edge when a device becomes unavailable and uses its own timestamp. A host losing its broker connection must mark associated data stale. This preserves observational uncertainty; it does not mean the physical actuator stopped. [Sparkplug §§4.2.1–4.2.2, 5.3–5.7][sparkplug]

**Two different small sequences.** `bdSeq` is an INT64 metric whose specified operational range wraps 0–255 on CONNECT and matches NBIRTH/NDEATH. `seq` is a separate payload field advancing across node/device messages, also 0–255; NDEATH and commands omit it. Rebirth within an existing connection reuses `bdSeq`. Neither can serve as a lifetime operation identity, anti-replay epoch or fencing generation. A very old death and a later wrapped birth can share a value; HMS requires independent continuity/authority evidence. [Sparkplug §§5.4, 5.17, 6.4.5, 6.4.23–6.4.26][sparkplug]

**Aliases and model change.** Metric aliases are optional, unique across the entire edge-node metric set, introduced with names in BIRTH, then used instead of names in DATA/CMD. These are not MQTT Topic Aliases. Unknown metrics/aliases can trigger rebirth. Node Control/Rebirth is the named exception and cannot have an alias. Rebirth stops DATA, emits BIRTH sequence, then resumes; it neither increments `bdSeq` nor cancels ongoing physical work. Catalogue-dependent queued writes must not be interpreted against a new alias table. [Sparkplug §§5.15, 5.17, 6.4.6][sparkplug]

**Ordering and observation.** Cross-topic sequence reordering uses a configurable timeout, with rebirth on unrecovered gaps. The standard leaves application treatment of out-of-order data flexible; a historian and a control decision engine need different policies. Multiple value changes for one metric can be batched with distinct timestamps. Payload time is publication time; metric time is acquisition time. Historical and null flags are semantically significant. Quality codes are BAD0, GOOD192 and STALE500; GOOD does not prove an independent sensor or bounded acquisition age. [Sparkplug §§5.9, 5.16, 6.4.5–6.4.9][sparkplug]

**Discovery cannot guarantee completeness through silence.** BIRTH is not normally retained. A newly joined host can receive DATA without an earlier BIRTH and request resynchronization; however a quiescent node need not send new DATA at all. Unknown nodes that cannot be rebirthed by the observer may remain undiscovered. Even sequence-gap detection needs a later message. Sparkplug-aware brokers help with `$sparkplug/certificates/...` cached BIRTHs, but those are the original snapshots and explicitly not current metric values. Discovery results must distinguish cached metadata, current session evidence and incomplete coverage. [Sparkplug §§2.2, 5.15, 5.17, 10.1.4][sparkplug]

**Primary host and distributed presence.** Host STATE is retained; birth and Will carry the connection's matching timestamp, tracked per broker. An edge configured for a primary host waits for its online STATE, ignores older offline state and moves servers upon valid offline state. An edge uses one broker at a time. This prevents certain stranded data paths, but is not a consensus algorithm or controller lease. Clock rollback, loss of history, stale retained online state and partitioned old controllers are outside a strong fencing argument. The HA chapter's cluster and load-balancer discussions are non-normative deployment sketches. [Sparkplug §§5.4, 5.10, 5.13–5.14, 8][sparkplug]

**Decoding and model limits.** Protobuf's optional fields do not make required Sparkplug fields optional. Bound repeated metric/property/template depth and file/multipart data sizes. Template definitions are introduced at node BIRTH; instances reference known definitions. Numeric representation, signed values stored in unsigned protobuf fields, byte arrays, null, historical values and unit metadata require lossless mapping. Generic Sparkplug metrics alone do not supply every physical action's unit, frame, limits or proof requirements. [Sparkplug §§6.4.1, 6.4.6–6.4.17][sparkplug]

## Material source inconsistencies and release questions

The following are findings in the pinned publications, not claims that an upstream errata decision has been made. Do not silently repair archived sources, infer implementation behavior from a contradictory example, or claim these have been resolved by testing.

| Location | Observed inconsistency | Conservative design/release consequence |
| --- | --- | --- |
| MQTT §3.1.2.11.2 non-normative comment | It equates Clean Start=0 with omitted expiry to MQTT3.1.1 CleanSession=0, while the normative omitted-expiry value is zero. | Use explicit expiry and normative behavior; consult current official errata before releasing a compatibility claim. |
| MQTT Appendix B, MQTT-3.3.1-10 | Its Retain Handling=1 summary reverses the existing/new-subscription conditions from §3.3.1.3; Appendix B also truncates the following retained-message statement. | Use normative body §§3.3.1.3/3.8.3.1. HMS command suppression uses Retain Handling=2 anyway. |
| Sparkplug §3.5 versus §1.4.1 | One paragraph says it supports multiple primary hosts for one edge, while the definitions explicitly describe one. | Configure one primary host per edge; do not infer distributed command arbitration from either wording. |
| Sparkplug §2.5 versus §5.5/§6.4.25 | Early nonpersistent-node prose allows graceful departure without death; later termination clauses require/provide NDEATH, including MQTT5 Disconnect with Will. | Follow explicit termination requirements and verify TCK/errata. For MQTT5 satisfy the stated Will reason-code behavior and tolerate duplicate matched deaths. |
| Sparkplug §4.2.1 versus §§5.4, 6.4.5, 6.4.19 | NBIRTH seq is required to be zero in one clause, while other clauses permit any value0–255. | Emit zero to satisfy the narrower condition; document receiving policy and seek current authoritative resolution before conformance claims. |
| Sparkplug §5.13 Will-payload wording versus §4.2 host death definition | One statement refers to the prior CONNECT's timestamp when defining the new Will, while the detailed death definition says current CONNECT time. | Track one current connection timestamp per broker consistently with birth/Will correlation; verify authoritative clarification. |
| Sparkplug §5.15 versus §5.9 | Rebirth requests are described as optional/configurable in receive-data prose, while a configured reorder timeout requires a rebirth when the gap persists. | Respect the specific configured-timeout requirement; non-writers must expose inability to recover rather than pretend synchronized state. |
| Sparkplug §8.2 step1 | The non-normative HA example refers to `bdSeq` inside host STATE, while normative STATE uses JSON `online` and `timestamp`. | Apply the normative host STATE timestamp rules; never substitute the node birth/death metric. |
| Sparkplug §6.4.25 example | Example labels `bdSeq` UInt64 whereas §5.4 requires INT64. | Use the explicit INT64 requirement and reject incompatible commissioned mappings. |
| Sparkplug §6.4.17 arrays | Int8 example maps -23 to 0xEF (which does not encode -23 in 8-bit two's complement); float/double examples appear big-endian despite little-endian prose; DateTime example lists fewer bytes than two 8-byte elements. | Do not build byte conformance fixtures from examples without upstream resolution. These representations were not implemented in this task. |

Figure inspection also confirms editorial shorthand in Figure4's host STATE topic labels and the off-by-one figure references in nearby prose. Follow the explicit topic rules rather than copying shorthand labels into a binding.
