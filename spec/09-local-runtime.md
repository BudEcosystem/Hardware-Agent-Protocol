# Executable local runtime — experimental v0.1

The repository now runs a local simulation service through `python3 -m hms`. It combines the [host contract and journal](08-host-contract.md), a versioned registry, mandatory admission policy, observations, a synthetic adapter and a Linux Unix-domain socket CLI. It executes three synthetic capabilities and retains their operation records across restart. This is an executable HMS prototype, with no commissioned physical device, physical-conformance claim or official Anthropic MHS compatibility claim.

The implementation is [registry.py](../hms/registry.py), [runtime.py](../hms/runtime.py), [simulator.py](../hms/simulator.py), [ipc.py](../hms/ipc.py) and [cli.py](../hms/cli.py). [Local-control instructions](../docs/local-control.md) give runnable commands. This document describes that implemented surface; broader requirements in [execution](02-execution.md) and [registry/runtime](03-registry-runtime.md) still apply before a physical deployment.

An additional explicit `simulation:compact` installation now connects the same checked host API to the original native C endpoint. It uses `--init-compact-simulation --endpoint-fd N`, stores mappings and receipts in the authority database, and leaves endpoint lifetime with a trusted external launcher. The [compact binding document](../docs/compact-host-binding.md) defines its narrower envelopes, clock assumptions and recovery rules. The SQLite-plant details below continue to describe the original `simulation:local` backend. The [multi-adapter installation profile](../docs/multi-adapter-runtime.md) adds explicit `simulation:multi` catalogs, separate plants/compact state and immutable route recovery while retaining shared claims and authority.

## Initialization and authority

`serve --init-simulation` explicitly creates a new authority database, registry and separate simulated-plant database. It bootstraps the invoking Unix principal as administrator of `simulation:local` and installs the synthetic definitions. Ordinary startup opens existing state; a missing authority or plant is an error. Initialization does not silently replace an existing authority. There is no initialization rollback or repair ceremony across both database files if creation is interrupted.

The state directory must belong to the invoking Unix user and have exactly mode `0700`. Startup traverses its absolute path using directory-relative opens that refuse symlinks. Every ancestor must belong to root or the invoking UID and must not allow group/other writes, except for a trusted-owner sticky directory whose traversed child is also trusted-owned. Thus a private child under an ordinary shared writable directory is refused. Existing authority/plant databases, owner locks and SQLite sidecars must be single-link regular files owned by that UID with mode `0600`.

This protected-ancestor policy prevents replacement by an untrusted UID; it does not promise rename resilience or isolation from the current UID/root. Stock SQLite resolves pathnames and opens sidecars separately, so merely using `/proc/self/fd` would not establish a safe directory-capability storage design. The Journal and simulated plant each hold a process-owner lock. Their storage and stale-backup restrictions remain those of the host profile. [Independent path regressions](../tests/test_state_path_review.py) exercise the startup policy.

Registry records use the Journal's connection and authority mutex. Provisioning mutations, grants and admission therefore participate in the same transaction boundary as operation claims. `RegistryPolicy.attach` rejects a registry owned by a different Journal policy. Trusted provisioning APIs exist in Python; publication, enrollment, grants, binding changes and adapter ingress are not public local RPC methods.

The principal/deployment pair comes from the embedding service. Registry grants distinguish `read`, exact `invoke:<action>`, `cancel`, `namespace` and administration. A wildcard administrator grant authorizes the deployment. New invocation requires both exact action permission and instance read permission. Namespace permission is checked in its issuance/pruning transaction. Results, event pages and cancellation are restricted to the original operation principal/deployment, with the relevant current grant; administrator access does not provide cross-principal operation ownership. A stored `stop` grant has no implemented stop service.

## Types, instances and bindings

The implemented records remain separate:

| Record | Implemented meaning |
|---|---|
| Type bundle | Immutable public TD and strict execution contract pinned by one digest |
| Enrolled instance | Stable ID, deployment, type digest and explicit simulation/gateway/device identity kind/reference |
| Binding | Versioned adapter, control/calibration revisions, resource map and per-action argument envelopes |
| Presence | Current endpoint session and expiring availability from trusted adapter ingress |
| Operation/resource authority | Journal intent, replay identity, admission, resource claims/fences and evidence history |

A type bundle has exactly `profile: "hms.type-bundle/0.1"`, `td` and `execution`. The description digest is lowercase `sha256:` plus SHA-256 of:

```text
ASCII("HMS-TYPE-BUNDLE-v0.1") || 0x00 || UTF8(JCS(bundle))
```

Publication validates and retains the canonical bundle. Pure validation has a bounded 32-entry cache keyed by at most 65,536 bytes of type-preserving serialized input; caller objects and authorization decisions are never cached. Integral floating-point inputs cannot borrow a validation result from an exact integer merely because JCS makes their digest bytes identical. A new bundle does not rewrite an enrolled instance or an operation's pinned description. Re-enrollment of an existing instance ID is refused. Capability identifiers are indexed for discovery; the current profile does not infer capability compatibility, dimensions, coordinate transforms or substitutability from those identifiers.

The execution profile is `hms.execution-contract/0.1`. It requires exactly the recognized features `durable-operations/1`, `binding-generations/1`, `physical-evidence/1` and `host-invoke/0.1`, without duplicates. Recognizing physical-evidence semantics does not mean a physical evidence producer is installed. The profile carries 1–16 capability identifiers, 1–32 properties and 1–32 actions. Each property has an explicit schema, unit and nullable frame. Each action has an object input schema, resource roles, effect identifier, maximum run duration, completion evidence kinds and at most 32 equality preconditions. Preconditions name a property, expected value, maximum age and evidence kind. These are intentionally limited predicates, not a procedure language or general physical constraint solver.

Executable schemas use an explicit subset of JSON Schema 2020-12. Allowed keywords are `type`, `properties`, `required`, `additionalProperties`, `items`, `minItems`, `maxItems`, `minimum`, `maximum`, `enum`, `const`, `minLength` and `maxLength`. Every schema supplies one supported scalar/object/array type. Objects are closed, declare their properties and required list, and have at most 64 properties. Arrays require an item schema and a maximum item count no greater than 256. Strings require a maximum length no greater than 4096. Schema nesting depth is capped at 12. The host parser's byte, tree and numeric bounds also apply. References, composition, patterns, formats and unknown keywords are rejected; no schema is fetched from a supplied URL. This subset does not implement all JSON Schema or WoT DataSchema features.

A binding uses `hms.binding/0.1`, pins the instance's type digest and maps every declared resource role to a concrete local resource ID. Every action has an additional argument schema; admission requires both type and binding schemas, so a binding cannot widen the type's accepted inputs. Resource IDs are deduplicated before claim acquisition. Binding generations cannot be reused, and their complete documents remain in history so later evidence is judged against the operation's original adapter policy. Rebinding is refused while any resource claim for the instance remains unresolved. A new binding clears current presence, observations and active streams. Invalidation prevents new admission/dispatch; the runtime also rechecks a pending synthetic effect before committing it.

Only `simulation` and `uncommissioned` binding modes are accepted. Simulation requires a simulation identity; uncommissioned bindings cannot execute. Gateway/device identity records are data, not cryptographic enrollment. The implemented simulator supports only the three installed instances and their declared primitives; publishing an arbitrary type does not install a corresponding adapter.

## TD projection and transport mapping

Publication checks the TD against the retained, hash-pinned informative TD 1.1 schema, then checks the HMS relationship between description and execution. The action/property names must agree. Property schema, unit, coordinate-frame metadata and `readOnly: true` must match the execution projection. Action input describes the complete `hms.invoke/0.1` envelope with that action's arguments, rather than accepting a bare argument object. Actions explicitly advertise `safe: false`, `idempotent: false` and `synchronous: false`; durable duplicate suppression does not redefine an effectful action as inherently idempotent.

The projection expands the host envelope's retained local schema references and omits `additionalProperties`, which is not the TD DataSchema closure mechanism. The execution contract and host parser retain strict object closure. TD shape/projection checks are a bounded compatibility check, not a complete WoT conformance certification.

Property forms must explicitly use only `readproperty`; action forms must explicitly use only `invokeaction`. Missing, empty or mixed operation declarations fail. Top-level forms and event affordances are unsupported. Consequently the runtime description cannot advertise a raw property-write or bulk-write path around operation admission.

The generated forms use `https://example.invalid/...` placeholders. The draft HMS vocabulary also uses `example.invalid`. These are retained descriptive fixtures, not installed HTTPS endpoints, resolvable metadata services or an official vocabulary registration. The TD's synthetic security description does not define the local socket's authentication. The implemented mapping is `observe` for property reads and `invoke` with the full host request for actions, over `hctl.local/0.1`. No HTTP, CoAP, MQTT, serial or Harness transport is installed by this projection.

## Discovery, preparation and admission

Discovery filters by deployment, read authority and optional exact capability before applying the page limit. Results are ordered by instance ID and include description digest, identity kind, retirement/binding status and available presence metadata. The limit is 1–100. Its authenticated cursor binds principal, deployment, capability filter, registry revision and last returned instance. Catalog or grant changes invalidate an old revision; another caller cannot use the cursor. Presence can change between pages, so a catalog cursor does not freeze live availability. An unavailable instance can remain discoverable and describable.

`describe` returns the exact bundle and current instance/binding/presence records under read authority; an optional expected digest detects disagreement. `prepare` resolves the current binding, calibration, control generation, description and endpoint session into a complete immutable intent. It checks the host envelope and current policy, then returns `{request, requestDigest, admitted: false}`. It does not issue/validate a replay namespace, reserve resources or freeze observations. The caller must retain the returned request for retries. Submission independently validates the namespace and performs admission again.

`invoke` supplies only the complete host request; caller-selected authority fields cannot be added to the RPC. Existing replay-key lookup and result authorization precede new actuation admission as defined by the Journal. New admission checks the live instance/binding, every pinned generation, simulation mode, unexpired presence and exact endpoint session; exact action/read authority; the intersection of argument schemas; maximum duration; required-effect support; and each fresh observation predicate. `physical_verified` is refused. It resolves resource claims and sets a local lease no later than the requested completion deadline or 60 seconds after admission.

The Journal atomically retains admission, intent, replay mapping, all resource claims/fence increments and the first event. Preparation does not perform that commit. Immediately before dispatch, policy and timing are checked again; a stale binding, expired availability, revoked permission or failed precondition can reject accepted work before dispatch. The Journal records possible-send ownership before returning a dispatch ticket.

## Observation epochs and freshness

Presence and observation reports are trusted adapter ingress, separate from model-facing methods. Presence requires the installed adapter and an active binding; stream creation and observations additionally match the binding generation and current endpoint session. Presence TTL is bounded to 1–60,000 milliseconds. Replacing session A with B records durable history and prevents later reuse of A, including after host restart. Keeping the same endpoint session across a binding change is allowed; a configuration change does not invent a device reboot.

Each instance/property stream has an explicit epoch. A new stream epoch cannot reuse one in retained history, clears the prior observation, and permits a new sequence. Within an epoch, accepted sequence numbers must strictly increase. Binding changes and endpoint-session changes invalidate active observations/streams. A transport retransmission or delayed sample cannot reset ordering by supplying an old epoch.

The server constructs `hms.observation/0.1` records with property value/unit/frame, evidence kind/source/quality, stream epoch/sequence, endpoint session, control/binding/calibration revisions, acquisition clock metadata, host receipt metadata, acquisition-latency bound, clock-uncertainty bound and measurement uncertainty. Property values must satisfy the pinned schema; uncertainty units must agree. Simulation identity requires simulation evidence. These checks validate ingress consistency; they do not authenticate an arbitrary external measurement source.

Receipt ticks come from the injected host monotonic clock. Their epoch includes the authority ID and current Journal owner epoch. Acquisition clock-domain/epoch/ticks remain separately labeled adapter data. For a current receipt epoch and usable bounds, the read computes:

```text
ageUpperBoundMs = hostMonotonicNow - receiptTicksMs
                  + acquisitionLatencyBoundMs + clockUncertaintyMs
```

Unknown latency/clock bounds, a changed receipt epoch, clock failure/regression or a sum above the canonical safe-integer bound produces unknown age/quality. Detected monotonic-clock failure invalidates that Registry object's mapping; merely advancing the clock again does not repair it. Reopening the Journal creates a new receipt epoch, so persisted old receipts cannot become fresh under a new clock origin. Admission requires valid quality, the requested evidence kind, and an age no greater than each predicate's limit. A plain historical read can return stale/invalid/unknown data explicitly. Observation freshness alone does not authorize execution; admission also requires current presence and binding.

The CLI requires explicit maximum age and evidence kind for `observe`. The lower-level RPC permits either to be omitted for a descriptive read. The simulator samples synthetic state approximately every 200 ms and renews presence for 3000 ms; it labels synthetic acquisition latency, clock uncertainty and measurement uncertainty as zero. Those values describe this in-process model, not a sensor or a measured physical latency bound.

## Synthetic execution and recovery

The installed scenarios are a home fan `set_level` in percent, microscope `move_absolute` in micrometres and the named synthetic frame, and inspection-cell `inspect` with a recipe and part ID. Their numeric ranges, ready flags and results are fixtures, not equipment limits or calibration. The independent simulated-plant validator checks supported instance/action/arguments, endpoint session, one concrete resource claim/fence and required-effect policy before accepting a receipt.

The plant persists endpoint session, resource-fence floors, synthetic state and per-operation receipts in its own SQLite database. `begin` records a pending receipt without an effect. Repeated operation IDs must have the same digest and canonical intent. `finish` changes synthetic state and the completed receipt together in one plant transaction; cancellation records `effectCommitted: false`. The plant rejects stale fences and refuses a pending commit superseded by a newer fence.

The host Journal and plant are separate transaction domains. A crash after plant commit and before Journal completion is resolved from the durable plant receipt; it is not a cross-database atomic commit or proof that arbitrary physical equipment offers the same guarantee. Runtime settlement checks the receipt's digest and canonical intent, records simulation evidence and then releases claims with synthetic quiescence evidence. `effectVerification` remains `unverified`; a completed synthetic capability is not physically verified.

The worker normally polls at 20 ms, starts a pending synthetic effect with a nominal 50 ms delay, and handles bounded work pages. Before a pending effect commit it checks cancellation, monotonic/wall-clock authority, maximum run time, completion deadline, lease, current authorization, binding and observation predicates while retaining the authority mutex. A failed check records a synthetic no-effect receipt. Timing checks are cooperative host checks; the polling interval and delay establish no worst-case scheduling, filesystem, shutdown or physical deadline guarantee.

On Journal reopen, prior dispatching/running operations become `outcome_unknown` and retain claims. The plant cancels its still-pending receipts on owner reopen, since this model has no effect before commit; it never resumes them implicitly. A completed durable receipt can reconcile an unknown operation without executing again. A missing receipt leaves outcome unknown and retains claims. Accepted, never-dispatched work remains eligible only after fresh admission rechecks. The simulator's endpoint session persists across process reopen, while the new host receipt/stream epochs ensure observations are reacquired.

Cancellation before dispatch uses the Journal transaction's exclusion proof. After dispatch it remains separate from execution until the simulated adapter provides a termination/completion receipt. A disconnected CLI does not cancel work, and a cancellation request does not itself prove termination. Clean runtime shutdown stops the worker and closes stores; it is not an independent emergency-stop protocol. Recovery on subsequent open handles pending synthetic receipts under the rules above.

## Local socket and CLI boundary

The Linux pathname socket serves one newline-delimited JSON request per connection. Its exact envelope is `protocol: "hctl.local/0.1"`, `requestId`, `method` and `params`. Responses echo protocol/id with either `result` or `error: {code}`. The methods are `discover`, `describe`, `observe`, `namespace`, `prepare`, `invoke`, `operation`, `events` and `cancel`; each has a parameter allowlist. There is no public adapter-ingress, arbitrary code, configuration, grant, enrollment or stop method.

The socket's private parent directory must already exist, belong to the invoking user and have mode `0700`; the socket has mode `0600`. Symlinked parent paths and any existing socket pathname are refused. Binding/access/cleanup use the held directory descriptor through Linux procfs; cleanup removes only the server's own socket inode. There is no abstract-socket or TCP fallback. A leftover socket after an unclean exit requires deliberate operator cleanup once the former service is stopped.

The server derives `posix:<uid>` from `SO_PEERCRED` and uses the opened runtime's deployment. The client checks the server UID against the socket owner. All processes with the same UID share this principal, including model-accessible shells. Session IDs, request IDs and agent names are not separate authorities. A transferred connection descriptor is still associated with the original connection credentials. The current CLI therefore provides a Unix-user boundary and registry authorization within that boundary, not per-agent delegation or isolation. Distinct in-process principals in tests demonstrate policy logic; they do not establish separate authenticated agent identities on this socket.

Complete request/response wrappers are each limited to 65,536 bytes excluding the newline. An inner invocation at the host parser's full byte limit may not fit the wrapper. The server limits active handlers and listener backlog to 16. Socket I/O has a two-second monotonic deadline; slow fragments do not renew it. The deadline cannot interrupt a blocking runtime method or filesystem call. Shutdown drains handlers before closing the runtime, so it has no fixed completion-time guarantee.

The CLI emits JSON, uses explicit files for prepared/invocation content, and makes one transport attempt. A timeout, lost response or oversized response can occur after admission. Recover with the identical retained request and replay key, or with the returned operation ID; inventing a new key risks a new operation. Transport request IDs correlate replies only and do not replace durable operation keys.

## Implemented limits and evidence

This runtime has no physical adapter, commissioned limits/calibration, authenticated device enrollment, key provisioning, remote secure transport, per-agent credential/delegation mechanism, device-native deadline/lease watchdog, procedure engine or large-data store. A [local MCP stdio projection](../docs/mcp-integration.md) now supports the current and selected legacy protocol; remote authorization and broader extensions remain unfinished. The [native Harness overlay](../integration/harness/README.md) is tested in an isolated checkout; its production packaging and persistence gates remain incomplete. Events have bounded pages; retention/gap recovery, storage quotas and large-registry performance remain unfinished. Backups, stale-state restore and state migration require explicit designs. The [formal local response contracts](10-local-api-contracts.md) do not by themselves provide complete domain profiles or physical conformance.

There is no independent bounded stop path. Ordinary cancellation and synthetic effect checks use the same process, authority mutex and stores; they cannot meet the execution specification's stop requirement during a stalled writer, failed logger or blocked runtime. Physical use remains unavailable until a separate commissioned stop/protection design and its evidence exist.

[Registry review regressions](../tests/test_registry_review.py) and their [historical review receipt](../artifacts/verification/registry-independent-review.json) cover identified session replay, freshness, type/schema, projection, grant, evidence-history and transaction-boundary defects. [Runtime tests](../tests/test_runtime.py) cover synthetic scheduling and recovery; [CLI integration tests](../tests/test_runtime_ipc.py) exercise the real local service with persistent synthetic state. These are executable test sources with their own run evidence, not a claim of exhaustive verification or physical conformance.
