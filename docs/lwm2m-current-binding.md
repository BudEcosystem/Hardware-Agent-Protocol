The current approved OMA release is **Core 1.2.2 and Transport 1.2.2, dated 2024-06-13**, verified against the official release directory, release definition and current OMA knowledge base on 2026-11-06. This review completes the current specification reading that was explicitly unfinished in [the earlier binding proposal](lwm2m-binding.md). It proposes an HMS adapter contract; it does not implement an adapter or establish device conformance. ## Native guarantees and the HMS boundary

The following requirements are proposed HMS binding decisions. Their native basis is Core §§6–8 and Transport §§5–8; they do not assert that an unmodified LwM2M client already implements HMS intent storage, fences or deadlines. [Core](https://www.openmobilealliance.org/release/LightweightM2M/V1_2_2-20240613-A/HTML-Version/OMA-TS-LightweightM2M_Core-V1_2_2-20240613-A.html), [Transport](https://www.openmobilealliance.org/release/LightweightM2M/V1_2_2-20240613-A/HTML-Version/OMA-TS-LightweightM2M_Transport-V1_2_2-20240613-A.html).

| Native facility | What the adapter may record | What requires additional enforcement or evidence |
|---|---|---|
| Authenticated client/server association | Peer identity and the authentication method actually used | Physical target commissioning, current HMS actor authority, exclusive control and endpoint session identity |
| Register, Update, lifetime and Profile ID | Native registration, route and versioned inventory observations | Operation leases, executable capability approval and continuous reachability |
| Write, Execute, Create and Delete response | The result defined by that native operation and resource | Durable intent deduplication, equipment completion, postconditions and rollback |
| Observe, Notify and Send | Delivered values, native timestamps and reporting context | Fresh acquisition, uninterrupted sampling, completeness and synchronized multi-resource snapshots |
| Native ACL and Access Control Owner | Server permissions for an object instance and authority to edit its ACL | Exclusive physical ownership, a monotonic fencing token or prevention of manual/local interference |
| Queue Mode and reconnect | Availability and transport recovery events | Durable queue contents, order, command expiry, cancellation and a bounded stop time |
| Firmware Object 5 | Transfer/install states and the specified update result | Image authenticity, compatibility, commissioned readiness and installed-firmware rollback |

An adapter should expose commissioned capabilities, not unrestricted agent-facing `write(path, value)` and `execute(path, text)`. Admission still needs the actor, exact target and binding generation, typed argument bounds, resource claims, immutable timing constraints and required evidence from [the HMS execution contract](../spec/02-execution.md). A LwM2M Resource is a data/action field; it is not automatically an HMS resource claim.

## Execute, retries and physical effects

Core §6.3.5 makes Execute an action on an individual executable Resource. Its optional text arguments use distinct digit keys, each appearing at most once. The syntax does not define physical units, coordinate frames, safe parameter bounds or a generic invocation identifier. Do not add an HMS key to an undocumented argument slot. The resource definition must supply its semantics; a commissioned extension or gateway operation service must supply durable intent correlation when required.

Transport responses describe completion of the native operation. That wording must be interpreted with the target object definition. For example, a firmware URI Write can succeed before download or installation fails. CoAP block continuation acknowledges progress transferring bytes. Neither is independent physical completion evidence. After ambiguous dispatch or response loss, preserve possible effects and query resource-specific status; a new request token, connection, registration or actor retry must not silently execute the physical intent again. CoAP message identifiers, MQTT correlation tokens and security replay windows are not persistent HMS intent receipts. [Core §§6.3.3–6.3.7 and Appendix E.6; Transport §§6.4, 6.7, 8.3–8.5](https://www.openmobilealliance.org/release/LightweightM2M/V1_2_2-20240613-A/HTML-Version/OMA-TS-LightweightM2M_Transport-V1_2_2-20240613-A.html).

There is no universal Execute cancellation or action-status service in these specifications. Cancel Observation only ends a reporting relationship. Resource-specific Stop or Cancel methods must declare their applicable states and attainable result. An adapter timeout, connection close or subscriber removal cannot stand in for a physical stop. The HMS bounded-stop exception remains installation-specific; a sleeping endpoint cannot gain a remote stop guarantee from registration alone.

Create has an all-or-error resource-instantiation rule. Write-Composite supplies atomic updates to its addressed resource values; it must not be emulated with ordinary sequential writes while retaining that guarantee. Read-Composite is best effort and non-atomic and can omit unavailable or unauthorized values. These distinctions concern the native information model. They do not establish undo of resulting physical actions, cross-device transactions or a simultaneous sensor snapshot. Optional unknown resources can be ignored under native compatibility rules; HMS should reject unrecognized action arguments before translation instead of relying on native permissiveness. [Core §§6.3.3, 6.3.6, 6.3.8–6.3.9](https://www.openmobilealliance.org/release/LightweightM2M/V1_2_2-20240613-A/HTML-Version/OMA-TS-LightweightM2M_Core-V1_2_2-20240613-A.html).

## Registration, reporting and uncertain continuity

Registration expiration removes native registration/observation state. An Update error requires the client to register again before further communication; a new Register replaces old registration state and requires the server to restore desired observations. Conversely, a client is encouraged to preserve observation state across reboot. Neither a surviving observation nor a changed transport association proves an unchanged endpoint execution session. The binding needs a separately commissioned boot/session signal and an explicit gap/resnapshot state when continuity is uncertain. Registration lifetime zero can mean infinite registration; it must not create infinite HMS authority. [Core §§6.2 and 6.4](https://www.openmobilealliance.org/release/LightweightM2M/V1_2_2-20240613-A/HTML-Version/OMA-TS-LightweightM2M_Core-V1_2_2-20240613-A.html).

Native retry/backoff and priority resources control registration recovery, including possible bootstrap fallback. They do not authorize effect retries. A binding change can apply to a future transport session; the Registration Update Trigger can explicitly release the existing transport and select a supported replacement. Resolve that transition before reusing a route or assuming delivery continuity. Pin object versions separately from the enabler version and retain the full object-definition digest. The dynamically generated Profile ID includes object versions but can use a short hash; it is an inventory shortcut, not an HMS intent digest or authorization token.

Observe returns initial information and later notifications. `pmin` and `pmax` constrain reporting, including notifications of unchanged values; `epmin` and `epmax` concern evaluation of reporting criteria. None supplies a universal acquisition-age bound. Attribute precedence depends on observation scope, and changing attributes during an observation has implementation-dependent evaluation details. Recreating an observation can itself lose information. Preserve this uncertainty instead of inferring uninterrupted measurement from successful subscription setup.

Historical notification storage is bounded and implementation dependent. `hqmax` discards the oldest retained value when the limit is reached. An arrival after reconnect can therefore be old, incomplete history. Preserve native SenML time/base-time, receive time, stream epoch and clock-quality information separately. Absence of a timestamp stays absent; a writable Device Current Time resource does not establish trusted monotonic operation time. Store gaps explicitly rather than synthesizing missing samples. [Core §§6.4 and 7.4–7.5](https://www.openmobilealliance.org/release/LightweightM2M/V1_2_2-20240613-A/HTML-Version/OMA-TS-LightweightM2M_Core-V1_2_2-20240613-A.html).

Send is optional and client initiated. It can report only eligible registered, readable resources authorized for the receiving server; ineligible values are excluded. The Mute Send resource can disable it, and its absence also disables Send under the defined behavior. That suppresses reporting, not the underlying measurement or action. A missing report is consequently not proof that an actuator stopped or a sensor ceased collecting. Transport HTTP provides Send but does not provide Observe/Notify in this release.

## Queues and binding-specific recovery

Transport §6.5 explicitly does not mandate a queue implementation, queue location or its detailed behavior. Queue Mode says the client may be offline for an extended interval and lets the server adapt communication. The awake recommendation uses CoAP `MAX_TRANSMIT_WAIT`; failed retransmission is reported to an application through an API outside the specification. These rules provide no universal durable command backlog, cancellation API or deadline enforcement. [Transport §§6.5–6.6](https://www.openmobilealliance.org/release/LightweightM2M/V1_2_2-20240613-A/HTML-Version/OMA-TS-LightweightM2M_Transport-V1_2_2-20240613-A.html).

Before dispatch, the HMS adapter must recheck authority, latest start, binding/session generation and local interlocks. Once another native layer may have accepted the request, deleting an adapter queue record is insufficient. A queue or endpoint that cannot enforce expiry at the final execution boundary cannot support a promised revocable, time-bounded offline mutation. Reconnection or Update must never renew an admitted operation's deadline. Unreachable cancellation remains unconfirmed, with locally enforced loss-of-contact behavior where commissioned.

| Binding | Source detail that changes the adapter contract |
|---|---|
| CoAP/UDP | Execute, Notify and Send can be non-confirmable. A response and an ACK are different evidence. Transport §1.2 removes an earlier ambiguous requirement to re-register on every new CoAP security context. DTLS connection identifiers can preserve an association across address changes. |
| CoAP/SMS trigger | Retransmission and payload constraints differ from UDP. The special Registration Update Trigger outside the SMS binding must not receive an Execute response; a missing response is expected here. |
| HTTP | Optional binding; only Send for information reporting. §7.1.3 still requires registration when a new security context is created. §7.1.4 excludes Read-Composite and Write-Composite, despite contradictory status-table rows. |
| MQTT | Integer tokens correlate requests/results; they are not durable effect keys. Client/server traffic can share a topic, so distinguish direction and operation/result structure. Qualify tenant/topic permissions, retained messages, QoS, broker session recovery and expiry in the actual deployment. Transport TLS terminates at the broker; application COSE has a separate purpose and configuration. |
| LoRaWAN | Normative Appendix C uses receive windows, special delivery notifications and altered retransmission rules. Its default acknowledgment timeout is 300 seconds. Network delivery notification is separate from a CoAP result; this is unsuitable evidence for a short actuator deadline. |
| 3GPP CIoT | Informative Appendix D describes network buffering, rate limits and MTU limits without NAS segmentation. Network buffering plus server Queue Mode needs explicit coordination. Network timers and accepted sleep schedules are not execution leases. |

This review reads the LwM2M mapping in full. It does not claim full reading of every referenced CoAP, MQTT, TLS, LoRaWAN or 3GPP standard, or qualify an implementation's behavior under those standards. [Transport §§5–8 and Appendices C–D](https://www.openmobilealliance.org/release/LightweightM2M/V1_2_2-20240613-A/HTML-Version/OMA-TS-LightweightM2M_Transport-V1_2_2-20240613-A.html).

## Authority, credentials and maintenance effects

Native ACLs authorize servers for object instances, with operation support checked separately. The Access Control Owner manages the ACL; it is not a physical execution owner. Single-server configurations may have implicit full access, and multiple authorized servers can independently affect the same equipment. HMS exclusivity needs endpoint enforcement or a commissioned topology that accounts for every other server, automation and manual operator. A native security identity or Short Server ID alone cannot serve as a monotonic fence. [Core §8 and Appendix E.3](https://www.openmobilealliance.org/release/LightweightM2M/V1_2_2-20240613-A/HTML-Version/OMA-TS-LightweightM2M_Core-V1_2_2-20240613-A.html).

Bootstrap can create or replace configuration outside ordinary management ACL checks. Bootstrap-Pack replacement is scoped to included objects with specified exceptions; it is not a general snapshot rollback. Failed bootstrap retention of a prior bootstrap account does not guarantee restoration of all credentials, configuration or physical effects. Unbootstrapping removes associated observations and access; shared objects can survive, and an ACL owner can be reassigned according to native rules, including an arbitrary choice between equal candidates. This is an administrative transition that needs HMS reconciliation, not proof of an orderly physical-control handover. [Core §6.1; Transport §5.2.5](https://www.openmobilealliance.org/release/LightweightM2M/V1_2_2-20240613-A/HTML-Version/OMA-TS-LightweightM2M_Transport-V1_2_2-20240613-A.html).

Security/OSCORE/COSE Objects 0, 21 and 23 are excluded from ordinary management and reporting access. Do not generalize that rule to every credential-bearing object: MQTT Object 24 includes writable credentials under its own native permissions. Keep all such material outside agent-visible inventories and logs. Bootstrap, credential rotation, ACL edits, clock setting, reboot/reset and firmware writes require distinct maintenance capabilities, with outstanding operations reconciled around each change.

Transport §5 requires authentication, confidentiality, integrity, replay protection, request/response binding and freshness capabilities, with alternative security required for NoSec deployments. Endpoint Client Name must be checked against authenticated identity or an authorized mapping. Credential replacement does not automatically terminate existing TLS/DTLS associations, so revocation needs an explicit policy for existing sessions as well as stored credentials. Expired or revoked bootstrap credentials can require out-of-band recovery. The document's cipher/version requirements describe its baseline, not a fresh security recommendation for every current deployment.

Replay protection also does not eliminate late, previously unseen requests. Transport §5.6 specifically discusses freshness to prevent stale operations from overwriting newer state. §5.5 recommends Request-Tag for blockwise request separation, including some DTLS/OSCORE replay-window configurations. HMS must still enforce its own immutable start/cutoff rules and reject stale authority at execution. OSCORE provisioning also trusts the party that knows the master secret; this is distinct from endpoint-exclusive identity. Restart persistence of security context, application receipt and physical fencing each needs separate qualification. [Transport §§5.1–5.6](https://www.openmobilealliance.org/release/LightweightM2M/V1_2_2-20240613-A/HTML-Version/OMA-TS-LightweightM2M_Transport-V1_2_2-20240613-A.html).

## Firmware: cancellation ends before installation

Core Appendix E.6 defines Firmware Update Object 5 version 1.2, with State and Update Result serving different purposes. Package URI writes can initiate downloads; completed package transfer establishes Downloaded, not installed readiness. Update is executable only from Downloaded. Optional Cancel (`/5/0/10`) is available before installation, with a canceled result, but must be rejected once installation has started or finished. Resetting package state does not undo installed firmware. [Core Appendix E.6, especially the state diagram on PDF page 126](https://www.openmobilealliance.org/release/LightweightM2M/V1_2_2-20240613-A/OMA-TS-LightweightM2M_Core-V1_2_2-20240613-A.pdf).

Automatic upgrade can install after downloading without a separate Update command. Deferral can retain Downloaded and later begin installation automatically when its interval expires. Admission must therefore cover the actual future installation boundary, and the endpoint must enforce any promised authority/interlock condition there. A host cannot revoke that behavior by forgetting its operation or losing the connection. A successful URI Write can also precede a later invalid-URI or transfer error; retain the subsequent result before another attempt resets it.

After installation, require the applicable native result plus authenticated version/artifact evidence and renewed capability commissioning. Idle alone is ambiguous: cancellation and reset also lead there. Firmware can remove supported objects or change behavior. Image signature verification, repository trust, hardware compatibility, storage layout and installed-version rollback are outside the Core's firmware mechanism. The HMS binding must declare them separately and must never infer image authenticity from successful TLS transfer.

## Encodings and bounded endpoint resources

Content-format support depends on role, release and operation. Plain text, opaque and CoRE Link Format have baseline roles; SenML JSON/CBOR, LwM2M CBOR, legacy TLV/JSON and composite-operation formats have different requirements. In particular, current clients must not select the obsolete LwM2M JSON format merely because a server still implements it. Pin the negotiated format for each adapter operation; an encoder that handles one CBOR form is not automatically a complete LwM2M implementation. [Core §7.5](https://www.openmobilealliance.org/release/LightweightM2M/V1_2_2-20240613-A/HTML-Version/OMA-TS-LightweightM2M_Core-V1_2_2-20240613-A.html).

HMS parsing must retain signed/unsigned 64-bit values without JSON-number rounding and apply explicit units, ranges, frames and finite-value rules. Object/resource identifiers generally reserve the all-ones value, while particular formats define sentinel uses. TLV supports large payload lengths, and CBOR permits representations that require careful bounded decoding; neither the specification nor successful XML schema validation proves suitability for a small MCU. Commission maximum message bytes, nesting, records, object instances, string/binary lengths, block assembly, historical queue entries and time spent parsing.

The two separately read XSDs describe structural XML fields and enumerations. Version 1.1 adds types including Unsigned Integer and Core Link relative to the older schema. Fields such as ranges and units are strings, resource items can repeat without a tight equipment bound, and schema validation does not establish unique semantic IDs, reserved-ID rules, Execute argument semantics or safe physical limits. Validate the installed object contract separately. This research does not report measured RAM, flash, latency, throughput or watchdog behavior.

## Version differences and publication conflicts

The earlier document's complete baseline was Core 1.2 (2020); its 1.2.2 reading was selected only and Transport was unread. This review closes the current published Core/Transport reading gap, including their appendices and semantic figures. It does not perform a complete line-by-line comparison of the old and new baselines. The authors' current change lists identify 1.2.1 corrections to Execute argument uniqueness, bootstrap/discovery and COSE visibility, attributes, object encoding/examples and CoAP registration/security-context behavior. The 1.2.2 release definition lists reference/link fixes, object-versioning and Object 27 corrections, UDP and CoAP-result clarification, LoRaWAN diagrams and MQTT test updates. [Core §1.2](https://www.openmobilealliance.org/release/LightweightM2M/V1_2_2-20240613-A/HTML-Version/OMA-TS-LightweightM2M_Core-V1_2_2-20240613-A.html), [Transport §1.2](https://www.openmobilealliance.org/release/LightweightM2M/V1_2_2-20240613-A/HTML-Version/OMA-TS-LightweightM2M_Transport-V1_2_2-20240613-A.html), [release definition §3.5](https://www.openmobilealliance.org/release/LightweightM2M/V1_2_2-20240613-A/HTML-Version/OMA-ERELD-LightweightM2M-V1_2_2-20240613-A.html).
