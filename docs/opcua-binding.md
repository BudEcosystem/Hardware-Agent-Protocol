# OPC UA binding: industrial commands and observation recovery

OPC UA supplies typed server operations, authenticated Sessions, monitored data and notification recovery. HMS must still establish who may control the physical resource, which execution an observation belongs to, and what evidence demonstrates completion or a stopped plant. A recovered Session or Subscription does not answer those questions. This is a proposed adapter design informed by the references below; no industrial adapter, PLC integration, endpoint experiment or conformance claim is included.

## Service success and physical evidence

Part 4 has two result levels: the service response and individual operations. A successful service envelope can contain unsuccessful individual results. HMS therefore retains the service status, each operation status and valid typed outputs before deriving its own result. It cannot collapse them into one Boolean. [Part 4 §5.3](https://reference.opcfoundation.org/specs/OPC-10000-4/5.3).

| OPC UA result | What it supports | What HMS must still establish |
|---|---|---|
| Successful Write | The server's specified write result for that Attribute | Meaning of the target, independent feedback and physical outcome |
| `Good_CompletesAsynchronously` on Write | Intermediate system accepted the write | Whether the underlying data source was updated |
| Successful Call operation | The specified Method completed successfully | Whether that Method completes the physical job or merely starts/manages it |
| Program state transition | A transition of the modeled Program | Correct invocation/run, subtype meaning and physical completion predicate |
| Good DataValue | Server-reported usable value | Provenance, freshness, measurement versus command echo and applicability to this operation |
| Subscription keep-alive | Subscription remains active | Device health, plant quiescence or completion |

These distinctions follow the separate [Write](https://reference.opcfoundation.org/specs/OPC-10000-4/5.11.4), [Call](https://reference.opcfoundation.org/specs/OPC-10000-4/5.12.2), [DataValue](https://reference.opcfoundation.org/specs/OPC-10000-4/7.11) and [Subscription](https://reference.opcfoundation.org/specs/OPC-10000-4/5.14.1) contracts.

A Method returns after its own execution finishes; the adapter should preserve that stronger statement. Its configured semantic contract determines whether that execution is the plant job itself or, for example, the `Start` transition of a longer-lived Program. If a Session terminates, Method results are discarded independently of the task actually performed at the server. Thus a timeout or lost response is an uncertainty boundary, not proof that nothing happened. [Part 4 §§5.12.1–5.12.2](https://reference.opcfoundation.org/specs/OPC-10000-4/5.12).

Write and Call operation arrays have undefined execution order. A Write can partially succeed; the specification places rollback responsibility on the client. Separate calls can impose request order but do not make multiple effects atomic. A compensating write is a new physical action that can fail or cause further changes. HMS should admit only installed, bounded actions with explicit compensation limits; it should not promise automatic restoration of material, heat, motion or consumed samples. [Part 4 §5.11.4](https://reference.opcfoundation.org/specs/OPC-10000-4/5.11.4), [§5.12.2](https://reference.opcfoundation.org/specs/OPC-10000-4/5.12.2).

## Request identity, cancellation and stopping

`requestHandle` correlates a response and selects outstanding requests for Cancel. Multiple requests can share it; Cancel covers all outstanding matches. `cancelCount` counts canceled requests. Neither field is specified as a durable, intent-bound execution receipt or controller fencing token. `auditEntryId` supports cross-log correlation. The request timestamp is diagnostic/logging data, and `timeoutHint` is only a server hint except where the Publish rules explicitly require its check. An HMS start deadline must therefore be enforced by an admitted controller primitive or an appropriately constrained gateway, rather than inferred from these header fields. [Part 4 §7.32](https://reference.opcfoundation.org/specs/OPC-10000-4/7.32), [§5.7.5](https://reference.opcfoundation.org/specs/OPC-10000-4/5.7.5).

Cancel operates on outstanding service requests. CloseSession stops accepting that Session's requests and returns `Bad_SessionClosed` for outstanding requests. Combined with the Call result-loss rule, these contracts do not establish rollback of completed effects or verified physical quiescence. HMS should distinguish cancel requested, service request canceled, a device-specific Halt accepted, and independently observed stopped state. A transport disconnect, Session close or Subscription deletion must not be used as the implementation of physical stop. [Part 4 §§5.7.4–5.7.5](https://reference.opcfoundation.org/specs/OPC-10000-4/5.7.4), [§5.12.2](https://reference.opcfoundation.org/specs/OPC-10000-4/5.12.2).

For effects without a native idempotency record, a gateway journal may prevent its own automatic duplicate dispatch while that journal and owner remain authoritative. It cannot atomically couple an arbitrary remote Write/Call with its journal. A crash after remote delivery but before recording a response remains unconfirmed. Reconciliation must read a trustworthy controller execution record or report unresolved outcome; repeating the Method with the same `requestHandle` is not a recovery mechanism established by these sources.

## Sessions and security versus control ownership

SecureChannel protects messages according to the negotiated security policy; a policy can disable security. A Session associates application/user identity with service access. Re-activation on a new SecureChannel checks the relevant application certificate, user identity, security mode and policy, then rejects requests on the old channel. This is useful channel replacement, but it does not establish a resource-wide fence against other Sessions, local HMI operation, PLC logic or previously accepted work. [Part 4 §5.6](https://reference.opcfoundation.org/specs/OPC-10000-4/5.6), [§5.7.3](https://reference.opcfoundation.org/specs/OPC-10000-4/5.7.3).

TransferSubscriptions moves a Subscription and MonitoredItems to another Session after its identity/profile checks. The old Session receives `Good_SubscriptionTransferred`. This transfers observation ownership; it does not revoke another actor's authority to command the plant. Its anonymous-user conditions also differ from ActivateSession: transfer allows matching ApplicationUri with SIGN or SIGNANDENCRYPT, while ActivateSession explicitly rejects anonymous re-activation on a new channel using Sign. A deployment should use the specific operation's rules rather than a generic “same client” shortcut. [Part 4 §5.14.7](https://reference.opcfoundation.org/specs/OPC-10000-4/5.14.7), [§5.7.3](https://reference.opcfoundation.org/specs/OPC-10000-4/5.7.3).

The HMS proposal is to retain separate identities for the authenticated principal, endpoint Session, admitted controller instance, physical resource owner and execution incarnation. Installed controller primitives should validate the current owner/fence and bounded arguments before committing effects. Where a controller lacks these facilities, the deployment must describe the gateway's exclusive control boundary and remaining bypass paths. Authentication alone cannot justify a stronger guarantee. Gateway credential mapping must also preserve meaningful user authorization: Part 4 expressly requires user security to survive server chaining. [Part 4 §5.6.1](https://reference.opcfoundation.org/specs/OPC-10000-4/5.6.1).

This research does not select a production cryptographic profile or validate a trust store. Parts 2, 6, 7 and applicable role/user-management rules require separate review. No OPC endpoint was contacted for testing.

## Reconnect and observation recovery

The specified recovery sequence first creates a new SecureChannel and re-activates the existing Session. Only if activation fails does the client create a new Session and attempt Subscription transfer; failed transfer requires new Subscriptions. The client then Republish-es from the next expected sequence number until `Bad_MessageNotAvailable`, before normal Publish handling. It must avoid overwriting newer values with older recovered notifications. Figure 36 illustrates this flow and expressly does not cover every error scenario. [Part 4 §6.7](https://reference.opcfoundation.org/specs/OPC-10000-4/6.7).

HMS should persist the observation cursor separately from effect receipts. Notification sequence numbers are per Subscription, wrap to 1, and are not operation identifiers. Acknowledgment permits server deletion from its retransmission queue; queue overflow can discard unacknowledged messages, and some profiles make retransmission support optional. The adapter must retain the actual negotiated support and bounds. Recovery of notification delivery must never itself enqueue an unresolved Write/Call again. [Part 4 §5.14.1](https://reference.opcfoundation.org/specs/OPC-10000-4/5.14.1), [§5.14.5](https://reference.opcfoundation.org/specs/OPC-10000-4/5.14.5).

There are at least three distinct information-loss boundaries: changes missed before server sampling, discarded MonitoredItem entries, and unavailable sent NotificationMessages. Republish only addresses the third. A one-entry MonitoredItem queue retains the latest notification without the larger-queue Overflow flag. For larger queues, overflow flags and event overflow indications expose lost observations. A lack of such flags is therefore insufficient to prove an uninterrupted transition history. [Part 4 §5.13.1](https://reference.opcfoundation.org/specs/OPC-10000-4/5.13.1), [§7.25](https://reference.opcfoundation.org/specs/OPC-10000-4/7.25).

Read or ResendData can restore a current cache after a notification gap, but cannot reconstruct every intervening transition. Transfer with `sendInitialValues=true` and ResendData may return an already queued or last-sent value. They are not promises of a fresh physical sample. A Program completion event lost during a gap needs a retained, invocation-bound result or a separate reconciliation path. [Part 4 §6.7](https://reference.opcfoundation.org/specs/OPC-10000-4/6.7), [§5.14.7](https://reference.opcfoundation.org/specs/OPC-10000-4/5.14.7).

Durable Subscriptions are an optional facility requiring a specific Method, larger queues, saved settings and transfer support. Part 4 still acknowledges possible loss on ungraceful shutdown or power failure. Their durability concerns observations, not persistence or exactly-once execution of Method effects. Offline behavior of the industrial process remains a controller/deployment contract. [Part 4 §6.8](https://reference.opcfoundation.org/specs/OPC-10000-4/6.8).

ContinuationPoints are result-pagination state for Browse, Query and HistoryRead. They expire on Session closure and can be reclaimed by the server. They do not resume physical work and should never become an HMS action continuation token. [Part 4 §7.9](https://reference.opcfoundation.org/specs/OPC-10000-4/7.9).

## State freshness and metadata changes

Read `maxAge=0` asks the server to attempt a fresh data-source read; it still permits best effort. `maxAge` is based on server timestamp rather than proof of a new physical conversion. Sampling can be slower at the underlying system, and its update cycle can be unsynchronized with UA sampling. Admission and verification therefore need explicit age bounds, quality handling, source meaning and uncertainty behavior. [Part 4 §5.11.2](https://reference.opcfoundation.org/specs/OPC-10000-4/5.11.2), [§5.13.1.2](https://reference.opcfoundation.org/specs/OPC-10000-4/5.13.1.2).

A source timestamp travels unchanged through UA aggregation, while a server timestamp describes when that server received the value or knew it accurate. A server may advance its timestamp without a new source change. Good quality alone is also limited: a server without status information is permitted to report Good. HMS should retain both timestamps, status/substatus, arrival time, source identity and the configured distinction between requested setpoint, controller estimate and independent measurement. Clock relationships require deployment evidence; the presence of UTC fields does not establish clock synchronization. [Part 4 §7.11](https://reference.opcfoundation.org/specs/OPC-10000-4/7.11).

`StructureChanged` and `SemanticsChanged` require metadata refresh before using affected data; engineering units are an explicit example. HMS should invalidate a stale binding/calibration assumption, revalidate its admitted primitive metadata, and avoid silently applying the old interpretation. The exact data-access metadata contract requires Part 8 and the chosen information model, which were not read here. [Part 4 §7.38.1](https://reference.opcfoundation.org/specs/OPC-10000-4/7.38.1).

## Programs as controller-owned workflows

Part 10 is useful for complex operations because it separates control Methods, state transitions, Events and result data. A server need expose only the applicable control Methods; Suspend/Resume is not universal. `Executable` describes current applicability, so observing it does not reserve a future transition. Internal completion/errors can also move the state machine. HMS must bind a specific installed Program subtype and resource configuration rather than treating all Program nodes as interchangeable capabilities. [Part 10 §§4.2.6–4.2.8](https://reference.opcfoundation.org/specs/OPC-10000-10/4.2.6), [§5.2.4](https://reference.opcfoundation.org/specs/OPC-10000-10/5.2.4).

Halted can be initial, completed or failed. A subordinate state or result distinguishes those meanings. Intermediate results may be transient; terminal results last until rerun or deletion, and AutoDelete can remove the instance and associated results. HMS should capture an execution incarnation and final evidence before restart/reset/delete can replace it. Program node identity alone is insufficient when it can be recycled. RecycleCount and diagnostics are useful context, not a specified persistent HMS idempotency receipt. [Part 10 §5.2.3.2](https://reference.opcfoundation.org/specs/OPC-10000-10/5.2.3.2), [§4.2.9](https://reference.opcfoundation.org/specs/OPC-10000-10/4.2.9), [§5.2.2](https://reference.opcfoundation.org/specs/OPC-10000-10/5.2.2).

ProgramDiagnostic2 records creation Session, recent Method identity, arguments, values and return status. These describe history; they are not a lock excluding other users. Audit Events likewise support accountability without proving exclusive ownership or complete durable history. The adapter must resolve the actual controller's allowed actors, interlocks and stop behavior. [Part 10 §5.2.8](https://reference.opcfoundation.org/specs/OPC-10000-10/5.2.8), [§4.2.2](https://reference.opcfoundation.org/specs/OPC-10000-10/4.2.2).

Annex A's DomainDownload illustrates a separate invocation per download, substates and distinct completed/aborted results. It is informative, handles a transfer workflow, and does not validate a robot or process safety controller. Its literal transition numbering also contains inconsistencies in the available text/figures. It supplies a modeling example, not executable adapter logic. [Part 10 Annex A](https://reference.opcfoundation.org/specs/OPC-10000-10/A).

## Source discrepancies and next implementation evidence

The retained Part 10 export has material inconsistencies: Table 7 reverses FromState/ToState for RunningToSuspended relative to the other tables and prose; Table 5/property prose disagree over signedness and negative unlimited counts; some Annex A transitions and figure labels use inconsistent numbers. Missing figures compound the gap. The corpus preserves these bytes rather than silently correcting them. Before implementing that model, compare the authoritative publication and the actual versioned model used by the server; no automatic resolution is justified by this reading.

An implementation acceptance package should establish, with a specific controller: native intent deduplication or its absence; authority/fence enforcement against concurrent actors; the effects of disconnect and process restart; response-loss reconciliation; bounded stop with measured terminal evidence; queue/republish loss handling; metadata/unit changes; result retention across Program recycling; and partial failure of compound actions. These are proposed HMS tests, **not tests performed in this research**. The existing synthetic plant's atomic state-and-receipt guarantee cannot be transferred to an arbitrary OPC UA server.
