# WoT Architecture 1.1 and the HMS boundary

The current approved baseline verified on 6 November 2026 is **Web of Things Architecture 1.1, W3C Recommendation, 5 December 2023**. The versioned publication and both current aliases returned identical archived bytes. The official publication history lists no later Recommendation. The editor source still identifies itself as Architecture 1.1 with `specStatus: "ED"`; its configuration even retains a 2022 previous-publication date. It is a separately retained, selected-read editor source, not evidence of a newer approved architecture. The errata page lists zero recorded errata and a last-update date of 3 October 2023; that is a snapshot of the page, not a claim that all open issues were reviewed. Architecture 1.1 is a conceptual framework with some normative requirements, not an implementation of device execution. Section 2 marks diagrams, examples, notes and authoring guidelines non-normative; §6 is normative, whereas the building-block overview in §7 and implementation/deployment examples in §§8–9 are non-normative. Security and privacy include normative mitigations. Appendix A explicitly records that the building-block overview became informative and that some insufficiently implemented at-risk assertions were removed or made informative. A figure or example therefore cannot establish an HMS conformance obligation by itself. [Conformance](https://www.w3.org/TR/2023/REC-wot-architecture11-20231205/#conformance), [changes](https://www.w3.org/TR/2023/REC-wot-architecture11-20231205/#changes).

| Architecture boundary | HMS interpretation and work still required |
|---|---|
| A Thing is an abstraction of a physical or virtual entity; at least one TD must exist, but hosting may be on the device, gateway or cloud (§6.1). | A host-served TD can describe a constrained endpoint through an adapter. This does not make the endpoint parser itself a WoT Consumer or prove the serial protocol is an eligible direct WoT binding. Record which interface the TD actually describes. |
| A Thing Model describes a class; a TD describes an instance (§6.1.1). | Use reusable models for primitive families, then resolve instance identity, binding, security and installed limits. A model alone supplies neither a contactable instance nor authority to operate it. Context and Thing Model schema compatibility remain separate unfinished work. |
| A Thing has behavior, affordances, security configuration and protocol bindings (§6.3). | Keep physical behavior and controller invariants distinct from descriptive metadata. A valid description cannot demonstrate installed firmware behavior, calibration, stop bounds or acquired-state freshness. |
| Properties expose state; Actions may start processes or change physical state over time; Events report transitions (§6.5). | An invocation response needs an HMS-defined interpretation. The architecture does not supply a durable operation receipt, a completion proof, exactly-once actuation, an abort bound or physical rollback. Observation events need provenance and acquisition semantics. |
| Intermediaries may translate, cache, augment or compose Things (§6.10.2; §9.2.2). | Preserve original device, adapter and operation identities. Distinguish measured state, cached state and simulated predictions. Aggregate operations need explicit partial-outcome and recovery handling. |

These are HMS design inferences, not new claims about what W3C mandates. The architecture supports native C/C++ and other APIs, optional scripting, external descriptions of existing devices and internal hardware abstractions. That fits a host runtime plus constrained controller without putting a scripting engine on the microcontroller. Its device-category table is approximate and explicitly allows overlapping categories; it is not a flash, RAM or secure-transport qualification for ATmega328P. Existing HMS target evidence must continue to stand on its own. [Fundamental concepts](https://www.w3.org/TR/2023/REC-wot-architecture11-20231205/#sec-architecture-overview), [native and existing implementations](https://www.w3.org/TR/2023/REC-wot-architecture11-20231205/#alt-servient-impl).

The binding obligations are more concrete than a protocol name. Section 6.7 requires each interaction affordance to include one or more bindings serialized as hypermedia controls. Forms identify the operation, target and protocol method; content needs a media type, and structured data should have a schema. URI schemes alone cannot capture subprotocols or platform-specific options. The binding-template overview distinguishes protocol, payload and platform concerns, and says the Consumer must actually implement the required stack and encoders. Binding Templates are informative guidance; serializing a URL or choosing JSON does not implement them. For HMS, a reviewable binding needs exact operation/status/cancellation behavior, security selection, limits, errors and unsupported-feature handling. Full Binding Templates and individual candidate protocol templates are still separate reading and conformance work. [Forms](https://www.w3.org/TR/2023/REC-wot-architecture11-20231205/#sec-hypermedia-forms), [bindings](https://www.w3.org/TR/2023/REC-wot-architecture11-20231205/#sec-protocol-bindings), [template overview](https://www.w3.org/TR/2023/REC-wot-architecture11-20231205/#sec-binding-templates).

The metadata authority in §6.7.1 means an entity with full, current knowledge can produce the hypermedia controls. It does **not** mean a directory registrant owns the actuator. Cached controls are permitted for offline processing when freshness metadata exists. Discovery separates introduction from authenticated and authorized exploration; a directory distributes TDs and changes, and an external agent can register a brownfield device. HMS should keep registry provenance, description digest, freshness/expiry, endpoint enrollment, authenticated principal and operation authority separate. A stale TD must not authorize a newly rebound device merely because the same identifier or URL resolves. An untrusted description is data to validate, not instructions to install software, fetch arbitrary links or disclose credentials. This last rule is an HMS inference about its agent-facing use. [Hypermedia authority and caching](https://www.w3.org/TR/2023/REC-wot-architecture11-20231205/#hypermedia-driven), [discovery overview](https://www.w3.org/TR/2023/REC-wot-architecture11-20231205/#sec-discovery).

The digital-twin example explicitly permits cached property replies and commands queued while the physical Thing sleeps. Consequently, HTTP success at a twin or an accepted queue entry cannot establish physical completion. For HMS, deferred dispatch needs immutable intent identity, a start deadline, current controller context and fencing checked at the final controller; reconnecting or refreshing a TD must not renew an expired command. A directory change event also cannot substitute for an actuator receipt. Architecture 1.1 does not specify the replay, cancellation, transfer-of-control or reconnect state machine needed to make those guarantees. Nor does its orchestration example give transactional rollback across devices. [Twin example](https://www.w3.org/TR/2023/REC-wot-architecture11-20231205/#sec-deployment-digital-twin), [orchestration](https://www.w3.org/TR/2023/REC-wot-architecture11-20231205/#orchestration).

Lifecycle figures distinguish bootstrapping, onboarding, activation, use, offboarding and decommissioning. The prose additionally discusses ownership, trust roots, access control, service provisioning, updates, re-bootstrapping, factory reset and destruction. These are useful requirements prompts, not a wire protocol or a complete management service. HMS should treat enrollment and ownership changes, driver/firmware replacement, credentials, calibration and physical-contract changes as privileged lifecycle operations. Ordinary prepare/invoke authority should not silently authorize them. After an ownership change or reset, queued work and old controller/session assumptions need explicit invalidation and evidence reconciliation. Offboarding metadata alone does not prove a motor stopped, a credential was erased or a device was destroyed. [Lifecycle](https://www.w3.org/TR/2023/REC-wot-architecture11-20231205/#lifecycle).

Security configuration is distinct from the published description: TD producers must exclude private security data, including misuse of free-text fields. The runtime recommendations include tenant isolation, protected credential storage, restricted application interfaces and secure provisioning/update. Section 10.2.2 directly addresses physical damage from compromised scripts: mediate low-level access through a hardware abstraction and use layered software and hardware safety controls. HMS therefore needs enforcement beneath the planning agent and beneath a replaceable host adapter. A shared transport credential or one host UID is not proof of separate authority for each agent, user or automation; those boundaries need their own enforcement and tests. [Security risks and mitigations](https://www.w3.org/TR/2023/REC-wot-architecture11-20231205/#sec-security-considerations).

The Recommendation describes historically common trusted-network setups, including WEP and browser certificate assumptions; those descriptions are not a suitable current deployment prescription. Its normative transport requirements distinguish public networks, private networks and descriptive treatment of insecure brownfield devices. A gateway can secure the public hop while the device-side hop remains weak; HMS must state that boundary and prevent alternate control paths from defeating ownership assumptions. Authentication, confidentiality and replay protection on a connection also do not prove the physical stop behavior of its endpoint. Privacy guidance matters to the registry and evidence store: identifiers, device types and location can reveal personal information even without explicit personal fields. Accessibility applies across owner, installer and user interfaces, including onboarding and physical controls; an API alone does not resolve it. [Trust and transport](https://www.w3.org/TR/2023/REC-wot-architecture11-20231205/#sec-security-consideration-trusted-environment-risks), [privacy](https://www.w3.org/TR/2023/REC-wot-architecture11-20231205/#sec-privacy-considerations), [accessibility](https://www.w3.org/TR/2023/REC-wot-architecture11-20231205/#sec-accessibility-considerations).

This reading strengthens the existing choice of TD as an external description layer plus a separate HMS execution contract. It does not yet establish a conforming HMS WoT profile. Remaining work includes complete context/Thing Model schema review, exact protocol/template choices, required extension semantics, concrete discovery distribution policy and conformance tests. The linked Security and Privacy Guidelines, Scripting API, Profile, use-case document and bibliography were not fully read in this lane. No newer editor-draft architecture behavior was adopted.
