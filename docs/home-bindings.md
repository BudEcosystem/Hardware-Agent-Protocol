# Home Assistant and ESPHome bindings

Status: primary-source research and proposed HMS binding requirements, 2026-11-06. No home account or device was contacted, and no acquired program was executed. This review supports an adapter design; it does not establish implementation conformance, physical feedback, cryptographic assurance or measured timing.

The retained corpus contains **32 complete source files/texts**, **three partially read implementation files**, and **three additional published renditions acquired for provenance but not independently read**. Complete means the identified file or extracted text, not its repository, linked references, embedded images or generated MDX components. [The corpus README](../research/home/README.md), [acquisition manifest](../research/home/manifest.jsonl), [repository pins](../research/home/repos.json) and [exact LF reading receipts](../research/home/reading-home-full.json) separate these scopes. Home Assistant Core is pinned at **2026.11.0**, ESPHome firmware at **2026.10.2**; documentation and the JavaScript client have their own commit pins. Live developer WebSocket/REST URLs now redirect to the contributors site.

## Binding decision

Use Home Assistant as an existing integration, discovery and automation hub when it already owns the installation. Use ESPHome's native API when a commissioned device needs a direct local binding. Both fit a typed HMS description, but their ordinary operations provide weaker recovery, authority and physical-evidence semantics than [the proposed HMS execution contract](../spec/02-execution.md). The host must advertise those limits instead of silently inventing stronger guarantees.

| Concern | Home Assistant | ESPHome native API | HMS decision |
| --- | --- | --- | --- |
| Description | Entities, registries, domains, service/action descriptions and supported features | Device information, entity lists, per-domain traits and user-action argument types | Pin an installation binding and the particular integration/component's meaning; a domain name alone is insufficient |
| Observation | State-machine records and event subscriptions | State messages keyed by entity/device; metadata includes some assumed/missing-state flags | Retain provenance and distinguish sensor report, software state, estimate and command echo |
| Invocation | REST service endpoint or WebSocket `call_service` | Per-domain command messages; optional user-defined action responses | Journal HMS intent separately; record native dispatch evidence without assuming a physical result |
| Correlation | Increasing command ID per connection; call context | Message type IDs; optional action `call_id` | Native identifiers are not durable HMS operation keys |
| Recovery | New connection, new subscriptions, current snapshot | Reconnect, renegotiate capabilities, enumerate and subscribe again | Mark a stream gap and reconcile possible prior effects before conflicting work |
| Authority | User permissions and context | Configured Noise key; several API clients can connect | Commission one authority path for each physical resource, including manual and local automation paths |

The interface facts come from the full [WebSocket documentation](https://contributors.home-assistant.io/core/internals/websocket-api/), [REST documentation](https://contributors.home-assistant.io/core/internals/rest-api/) and [native API schema](https://github.com/esphome/esphome/blob/9a78022ded2285861f10de50168a0aa71e2a4322/esphome/components/api/api.proto). The HMS column is design analysis.

## State is not necessarily physical feedback

A Home Assistant state object contains a string state, attributes, context and timestamps. `last_changed`, `last_updated` and `last_reported` describe changes or writes in its state machine. They do not, by themselves, identify when a physical sensor acquired a sample. A repeated device value may not even cause a new state write. `unknown` and `unavailable` have different meanings, and neither means zero, off or safe. [State object](https://www.home-assistant.io/docs/configuration/state_object/), [state-machine internals](https://contributors.home-assistant.io/core/internals/states/).

The current integration guidance explicitly permits optimistic updates after commands, and restoration of assumed state where equipment cannot report its condition. A state write can reuse cached integration data; requesting a refresh can be debounced. Availability describes the integration's ability to provide state, not measured actuator readiness. The absence of `assumed_state` is therefore insufficient proof of physical measurement: HMS needs the commissioned component's feedback model and its acquisition/cache bounds. [Updating state](https://contributors.home-assistant.io/core/entities/state-updates/), [fetching data](https://contributors.home-assistant.io/core/integrations/fetching-data/), [state attributes](https://contributors.home-assistant.io/core/entities/state-attributes/).

The REST state-write endpoint changes Home Assistant's state machine without commanding the device. HMS must not implement physical `set` operations through `POST /api/states/<entity_id>`. The retained REST implementation confirms that this endpoint calls `hass.states.async_set`, whereas the service endpoint calls the service registry. [Pinned REST implementation](https://github.com/home-assistant/core/blob/74cf5a49c63ed8d4d87717844bf14f79c28c9cea/homeassistant/components/api/__init__.py).

ESPHome gives concrete counterexamples to equating reported state with measured effect. A template switch can publish its requested state immediately, and setup may call control with a restored state. A time-based cover derives position from elapsed time; its initial value can be restored or default to the midpoint. With configured built-in endstops, it can mark its operation idle without calling the stop action. That is an implementation estimate and a reliance on the installed mechanism, not an encoder observation. [Template switch source](https://github.com/esphome/esphome/blob/9a78022ded2285861f10de50168a0aa71e2a4322/esphome/components/template/switch/template_switch.cpp), [time-based cover source](https://github.com/esphome/esphome/blob/9a78022ded2285861f10de50168a0aa71e2a4322/esphome/components/time_based/cover/time_based_cover.cpp).

For HMS, retain the native entity state and timestamps as evidence, add monotonic receipt time, and declare acquisition age unknown unless the installed integration supplies a defensible bound. Preserve the distinction between firmware-reported validity and host reachability. A sensor's configured decimals or display precision is not a calibration uncertainty. An adapter-generated sequence describes the adapter's received stream, not unseen endpoint samples.

## Snapshot, subscriptions and reconnect

Home Assistant's `subscribe_entities` is stronger than an arbitrary separate read followed by a watch. The pinned handler collects allowed states and registers its listener in one callback with no intervening await, then sends the initial compressed snapshot and later diffs. This avoids an event-loop handoff race. It does not make sensors simultaneous, provide an endpoint acquisition timestamp, or add a durable replay cursor. The same implementation can omit states that fail JSON serialization, so a missing required entity must remain a failed precondition. [Selected server commands, lines 403–582](https://github.com/home-assistant/core/blob/74cf5a49c63ed8d4d87717844bf14f79c28c9cea/homeassistant/components/websocket_api/commands.py#L403).

The official JavaScript client resets command numbering on disconnect, rejects ordinary in-flight requests, and resubscribes recoverable subscriptions. Its state collection replaces the old map with the first new snapshot after reconnect. A still-present cached object while offline is not fresh state. A rejected promise cannot establish that an earlier service call had no effect. [Connection implementation](https://github.com/home-assistant/home-assistant-js-websocket/blob/ad8031f63b996cccb9dc53633325c2039b030aee/lib/connection.ts), [state collection](https://github.com/home-assistant/home-assistant-js-websocket/blob/ad8031f63b996cccb9dc53633325c2039b030aee/lib/states.ts), [collection lifecycle](https://github.com/home-assistant/home-assistant-js-websocket/blob/ad8031f63b996cccb9dc53633325c2039b030aee/lib/collection.ts).

ESPHome's state subscription starts an initial-state iterator, which can wait behind entity enumeration. The ordinary state schema has no common source timestamp, boot epoch, replay cursor or operation ID. A reconnect therefore restores current reported state, not the missing transition history. The header's deferred queue deduplicates pending state messages by entity and message type, while events are excepted. The send path can later encode the entity's then-current state, so intermediate state transitions can disappear through batching. `batch_delay: 0ms` requests immediate sending, but the implementation can fall back to queued sending when it cannot write. [Selected connection header](https://github.com/esphome/esphome/blob/9a78022ded2285861f10de50168a0aa71e2a4322/esphome/components/api/api_connection.h#L293), [selected state/batch implementation](https://github.com/esphome/esphome/blob/9a78022ded2285861f10de50168a0aa71e2a4322/esphome/components/api/api_connection.cpp#L2449).

HMS should create a new adapter stream epoch on reconnection, report a gap, replace its current-state cache only under a defined resynchronization policy, and invalidate continuity-dependent claims. It must not fabricate a physical reboot merely because the network connection changed. Authorization changes also require cache invalidation or a new authorized snapshot: a server can stop forwarding states that a user may no longer read.

## A result is scoped to the operation actually implemented

A Home Assistant service result means its handler returned under that integration's semantics. The WebSocket result includes context and optional response data. The current REST implementation records changes sharing the call's exact context while its listener is attached; it is not a complete record of all later device changes or descendant automation contexts. The REST service task is explicitly shielded from cancellation when its HTTP connection drops. Treat a lost connection after possible dispatch as `outcome_unknown`, unless separate evidence resolves it. [Pinned REST call handler](https://github.com/home-assistant/core/blob/74cf5a49c63ed8d4d87717844bf14f79c28c9cea/homeassistant/components/api/__init__.py#L383), [WebSocket call handler](https://github.com/home-assistant/core/blob/74cf5a49c63ed8d4d87717844bf14f79c28c9cea/homeassistant/components/websocket_api/commands.py#L326).

ESPHome ordinary cover, switch, light and number commands are not generic persistent jobs. Their schema uses message-type IDs, and their handlers dispatch directly into the component. Native TCP success cannot establish component acceptance or physical completion; the frame helper can return `OK` after queuing unsent bytes in an overflow buffer. [Selected component dispatch](https://github.com/esphome/esphome/blob/9a78022ded2285861f10de50168a0aa71e2a4322/esphome/components/api/api_connection.cpp#L549), [complete frame helper](https://github.com/esphome/esphome/blob/9a78022ded2285861f10de50168a0aa71e2a4322/esphome/components/api/api_frame_helper.cpp).

There are meaningful stronger, domain-specific exceptions. User-defined actions can send status or data responses through `api.respond`. Server call tracking maps each new request to an in-memory ID, with default 30-second cleanup and removal on disconnect. It does not compare an immutable request digest, deduplicate retries, or retain a recoverable result. A response is emitted at the configured action step, which need not be the end of the physical process. [User-action implementation](https://github.com/esphome/esphome/blob/9a78022ded2285861f10de50168a0aa71e2a4322/esphome/components/api/user_services.h), [server response routing](https://github.com/esphome/esphome/blob/9a78022ded2285861f10de50168a0aa71e2a4322/esphome/components/api/api_server.cpp#L822).

The complete schema also includes IR/RF transmission completion, serial-proxy ownership, and separate confirmed versus assumed TX-drain status. These should be preserved by a corresponding adapter. Transmitter completion still does not prove a remote appliance acted; UART drain does not prove a downstream instrument completed. The IR completion comment explicitly includes superseded and timed-out transmissions among failures and cautions against blind retry. These exceptions prevent the overly broad claim that ESPHome provides no completion or ownership information anywhere. [Pinned schema, IR and serial sections](https://github.com/esphome/esphome/blob/9a78022ded2285861f10de50168a0aa71e2a4322/esphome/components/api/api.proto#L2806).

## Identity, authority and competing actors

Home Assistant context records can connect users, events and automation parentage. They help explain a state change, but they are not a resource lease or a mechanism that rejects an old controller's command. Connection teardown removes subscriptions; it does not constitute a universal actuator stop. [Event bus](https://contributors.home-assistant.io/core/internals/events/), [connection implementation](https://github.com/home-assistant/core/blob/74cf5a49c63ed8d4d87717844bf14f79c28c9cea/homeassistant/components/websocket_api/connection.py).

ESPHome's configured Noise channel uses `Noise_NNpsk0_25519_ChaChaPoly_SHA256`. Possession of the commissioned secret can authenticate that channel; a name or MAC alone cannot establish exclusive control of a physical installation. The code also supports a well-known all-zero provisioning PSK when no real key is set, explicitly without authentication, and configurations can permit plaintext. A logical `AUTHENTICATED` connection state after hello must therefore not be translated into cryptographic identity without checking the negotiated transport and key provisioning state. [Noise handshake](https://github.com/esphome/esphome/blob/9a78022ded2285861f10de50168a0aa71e2a4322/esphome/components/noise/noise_handshake.cpp), [key/provisioning context](https://github.com/esphome/esphome/blob/9a78022ded2285861f10de50168a0aa71e2a4322/esphome/components/noise/noise.h), [selected hello/authentication code](https://github.com/esphome/esphome/blob/9a78022ded2285861f10de50168a0aa71e2a4322/esphome/components/api/api_connection.cpp#L1870).

Neither ordinary HA service requests nor ordinary ESPHome actuator commands carry the HMS resource fencing generation. Several authorized API clients, HA automations, ESPHome local automations and physical controls can all affect the same equipment. A lock only inside the HMS process does not exclude those paths. The binding must inventory them and either route all effectful paths through the commissioned controller, enforce a local authority/mode policy, or explicitly advertise weaker shared control. Observe manual intervention when possible and advance the HMS control generation; when it is not observable, report that limitation and deny actions requiring exclusive ownership.

## Stopping and offline operation

Unsubscribing ends a stream. Closing TCP ends a connection. Neither is a generic stop operation. `cover.stop` only invokes the installed component's stop behavior. ESPHome `script.stop` prevents subsequent actions, so stopping between relay-on and relay-off can skip the latter. Its `single`, `restart`, `queued` and `parallel` modes define script invocation behavior rather than a whole-installation resource lock. Commission a separate stop procedure with explicit output behavior and feedback, plus local limits/watchdogs appropriate to the equipment. [Script documentation](https://esphome.io/components/script/), [time-based cover documentation](https://esphome.io/components/cover/time_based/).

ESPHome automations execute on the device and can continue without the network. This makes installed finite local skills practical. It also means disconnect does not automatically revoke their physical effects. API/Wi-Fi/MQTT reboot settings can change offline behavior; the API default is documented as 15 minutes, and setup restoration can itself affect outputs. Cloud-dependent HA integrations and ESPHome actions that call back into HA have different dependencies from purely local firmware actions. A connection trigger can run before HA subscribes to device-originated actions, causing an action to be dropped. [Local automation behavior](https://esphome.io/automations/actions/), [native API configuration and action readiness](https://esphome.io/components/api/).

An HMS installation must declare whether a finite procedure continues, stops, holds or enters a recovery state on each lost dependency. Firmware YAML/lambdas and new component code are installation changes; parameterized invocation of an already installed user action is ordinary execution. Nothing here establishes a bounded sandbox for arbitrary generated C++.

## Required implementation and validation

A proposed adapter should retain an immutable binding from HMS capability to native domain/action, target entities/keys, firmware/integration revision, observation interpretation, units and local loss-of-contact behavior. Its journal should record native connection epoch, command ID or call ID where present, HA context where returned, dispatch time, and separate observed evidence. Native retries must not create another physical request under an existing HMS operation key. A missing native result-retention capability remains explicit.

Before conformance, test at least: optimistic state without actuation; unchanged cached state; dropped connection before and after dispatch; HA restart and ESPHome reboot during an action; native response arriving after timeout; lost subscription intervals; batching of rapid transitions; state unavailable or entity removed; overlapping manual/local automation commands; duplicated user-action calls; and stop during delay or saturated output. Measure effect and stop latency with actual feedback, hardware/firmware/load details and uncertainty. Documentation claims about low latency do not replace those measurements.

Remaining work includes the specific HA integration implementations, the selected firmware build and wiring, aioesphomeapi reconnect/timeout behavior, generated dispatch and dependency code, full cryptographic review, and hardware fault injection. Matter core/device/cluster standards are outside this reading claim. No universal native completion, actuator fence, offline guarantee or safety certification follows from this corpus.
