# LwM2M binding proposal

LwM2M is a useful native binding for provisioned, networked devices and gateways. HMS can reuse its typed object model, registration, reporting, access checks and firmware lifecycle while retaining the execution contract in [02-execution](../spec/02-execution.md) and the separate registry records in [03-registry-runtime](../spec/03-registry-runtime.md). This document proposes adapter rules; it does not describe an implemented or certified binding.

The baseline review covers the complete approved Core 1.2 specification dated 2020-11-10: 154 pages, 11,164 LF-delimited extracted lines, all tables and appendices, and all 28 semantic figures. The [reading record](../research/protocols/reading-lwm2m-full.json) pins bytes and coverage; the [review notes](../research/protocols/notes/lwm2m-full-review.md) separate source claims, interpretation and conflicting evidence. OMA also publishes approved 1.2.2 dated 2024-06-13. Its release definition and selected corrective sections were checked and archived; only 334 of its 7,893 extracted Core lines were read, and its companion Transport specification was not read. An implementation must choose and finish reviewing its precise release and transport baseline before claiming conformance. [OMA release definition](https://www.openmobilealliance.org/release/lightweightm2m/V1_2_2-20240613-A/HTML-Version/OMA-ERELD-LightweightM2M-V1_2_2-20240613-A.html)

## Native concepts and HMS records

| Native concept | Proposed HMS representation | Boundary |
|---|---|---|
| Endpoint Client Name and authenticated channel identity | Enrollment evidence and a protocol-specific locator | The name alone is unauthenticated; address, registration location and Short Server ID are not global physical identity. |
| Object ID, version, Object Instance, Resource and Resource Instance paths | Native capability/schema references in a pinned adapter description | A LwM2M Resource is an information/action field. An HMS `Resource` is an exclusivity or physical constraint. Keep separate names and mappings. |
| Register, Update and lifetime | Registration/presence observations | Registration lifetime does not grant a lease, prove continuous reachability or identify an endpoint execution session. |
| Read, Observe, Notify, Send | Typed values plus evidence/provenance and delivery metadata | Receipt does not prove fresh acquisition; missing fields remain missing. |
| Write, Execute, Create, Delete | Mutations admitted through an HMS operation | Classify the actual effect, including writes that start downloads or change control behavior. |
| Access Control Object | Native server authorization evidence | This is per-server/object-instance permission, not HMS actor delegation, physical interlock, fencing or resource ownership. |
| Firmware Update Object 5 | A supervised maintenance operation with native substate and results | Transfer success, installation success, activation and commissioned readiness remain separate evidence. |
| Gateway Objects 25/26 | Explicit gateway-to-downstream-device route | A gateway identity does not authenticate the downstream physical device automatically. |

These mappings follow Core §§3.2, 6–8 and Appendices C–E. The separation of HMS meanings is a proposed binding decision.

## Enrollment, versioning and presence

The adapter must match the endpoint name against the authenticated security identity before enrolling or refreshing a trusted instance. It records the authority that vouched for a gateway or downstream device, the exact route and the commissioned mapping. A changed prefix, replacement device or new security association triggers reconciliation; it must not silently rebind old operations to another physical target. Core §7.3.1 explicitly forbids making decisions from the unauthenticated name alone; Appendix E.12 supplies a downstream Device ID and writable Prefix but does not establish end-device attestation.

Pin the LwM2M enabler release, object versions, object-definition bytes, adapter interpretation and installed capability binding independently. Resolve omitted object versions according to the chosen release rather than treating every missing `ver` as 1.0: core object versions can be inferred from the enabler release. An unfamiliar optional object may register successfully in native LwM2M. That does not authorize HMS to execute its unknown semantics. Imported numeric types, units, ranges, mandatory fields and allowed operations constrain the binding; physical frames, equipment limits, calibration and completion evidence still need a domain profile.

A native Profile ID is a compact reference to an object inventory. It may contain a truncated hash and is not an HMS description digest, signature or immutable intent identifier. A successful registration likewise does not authenticate a description's physical truth. The 1.2.2 clarification additionally includes object versions in dynamically generated Profile ID fingerprints and specifies `ver` placement on object or single-instance links. Keep this parsing versioned. [Core 1.2.2, §§6.2.1 and 7.2.3](https://www.openmobilealliance.org/RELEASE/LightweightM2M/V1_2_2-20240613-A/HTML-Version/OMA-TS-LightweightM2M_Core-V1_2_2-20240613-A.html)

Track registration expiry, authenticated last contact, reachable/unreachable state and HMS authority expiry separately. Native lifetime zero permits an infinite registration; HMS still needs bounded presence evidence and separately enforceable authority. Expiry removes the native registration and observations, not the enrolled asset, operation history or unresolved physical effects. Re-registering requires re-establishing desired observations. Conversely, native observation state can survive reboot, so a continuous registration/observation cannot substitute for the HMS endpoint session identity.

## Invocation and native result evidence

Each ordinary effectful native request must originate from a durable HMS intent with actor scope, target, description/binding generations, typed arguments, timing policy, resource claims and required evidence. A generic agent-facing `write(path, value)` or `execute(path, text)` would bypass these semantics and is not the proposed interface. Preserve the commissioned bounded-stop exception in [02-execution](../spec/02-execution.md#cancellation-stopping-and-disconnection): if normal journal storage fails, an authenticated stop may use its installation-defined procedure with explicit degraded-audit status, local evidence buffering where possible and later reconciliation. Ordinary new mutations remain denied. The exception neither expands stop scope nor makes a sleeping client reachable.

Core §6.3.5 defines Execute as initiation of an action on one executable Resource. Its digit-keyed plain-text arguments are an encoding for that resource's documented contract. It does not supply a generic durable operation key, result history, cancellation protocol or physical completion predicate. Preserve resource-specific syntax and types; do not inject HMS identifiers into undocumented argument slots. Use a commissioned extension object or gateway operation service when endpoint correlation/deduplication is required. The extension's wire shape and persistence remain design work.

Record native responses as evidence of the phase they actually establish. A successful Write can establish that a resource value changed while the process it initiated later fails. An Execute response can support acceptance under its object definition; it is not by itself universal task-completion evidence. After an ambiguous send/reply failure, retain `may_have_acted` and reconcile against resource-specific status. A new registration, transport connection or retry key must not cause automatic re-execution of the original physical intent.

Read-Composite is optional and explicitly non-atomic/best effort. Its response may omit invalid, unsupported or unauthorized values; HMS must expose per-item absence and timestamps rather than filling gaps or claiming a synchronized snapshot. Write-Composite is optional and explicitly atomic for the addressed resource writes. Preserve this all-or-reject contract where supported; never emulate it with unqualified sequential writes. Native atomic resource changes do not specify rollback of physical consequences, synchronized actuator motion, or a transaction spanning devices. A native request has fewer messages without necessarily having stronger effect guarantees. (Core §§6.3.8–6.3.9, 8.2.1.)

## Sleeping devices, queues and cancellation

Queue Mode advertises that a client may be unreachable for extended periods. The Core delegates its transport mechanism to the companion Transport specification; this review does not establish command retention, ordering, expiry or wake-up timing for any concrete stack.

Before releasing queued HMS work, revalidate authority, latest-start time, binding generation, freshness and local interlocks. A server/gateway may hold an intent only while it can prove it has not dispatched it. Once a native transport queue owns a request, the operation is in the possible-dispatch domain. If that queue cannot reject stale requests at the final execution point, the binding cannot promise timed or revocable offline mutation through it. Native registration renewal cannot extend the action budget or an authority lease.

Offline continuation requires a finite, previously admitted local procedure and declared loss-of-contact behavior. A sleeping client cannot provide a bounded remote stop merely because it is registered. Commission a local watchdog or another independently enforceable stop path before advertising such a guarantee. Cancel Observation ends a reporting relationship; it does not cancel the equipment action being observed. Unsupported action cancellation is reported separately from the operation state.

## Observations, time and historical data

Preserve source values and native types, including 64-bit integer precision, finite-number restrictions required by HMS and explicit binary encodings. An adapter must not let a JSON number parser silently round an integer or infer units from a friendly resource name. Preserve absent optional Resources and distinguish values from executable Resources, whose native data type is `none` and whose arguments require their own definition. (Core §7.1; Appendices C–D.)

Notification periods bound reporting behavior. `pmax` can retransmit an unchanged resource; `epmax` bounds evaluation of reporting criteria. Neither establishes a universal sensor acquisition-age bound. Observe-Composite may include unchanged resources whenever another included resource triggers notification. Evaluate freshness and evidence kind per item.

SenML timestamps can identify historical representations, and Location Object 6 includes a measurement Timestamp. Device Current Time is writable and does not supply a synchronization uncertainty bound. Preserve the native timestamp/base-time convention, report receipt time independently, and attach a validated clock mapping and acquisition-latency bound before satisfying an HMS freshness requirement. Unknown time quality remains unknown. The Location Radius is spatial uncertainty, not clock uncertainty. (Core §§5.1.2, 6.4, 7.4.6; Appendix E.4/E.7.)

Notification storage can flush historical data after reconnection; `hqmax` drops the oldest entry when full. Report bounded retention and possible gaps, retain acquisition times, and never relabel a historical burst as freshly acquired because it just arrived. Attribute changes can lose information when observations are recreated; a new native registration also requires observation setup. Advance the adapter stream epoch and expose an explicit gap/resnapshot requirement when continuity cannot be established. Native notification reliability is not evidence that every physical change was sampled.

## Native authorization and maintenance

Intersect HMS authority with native ACLs and resource operation support. A native ACL grants operations to an LwM2M Server for an Object Instance; its `R` bit also covers observation and Write-Attributes. Single-server configurations can have implicit full native access. An Access Control Owner manages ACLs; that role is not an exclusive physical resource owner and carries no fencing epoch. Explicitly commissioned exclusivity or endpoint enforcement is necessary if another server, local operator or independent controller could issue conflicting commands.

Keep bootstrap, credential rotation, ACL changes, reboot, reset and firmware update behind distinct maintenance privileges. Bootstrap has privileged configuration semantics outside normal ACL enforcement and may alter accounts or discard pending unrelated responses. Record the transition, apply the device's commissioned interruption policy, invalidate affected bindings, and reconcile outstanding work before admitting new ordinary mutations. A failed bootstrap's promise to retain the former bootstrap-server account must not be generalized into transactional rollback of all configuration or physical effects. (Core §§6.1–6.3, 8.)

Keep credential-bearing objects and resources out of model-visible discovery, observations and logs, including MQTT passwords and application-security keys. Do not use the 2020 Core's incomplete list of protected object IDs as an allowlist. Later Core corrections explicitly protect COSE Object 23 as well as Security 0 and OSCORE 21. Credential material stays in the binding's secret store. [Core 1.2.2, §§1.2, 6.3 and 6.4](https://www.openmobilealliance.org/RELEASE/LightweightM2M/V1_2_2-20240613-A/HTML-Version/OMA-TS-LightweightM2M_Core-V1_2_2-20240613-A.html)

Firmware Object 5 separates Idle, Downloading, Downloaded and Updating from Update Result. A Package URI write can start a later download; Update is executable only while Downloaded. Optional Cancel is unavailable once installation has begun or completed. Deferred updates can later install automatically when their defer interval ends. Capture native State/Result transitions and artifact identity, retain exclusive maintenance ownership across deferral, and recheck install conditions at the actual installation boundary. If the endpoint cannot enforce those conditions, do not advertise conditional deferred installation.

Installation completion needs the defined native result plus authenticated post-update identity/version evidence and revalidation of the commissioned binding. An Idle state alone is insufficient: it also follows reset or cancellation. Capture failures before another attempt resets Update Result. Unsupported objects can disappear after update. The Core leaves image application security, repository policy, storage layout and hardware update details outside its scope, so an artifact hash, publisher verification, hardware compatibility, activation/rollback policy and physical-state reconciliation remain HMS deployment requirements. (Core Appendix E.6, including the visually reviewed state diagram on p122.)

## Implementation boundary and next work

Use this binding for management and supervision where its object definitions fit the equipment. An Arduino-class endpoint may expose installed primitives through a gateway; the gateway must state its identity and control limitations. Linux/GPU endpoints can use the same HMS contract without pretending that their streams or kernels are native LwM2M capabilities. This review establishes no RAM, latency, throughput or hard-real-time performance result.

Before implementation claims, finish the chosen Core/Transport release, applicable security standards and exact object XML review. Then implement a read-only enrollment/description/observation path with explicit unavailable fields; add the durable gateway operation service and an independently commissioned endpoint extension only where required. Adversarial fixtures should cover identity substitution, registration expiry, object-version changes, duplicate Execute arguments, partial composite reads, rejected composite writes, stale historical notifications, reboot continuity, sleeping-client expiry, two native writers, firmware deferral/cancel races and ambiguous recovery. Hardware timing and fault-injection tests follow the static contract work; none were performed in this review.
