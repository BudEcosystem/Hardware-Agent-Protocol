This retained V1.02 guide specifies a serial exchange and installation contract. It does not supply an authenticated execution receipt, a physical completion oracle, or a durable authority model. The observations below distinguish its rules from proposed implications for a shared serial provider. Page numbers refer to the [pinned 44-page PDF](inputs/research/instrumentation/raw/modbus-serial-v1.02.pdf).

| Guide evidence | Consequence for a shared serial provider (design inference, not an implemented feature) |
| --- | --- |
| §§2.1–2.4, pp.7–11: one master and one transaction at a time; slaves reply only to requests. §§3.3.2–3.3.3, pp.22–23: one transmitting driver at a time. | All routes on the same physical bus need one transport owner and a shared arbitration resource. Separate slave addresses, logical device instances, or hub children do not make concurrent transactions independent. UART configuration, transmitter enable, receive framing, pending response, and turnaround belong to that owner. A lifecycle transition must settle or inhibit the old transmitter before handing the bus to another owner. Software claims cannot exclude an uncooperative external master. |
| §2.2, p.8: address zero broadcasts, 1–247 identify slaves, 248–255 are reserved; the master has no protocol address. §4.2.1, p.33 warns about duplicate slave addresses. | A bus address is routing information, not authenticated device identity. Installed register maps, functions, units, write semantics, address assignment, and shared-resource aliases must come from trusted configuration. Changing address, port mode, or bus configuration affects that binding. A protocol response alone cannot attest which physical installation answered. |
| §§2.1, 2.4.1–2.4.3, pp.7,9–11: broadcast writes produce no replies; turnaround allows receivers time to process. Appendix A, pp.35–37 also accounts for broadcast exceptions without an exception reply. | A successful write to the local serial interface establishes neither reception by every device nor successful application. A broadcast cannot be authorized as though it affected only one route. A conservative provider may decline broadcasts; that restriction must be described as a supported subset, not full compliance with the guide's broadcast requirements. Silence after the configured delay is not a completion receipt. |
| §§2.3–2.4, pp.8–11: the serial carrier contains address, function, data, and checksum. An unexpected slave reply leaves the response timer running. A timeout or damaged reply allows retry according to master configuration. | The carrier supplies no generic transaction ID, caller identity, lease, or replay key. After an uncertain write, a later same-address/function response may not distinguish attempts. Preserve the exact request, transmission stage, raw reply or timeout, owner/configuration epoch, and uncertainty. Bounded retries need operation-specific semantics or trusted deduplication beyond this guide. Reissuing an effectful request because its response was lost is not justified by the state diagram. |
| §§2.4–2.5, pp.9–18 distinguish response timeout, broadcast turnaround, and framing timers. RTU uses 11-bit characters, a gap of at least 3.5 character times between frames, and rejects an intra-frame gap above 1.5. At or below 19,200 bps those character-based timers must be respected; above that rate the guide recommends 750 µs and 1.750 ms. | These are distinct budget components. Derive character time from the configured wire format and baud rate; do not substitute a socket timeout or host sleep measurement. Account for request serialization, hardware transmit completion, receiver processing, reply serialization, and post-frame silence. The guide's typical response and turnaround values are examples, not qualified worst-case bounds. Host scheduling, buffering, clock error, and transceiver enable timing need separate evidence. |
| §§2.5.1–2.5.2, pp.12–18: RTU is required/default, ASCII optional; common serial parameters are required. RTU frames are bounded at 256 bytes; ASCII frames at 513 characters, colon/CRLF framed, with configurable inter-character timeout. | Use closed mode/format settings and bounded frame buffers. An ASCII inter-character timer alone does not bound an entire operation; retain an aggregate deadline and finite input/work budget. A partial frame or new colon must not inherit the preceding message's semantic authorization. No automatic mode/baud change should silently change an installed binding. |
| §§2.5–2.6 and Appendix B, pp.14–19,38–43 define public CRC/LRC arithmetic and parity checks. §2.6 uses the word “security” for error checking. | These checks detect certain transmission errors; they do not authenticate a sender, authorize an action, prevent replay, or establish freshness. Anyone able to construct a frame can calculate its checksum. Checksum-valid data must still pass exact address/function/length and device-specific semantic checks. This is an inference from the unkeyed algorithms and frame grammar, not a claim about a separately secured deployment. |
| §2.4.2, p.10 puts the unicast response after processing the requested action, while the document explicitly complements the application protocol (§1.1, p.4). | Interpret success at the supported function/register contract. A register-write acknowledgement can establish the documented register operation without proving a motor stopped, a valve moved, or a timed pulse finished. Physical completion, idle-before-release, cancellation, and safe recovery require device-specific evidence. A canceled host request does not retract bytes already transmitted. An uncertain handoff must not be converted into zero effects by timeout, restart, or local queue deletion. |
| Appendix A, pp.35–37 defines aggregate diagnostics cleared by restart, power-up, or a diagnostic command. | Counters help diagnose communications; they are not immutable per-operation receipts. Reads of them do not repair missing request association or prove exactly-once effects. Counter clearing is itself a management action whose authority must be explicit. |
| Chapter 3, pp.20–32 covers common conductors, pair topology, loading, termination, biasing, shields, and pinouts; §4, p.33 notes that connector shape often provides no protection against a wrong connection. | Logical containment in a hub must not be confused with electrical independence. Installation evidence must identify the physical bus and wiring assumptions. This document read cannot qualify a cable, load count, grounding arrangement, baud tolerance, or electrical safety of an actual installation. No hardware was contacted. |

Two source-reading cautions matter for implementation. First, the extracted text on p.36 includes duplicated counter labels and the strings `255number` and `3 characters silence` (text lines 1971 and 1978). The rendered flowchart has neither numeric limit: it labels a maximum character count and end-of-frame detection generically. Those extraction remnants must not override the explicit 256-byte and 3.5-character rules on p.13. Second, §3.2, p.20 says both 9600 and 19200 bps are required, whereas the Basic class table on p.34 lists 9600 with 19200 recommended. A future conformance claim should resolve and declare its class/profile rather than silently choosing whichever reading is convenient.

Appendix B was read as published source material, including the LRC example, CRC algorithm, worked example, C function, and both lookup tables. None was compiled or executed. The explicit wire rule is CRC low byte first (pp.14,39–40); presentation of a swapped hexadecimal result on p.41 and the function's byte-swap note on p.42 should not become an assumption about host integer memory layout. This lane performs no independent algorithm validation and claims no implemented Modbus driver or device qualification.
