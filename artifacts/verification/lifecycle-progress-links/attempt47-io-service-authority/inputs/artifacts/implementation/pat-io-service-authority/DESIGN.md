# Authority-owned finite I/O service configuration

This stage extends the [configured service](../pat-io-service-config/DESIGN.md) with a durable store inside the existing Journal authority. It is a host library for the finite synthetic GPIO/PWM policy. Public mounting, promotion, actual target providers and general hub management remain separate work.

An administrator explicitly creates the store. Four fixed tables hold immutable configuration versions, mutation keys, current heads and bounded metadata. Creation, configuration admission, receipt chaining and head updates use the existing Journal owner and transaction; no extra database is opened. The registry retains a metadata digest anchor. Missing or partial tables, unexpected owned schema objects, temporary shadows, changed limits and malformed retained rows refuse without repair. This is consistency checking within the trusted authority; it is not attestation against an adversary rewriting the whole database and its anchors.

Configuration mutation keys are scoped by principal. Requests bind the actual Journal authority ID, deployment, evaluator, expected prior revision and normalized configuration. Exact committed replay returns the original receipt before consulting source files, a runtime, current revision or remaining capacity. Changed requests with the same key conflict. Fresh commits require current admin authority, compare-and-swap revision, source-derived service pin and a complete descriptor snapshot from the installed resolver. Preparation occurs outside the authority transaction; admission is repeated inside the final transaction. A failure before commit rolls back configuration rows; a lost reply after commit can be resolved by lookup or exact replay. The existing independently retained clock floor may advance during a refused transaction.

The authority-bound service pin uses profile `hms.pat.io-service-pin/0.2`. Its configuration digest incorporates the Journal authority ID, so identical configuration names on different authorities do not produce the same run identity. Legacy profile 0.1 remains supported by the earlier pure service API. Durable authority history requires profile 0.2. Pins bind configuration and current compiler, driver, worker and supervisor sources, including this store. A pin remains data interpreted against a trusted anchor, not a standalone credential.

`IoRegistryPatBindings.configured_snapshot` obtains every explicitly registered descriptor inside the owning transaction. It validates the complete installation, current/historical bindings, resource proofs, route readiness, exact installed argument semantics, permissions and session provenance. No unavailable registration is silently omitted. It performs no writes and does not construct a fake candidate to discover capabilities. Session expiry remains typed provenance, not proof of current freshness; effect admission still performs its own checks.

Fresh run preparation compares installed configuration with the active durable record, reconstructs the original service using the stored pin and current sources, and obtains actual descriptors from the resolver. It uses the original complete matrix and bundle builders. A final transaction checks that the configuration and descriptors have not changed during planning. This is a consistency window, not a future lease or a durable run reservation. The existing supervisor ledger supplies run replay/conflict semantics. Catalog promotion must separately revalidate its current environment.

Retained history is canonical and closed, with typed/size preflight before payload reads. The store allows at most 128 revisions, 16 services and 8 MiB of accounted encoded data; creation may lower revision or byte limits. Per-record bounds remain 64 KiB configuration, 4 KiB pin/receipt and 2 KiB mutation request. No pruning or capacity-widening operation is introduced. Accounting is not an aggregate filesystem quota, SQLite memory limit or hard execution-time bound.

Thirty-two new control methods cover persistence, replay, source independence, revisions, authorization, two authorities, concurrency, commit interruption, capacity, corrupt-state retention, descriptor completeness and planning races. A separate actual-worker method reopens the authority, derives the plan from its installed resolver, retains configuration/pin/receipt before supervisor construction, and invokes the unchanged original owned worker and independent 30-case outcome reader. The source authority must show no device effects or claims. Inherited 206 controls and ten process selections are rerun with the expanded source identity.

Source, review and exact harnesses are frozen before project execution. New authority controls have a separate 16 MiB scratch scope, only 74 declared private database opens (at most four per method), no network or subprocess. The new process selection permits only its runtime's two fixed database paths and original supervisor ledger, at most six opens, plus the original fixed worker command. Existing 60-second owned/group and 180-second outer deadlines, effect, file and retention limits remain. All raw attempts, including failures, are retained. No hardware, emulator, acquired controller, live inference/service or adjacent Harness checkout is executed. Review is by the primary agent only.
