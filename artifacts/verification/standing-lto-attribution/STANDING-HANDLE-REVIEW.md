# Standing handler serialization review

The retained `hms_standing_handle` section is 5,784 bytes: 2,733 instructions occupying 5,752 bytes plus two eight-entry `.word` jump tables occupying 32 bytes. Its exact fit-baseline section is 5,816 bytes, a 32-byte reduction. The tables are reached by two `jmp __tablejump2__` instructions; neither table bytes nor jumps are counted as direct CALL sites. There are 124 direct CALL sites, including 17 `put64`, eight `read64`, 13 `put32`, and 39 `read32` calls after resolving the retained GAS aliases. This is static attribution, not execution frequency or a fit result.

The complete standing source prefix through handle (lines 1–492, SHA256 `cf3b9452882f14418b10262363deeaad8a2fafe568ae072b737ca571cd15b2e8`) was read. All 482 lines of the compact standing-handle instruction/data/label stream were read, covering raw assembly unit 18341–22165. A separate data-only comparison verified every instruction and `.word` token against its exact raw line. Most raw debug directives were not independently read for this unit; the raw section boundaries/tail and alias lines were. This differs from the complete raw-unit reading performed for the finite handlers. [finite-coverage.json](finite-coverage.json) records the distinction and all input/range hashes.

Four sites decode an already encoded eight-byte value and immediately encode the same value elsewhere. Source `r64` / `w64` are pure big-endian decoders/encoders and the retained aliases resolve to `read64` / `put64`.

These four windows total 94 instruction bytes, including eight CALLs (32 bytes) and register/pointer setup within the stated windows. They exclude earlier pointer preparation and the shared decoder/encoder bodies. Other reads still validate lease/syntax, so changing these copies does not imply either shared helper disappears. The original decode reads all eight source bytes before the encoder writes. A future byte-copy substitution needs overlap-safe semantics (for example a memmove-equivalent operation), or a proved non-overlap contract; the public handler itself does not establish that arbitrary request/record pointers cannot overlap. No substitution or resulting size claim was made here.

Nine of the 17 `put64` sites write `ABSENT == UINT64_MAX`. The remaining sites are the four encoded roundtrips above and four encodings of native `now_tick` values (CALL lines 20210, 20277, 21102, 21782). The ABSENT sites are OPEN's loss/cleanup/quiescence/feedback initialization (20222, 20234, 20245, 20293), RESUME's feedback/loss/cleanup/quiescence reset (20997, 21115, 21126, 21135), and the public state-page quiescence redaction (22053). The last redaction must still hide private loss-handoff storage until a valid witness exists.

The nine ABSENT preparation windows are 20212–20222, 20225–20234, 20236–20245, 20283–20293, 20987–20997, 21105–21115, 21117–21126, 21128–21135, and 22041–22053. They contain 208 instruction bytes in total: 64 explicit `ldi ...,lo8(-1)` instructions (128 bytes), nine CALLs (36 bytes), and pointer/setup instructions within those windows (44 bytes). Some pointer loads occur before the windows, and some adjacent sites reuse preserved argument-register values. This is a measured caller-span total, not a forecast of bytes saved by an eight-byte fill. Encoding UINT64_MAX does yield eight 0xff bytes, but any proposed replacement still needs new generated evidence and full behavior checks.

Existing constant copies and zeroing already compile to compact counted loops rather than expanded per-byte instruction sequences. For example, the occupied header copies 42, eight, and eight bytes at raw lines 21551–21584; the unoccupied header reuses the final copy loop via a jump at 21702. The state page copies 124 bytes at 22025–22030; observation and activation pages copy 48 and 44 bytes at 22076–22081 and 22091–22102. Each shown copy loop body is `ld`, `st`, `dec`, `brne` (eight static instruction bytes), with its own pointer/count setup. The OPEN 134-byte record copy at 20026–20035 has the same bounded loop form. Zero-fill loops use `st`, `dec`, `brne`; they are not arrays of 128 or 192 separate stores. Counting transferred data bytes as flash bytes would be incorrect.

The 17 encoder calls use the eight-byte value argument registers plus a destination pointer. Decode returns require four `movw` operations to move the result into encoder argument registers in each roundtrip; the measured windows expose this ABI cost directly. The shared encoder and decoder map sections are 92 and 48 bytes, respectively, and remain shared with other callers. Handle's own prologue saves 18 register bytes and allocates 23 local bytes; the `.su` entry reports 43 bytes, static. The common endpoint handle's live caller frame and outgoing arguments remain separate obligations. No combined stack bound, timing qualification, physical I/O qualification, or target execution is claimed.
