# Staged acceptance plan — execution not released

This is a source-preparation handoff, not a completed or qualified executor. Do not import or execute the copied project until the parent agent explicitly releases the shared hold after its full747 milestone. Source snapshots 01/02 and their independent reviews remain historical. Snapshot 03 adds the exact reviewed ordinary I/O output-contract port and the final source draft/test/harness bytes.

The executable baseline is the full696-derived 146-file prepared ordinary provider, with later source changes recorded separately. It is not an assertion of compatibility with the complete live747 tree. The copied native endpoint binaries are acquisition context only and are not test targets here.

## Intended order after explicit parent release

1. One copied current-source lifecycle setup/admission smoke case: `test_io_lifecycle.LifecycleTests.test_exact_all_sibling_claims_and_no_admin_publication_shortcut`. Retain failure if construction or admission fails; do not call a setup error a demonstrated lifecycle property.
2. If the setup path is established, run the specific old-proof/revision and delayed-final-lookup regressions against the retained snapshot01 source overlay, then the current source. The harness combines the old reviewed HMS source files with the later regression tests and records that composition. Before/after cases must preserve their exact source pins and actual outcomes; a different failure is not proof of the intended regression.
3. Run the 30 currently drafted lifecycle methods and 14 source-ported ordinary API result-contract tests in a new copied attempt. No skips/expected failures count as a full pass. The original authority and board stores are backed up per case, including failure paths; runtime/source/environment manifests are recorded before and after.
4. When that evidence supports it, run the 24 original ordinary-provider methods and appropriate original Journal/Registry/ResourceCatalog regressions against the same staged changes. This checks the shared extraction/profile hooks. It is not a live full-suite run or native endpoint/hardware test.
5. Review exact terminal receipts, source/input stability, actual database evidence and remaining limitations before any integration proposal. Any fixes get a new source snapshot and a new immutable attempt; no historical receipt or baseline is repinned.

The runner is `run_attempt.py`. Invocation requires the explicit `--parent-released` flag and a unique attempt name. A command example to use **only after release** is:

```text
python3 artifacts/implementation/io-lifecycle-settlement/run_attempt.py attempt01-smoke test_io_lifecycle.LifecycleTests.test_exact_all_sibling_claims_and_no_admin_publication_shortcut --parent-released
```

The runner copies the entire prepared project before loading tests. It records the original script, command targets, return code, test counts, source manifests, selected validation-distribution/Python/_sqlite3 manifests, scoped imports and per-case evidence. Network socket audit events are vetoed. This is a trusted-code restriction, not an OS sandbox or a hard aggregate filesystem quota.

## What the draft tests address

Actual original Journal admission and claims are used for sibling and cross-route alias exclusion, independent-pad progress, management grant separation, omitted resolver fallback refusal, exact request replay/key conflict, current/new versus historical ordinary bindings, inactive/grant preservation, scoped rebase, missing evidence/claims, corrupted quiescence, original old-Registry profile refusal, cancellation truth, and both sides of provider/authority settlement. Authority mutation failures after binding publication, after resource release, and at COMMIT are drafted to check rollback without clearing unknown claims. Two timing cases keep the original start budget: expensive binding preparation and the exact final-guard operation lookup. They are controlled-clock logic checks, not native-clock availability measurements.

The historical publication test substitutes a valid old proof, uses a boolean revision, changes the bindings container type, and finally restores exact original bytes to check unchanged replay. That last restoration is a controlled test action, not an automatic repair path in the implementation.

## Remaining acceptance and integration limits

These tests have not run. Additional cases should be assessed after the first evidence: explicit driver-target and dependency-free-service execution, capacity/revision exhaustion before and after a provider effect, partial installation/profile activation, broader field/fence/history corruption, and repeated generation changes with more historical receipt/cache combinations. Their absence must not be described as covered by the 30 draft methods.

The lifecycle output has an explicit `hms.synthetic-lifecycle-result/1` tag, but the current public validator does not support it. This deliberately fails closed instead of mapping it to legacy `effectCommitted` or ordinary GPIO/PWM activation fields. A separate reviewed lifecycle result schema and Runtime/IPC/CLI/MCP mounting step are required. The source-ported ordinary `hms.synthetic-io-result/1` fix does not establish lifecycle public compatibility.

The modeled effect changes a synthetic generation record while the full admitted physical footprint is already known idle. It does not restart OS services, load drivers, control actual hub hardware, qualify electrical states, establish autonomous stop behavior, or implement a general learned PAT outcome policy. Static future-step scope validation gives no current CAS, admission or effect authority. The broader prompt-to-agent-to-learned deterministic PAT and device/driver/hub goal remains open.
