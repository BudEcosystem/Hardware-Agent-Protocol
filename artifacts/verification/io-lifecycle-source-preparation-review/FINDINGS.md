# Snapshot03 source-only harness review

This review read the complete runner and acceptance plan, plus selected test capture/import paths and lifecycle generation/capacity seams. It did not import the copied project, run tests, open project databases, or approve the lifecycle implementation. Snapshot03 remains unchanged. Findings below concern the first future staged execution; no failure has been experimentally reproduced here.

1. **Attempt finalization and process ownership need explicit failure paths.** `run_attempt.py` uses `subprocess.run` without a timeout or surrounding `try/finally`. Launch failure, interruption, or an exception while producing after-manifests can leave before-only evidence without a result receipt. The runner must retain an owned child handle, bound waiting/termination, attempt finalization on every catchable exit, and mark unavailable after-state as unknown rather than inventing stability. Hard kill, host failure, disk exhaustion and OS-uninterruptible waits cannot be promised a completed receipt.

2. **Database capture failure can erase the only original state.** Both test capture helpers set their final-capture flag before backups complete. A backup error suppresses the cleanup retry, then `TemporaryDirectory` cleanup can remove the original authority/board files. Mark completion only after successful capture, retain raw scratch on failure, and record capture exceptions separately. A SQLite backup is a logical snapshot, not a byte-identical original WAL/database acquisition.

3. **The actual-import ledger misses shared project inputs.** It only selects `hms` and `test_io_*` names. `test_resource_topology`, other selected shared test helpers, and a dynamically executed old Registry fixture may not be listed; the latter is not inserted into `sys.modules`. Before-file hashes establish acquisition, not which source executed. Collect every imported project/test module by resolved origin and record executed code origins for dynamic fixtures. Validate against the copied input manifest, distinguish standard-library origins, and refuse unexpected project origins.

4. **Selected environment capture is incomplete even within its declared scope.** The full ambient environment is passed to the child, but effective variables, interpreter flags, import paths and startup customization are not recorded or controlled. The five distribution inventories plus Python and `_sqlite3` hashes are useful selected pins, not the whole host closure. Use an explicit safe child environment and record it; suppress ambient Python startup hooks where practical, pin selected package resources, and inventory actual external module origins. Do not dump inherited secrets or claim complete stdlib/shared-library/OS attestation.

5. **The runner should validate its success receipt and permitted targets.** It accepts arbitrary unittest names and bases its own exit on child status plus hash equality; it does not require a positive test count or a complete, closed test-return record. Restrict this first executor to explicitly approved pure/SQLite test modules, require exact counts with zero failures/errors/skips/expected failures/unexpected successes, and treat missing or malformed child reports as incomplete. This prevents an accidental empty target suite or unrelated native endpoint test from being described by the narrow lifecycle scope.

The source baseline itself is retained: snapshot03 contains 155 copied project inputs and the original 146-file baseline remains separately pinned. The documented exclusion of whole-host identity, physical qualification, native-clock availability and public lifecycle compatibility is correct.

## Cases to draft only after current-source smoke evidence

- **Driver target:** execute installed `advance_driver` against `driverA`; prove the exact target lifecycle atom and every sibling-action physical claim, unchanged service token and unrelated instance binding, one generation publication/release, old receipt replay after reopen, and fresh GPIO/PWM support under the new derived binding.
- **Service with no dependent consumers:** add an explicitly installed service with its lifecycle atom but no consumer dependency. Its admitted scope must contain exactly that atom, affected bindings must be empty, ordinary work must continue, and settlement/replay/reopen must still record one genuine synthetic generation effect. Merely containing nodes structurally must not expand ownership.
- **Capacity boundaries:** exercise the inclusive 32-claim boundary and refuse 33 without truncation; exercise management action/route/instance inventory limits before activation; separately test a valid installation whose derived dispatch/receipt/publication exceeds the canonical byte bound. Preserve any already-admitted claims when later serialization or storage fails. Exercise history-cache eviction with retained exact old receipts, without treating the 128-entry memory cache as a durable-history quota.
- **Revision exhaustion before effect:** use explicitly labeled, internally consistent boundary fixtures (not an asserted natural history of quadrillions of operations). Check exact integer limits, final permitted increment, refusal of later fresh work, and unchanged generations/claims/evidence on refusal. Do not merely patch a limit constant or create a malformed snapshot that fails for another reason.
- **Revision exhaustion after provider effect:** place a legitimate effect before an unrelated authority revision consumes the last publication slot; settlement must refuse without overflow/wrap or partial authority changes, preserve provider truth and all owned claims, and remain unknown on reopen. Prove that unavailable publication capacity never becomes a fabricated no-effect terminal receipt. Distinguish authority-global revision from provider-local revision.

These cases are acceptance proposals, not current test coverage. After the smoke path exists, select small faithful fixtures and record their exact construction before drafting assertions.
