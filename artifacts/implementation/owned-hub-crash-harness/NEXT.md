# Remaining hub recovery obligations

The twelve fixed owner-death cases establish conservative recovery at the selected provider checkpoints while a dedicated ancestor guardian remains alive. They do not complete the hub resource provider or the HMS goal.

1. Deliberately retain a child writer after early leader exit using an owned, source-reviewed fixture with deterministic coordination. Verify that the matching lease blocks terminal inference until every writer settles; this must not depend on a scheduling race or a brief sleep.
2. Integrate a durable hub resource provider with common admission, current artifact/configuration identity, original-key replay and explicit ownership generations. Define aggregate CPU, memory, process, file and retained-output capacity; per-process limits alone do not enforce aggregate reservations.
3. Supply protected control storage and backed continuation capacity before public mounting. Terminal syscall-boundary exceptions and process death do not qualify physical power-loss durability or universal storage exhaustion recovery.
4. Add actual driver/service and GB10/GPU contracts with concrete cancellation and settlement evidence. Process exit is not physical quiescence, GPU completion or safe device state.
5. Connect current qualified PAT selection and standing endpoint deployment to the same device/driver/hub resource graph. Prompt synthesis, experience-driven qualification, persistent host deployment and physical stopping remain separate required work.

Preserve the immutable attempts. Do not rerun unchanged attribute/adoption controls, infer authority from a persisted PID, increase bounds to conceal a failure, or present the live guardian as containment after all guardians die.
