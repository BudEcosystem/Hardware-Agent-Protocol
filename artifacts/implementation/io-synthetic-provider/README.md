# Staged original shared-board I/O provider

This lane implements an original SQLite GPIO-pulse/PWM-burst model in copied HMS sources. It is not integrated into the live application. The initial design is in `DESIGN.md`; the first source review and its exact old source copies remain under `review/`. Driver/service lifecycle execution is deliberately unsupported until a separate receipt-gated authority settlement contract is implemented and reviewed.

The 49 baseline copies combine the exact reviewed resource-admission Registry/ResourceCatalog with the live checkpoint's other project sources and local data. `baseline/inputs.json` distinguishes original source locations. These are acquisition pins, not a claim to have fully read every copied file. `io_fixtures.py` is the exact original helper source from the sealed admission stage (SHA-256 `9e4ce3eba938b432117c61ec301e7cf087ce9e28cc6c211d292c5487d46a4d5f`). No acquired controller is used.

## Implementation and trust boundary

`synthetic_io_installation.py` defines a closed `hms.synthetic-io-installation/1` descriptor with one board, bounded topology/initial generations, complete route/handler inventory and explicit `gpio_pulse`/`pwm_burst` primitives. It derives original I/O type bundles and proof-bound resource maps. It neither relabels nor executes the fan/focus/inspection handlers. Its project identity conservatively includes every staged HMS Python module, local schema and retained protocol data file, including unused project modules. This can invalidate an installation after unrelated project changes. Five installed Python validation distributions and their files are separately recorded by test receipts; the interpreter binary and complete OS environment are not included. Neither digest is physical attestation or general PAT qualification.

`synthetic_io_catalog.py` persists a distinct adapter catalog profile, exact installation, route readiness and immutable dispatch/receipt records. It activates the reviewed ResourceCatalog explicitly. A missing store after effect history is not recreated. Complete, ready installations reopen for historical recovery independently of current read/admin grants, active flags or fresh generation support; those conditions continue to deny fresh work through the existing policy and installed-handler checks. Unready provisioning still requires the original administrator authority.

`synthetic_io_board.py` owns one separate SQLite database bound to the Journal authority ID, board ID, descriptor and owner epoch. All routes share this same object and store. Canonical atom fences and active-owner rows prevent route aliases from maintaining separate physical histories. Exact receipt replay precedes fresh session/fence checks. New operations require strictly newer fences. Each activation and each terminal transition commits state and a versioned receipt together.

Active GPIO uses a virtual push-pull level; PWM retains virtual pin, timer and channel state. Completion/cancellation commits high-impedance pad state, disabled timer/channel state and exact idle evidence before host claims may be released. Interrupted pulses preserve `activationCommitted:true`; cancellation is not described as an effect-free event. A no-start veto is a distinct terminal receipt. An exact pending receipt after a lost handoff acknowledgement may justify a conservative stop, never an implicit continuation.

Owner recovery runs once per board/Journal epoch. It verifies current resource, owner, fence, counter and pending-receipt consistency before canceling original model work into safe idle. Missing or contradictory evidence is not repaired by asserting idle. A terminal receipt is used for settlement only after a current validated board snapshot; valid historical receipts remain readable when a later correctly owned operation uses the same atom.

`synthetic_io_adapter.py` uses original Journal admission, dispatch, cancellation, evidence, reconciliation and release methods. The existing dispatch reservation hook stores exact intent, canonical claims, attempt, original owner epoch and timing checkpoint in the authority transaction. Association checks the closed typed link against the immutable `dispatch_claimed` event. Verified provider receipt versions are retained in the authority before evidence use, so policy evidence validation performs only authority-local reads and pure checks. Current authority loss can inhibit fresh execution without preventing historical stop/reconciliation.

`synthetic_io_runtime.py` supplies an explicit internal I/O bootstrap and inherits the original Runtime scheduler, route selection and API methods. It creates one board and passes it to every installed route; the individual route close method does not reset or close the shared board. The copied `state_path.py` change admits only one additional exact hashed database-name prefix and retains the original owner/mode/link/sidecar checks. Stock Runtime construction, daemon configuration, IPC/CLI/MCP mounting and installed PAT routing are unchanged in the live tree.

`synthetic_io_storage.py` checks SQL storage type, byte size and row count before fetching bodies from the new provider tables. A receipt/dispatch body is at most 65,536 bytes, receipt versions per operation are limited to two on evidence reads, and active state inventories are bounded. These are host-fetch bounds, not bounds on SQLite's internal allocation, scan time or `CAST` work. They do not establish a total disk quota or an allocation bound for every inherited authority table. In particular, the copied historical ResourceCatalog remains the exact reviewed baseline; its body-fetch hardening is a separate root integration item.

## Timing and semantics

Start and completion guards sample authority and monotonic time after potentially slow catalog/policy validation and again at the board transaction boundary. They preserve original start, completion, maximum-run and lease bounds. A timing or authority veto never starts output and can stop exactly owned output. Returning to idle does not require fresh permission to continue an operation.

The model is host-driven. The virtual pin can remain active until the scheduler next services it or owner recovery runs; no autonomous hardware timer, bounded stop latency, waveform, electrical loading, real-time SQLite commit bound or physical output is claimed. A real finite-pulse provider would need qualified endpoint timing and independent local stop behavior. Controlled-clock tests establish refusal/state-transition logic, not native-clock availability under host load.

`publish_generation` remains an admin configuration API. It cannot execute a provider effect, update the board's actual generations or turn a changed binding into supported I/O. `current_generations_supported` is diagnostic only: an unrelated generation change can leave a consumer's scoped proof/binding unchanged, so that unchanged consumer can remain supported. A separate lifecycle operation must retain its full sibling-expanded claim footprint until an exact provider receipt and all authority binding/proof publications are settled atomically. The design explicitly rejects releasing or exempting those claims merely to call the admin method.

## Evidence procedure

The root execution hold was observed until the live 643-test checkpoint completed. Each later `run_tests.py` invocation creates an immutable numbered attempt, copies the executable source/data before import, checks source and validation-package hashes before/after, and records imports, test counts and failures. Tests invoke only the staged original I/O model with controlled clocks; no hardware, model, OS driver or native endpoint subprocess runs. Authority and board SQLite backups plus the actual installation/time context are retained per case, including setup failures where stores exist.

The initial review identified corrupted-quiescence settlement, recovery after current binding invalidation, exact dispatch association, bounded SQL reads and overbroad source-identity wording. Its record is preserved. Revisions add explicit regressions; final source-review status is recorded separately rather than rewriting that original review.

Attempt 01 ran 24 tests: 22 passed, one failed and one errored, with 54 copied inputs unchanged. The errors were test assumptions about the Journal's principal-owned operation reads and throttled sampling at unchanged virtual time. The next test revision preserves the public access denial, inspects recovery through the trusted internal view, and forces sampling for the separate missing-receipt diagnostic. No implementation change was inferred from those two results. Later receipts state their own exact outcome; they do not replace this history.

Attempt 02 passed all 24 tests in 113.999 seconds with 54 copied inputs and the validation-package files unchanged. Its receipt SHA-256 is `6e3b503f9c54da93714447a9fba4a3d98808607ef3d380628d370c3743c67b27`. The implementation bytes are identical between attempts; only the two test expectations changed. The reviewer did not rerun the suite.

No complete device/driver/hub implementation, general learned PAT outcome policy, physical qualification or exhaustive research completion is claimed.
