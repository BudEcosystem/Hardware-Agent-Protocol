# Separate current execution support from historical receipt identity

Independent design review identified this required extension to the frozen design and sealed immutable-generation provider. No code, test or provider was executed or changed. This amendment supplements the original index and Amendment 01.

In the pinned provider, `definitions(document)` derives bindings/proofs from `installation.initialGenerations`. `SyntheticIoBoard.supports_binding` compares against those definitions, and `_validate_operation` uses them when validating both new work and retained receipts. That is correct for the existing provider's fixed-generation scope. A lifecycle implementation cannot leave this view fixed after publishing new generations, and cannot simply overwrite it: the latter would invalidate exact historical receipts.

The proposed new lifecycle-capable profile must distinguish:

1. **Immutable installed structure:** type bundles, primitive/action allowlist, argument/electrical envelope, alias footprints, topology, original initial-generation provenance, installation/driver identity and board/authority identity. A generation operation does not edit the saved installation or recompute its digest from a different `initialGenerations` value.
2. **Current execution view:** derive the ordinary bindings/proofs from that immutable structure and the board's retained current generation snapshot. Fresh admission, new dispatch/start, current binding support and observation/presence refresh require exact agreement with the authority's current scoped binding/proof and relevant tokens, plus ordinary active/grant/session checks. Exposing a new board token before authority settlement must not make a new invocation executable; the mismatched affected routes remain unavailable. Unrelated unchanged scoped routes need not be disabled.
3. **Historical validation view:** use the exact binding generation, typed intent and immutable dispatch association to select a retained binding/proof and generation history, independently of current eligibility. Verify those bytes against the immutable installed handler/type/alias structure and the provider's retained generation-effect history. Cross-check the corresponding authority binding/proof history during settlement/evidence validation. Never accept a merely well-formed caller-supplied old binding or regenerate an old receipt using today's tokens.

The board's new storage profile therefore retains append-only generation snapshots/token history and the exact history association needed to validate each receipt after later changes. An operation receipt and its binding/generation association commit atomically with its provider effect. The management generation receipt binds the previous and next snapshots; historical proof lookup checks that chain and non-reuse. Body sizes/types and lookup cardinality are checked before host body fetch. Missing or contradictory history refuses; it does not fall back to initial/current definitions.

Refactor the provider's operation validation to make the phase explicit. Exact receipt replay remains first and uses the historical view without reexecuting an effect. A genuinely new `begin` requires the current execution view after that replay check. Receipt parsing, reconciliation and current-state ownership validation use the historical operation's pinned generation where appropriate; reading a historical receipt does not authorize a new old-generation operation or prove present physical idle. Settlement still requires the separate validated current board snapshot described in the original design.

Refresh must publish measurements with the binding/control generation actually supported by the current provider/authority agreement. It must not attach new samples to old binding identity or synthesize a new history record just to make publication pass. Reopen reconstructs current support and retained receipt validation from the saved installation plus append-only histories, before admitting any fresh work. Historical recovery remains available when current grants/bindings are invalidated, without restoring their authority.

Add acceptance cases through the original Journal/Registry and synthetic provider: settle one lifecycle operation, then successfully admit/complete an ordinary GPIO pulse and PWM burst using the newly derived binding; refuse an otherwise fresh request carrying the old generation without creating another effect; validate/replay old ordinary and lifecycle receipts after a later generation change and owner reopen; keep current invalidated bindings inactive; refuse missing/tampered generation history with claims preserved. A disjoint service change must leave an unrelated consumer's closure and executable support unchanged. These are required future tests, not results established by this design.

No current-generation cache or historical lookup API is claimed to exist. The live/public mounting path and I/O/lifecycle PAT outcome qualification remain separate work.

Implementation acceptance also covers bounded storage and revision exhaustion. Every new dispatch/receipt/publication metadata field and inventory needs storage type, byte length and row-count checks before host body fetch, following the hardened live resource catalog rather than copying the sealed provider's older catalog dependency. Check available revision/token/fence capacity before the provider effect. If a later disjoint publication exhausts the global revision before an already-applied lifecycle can settle, refuse overflow/wrap and retain the exact receipt and unresolved claims; scoped rebase does not invent capacity or silently widen a limit. This rare exhaustion case requires explicit recovery design, not a fabricated successful publication.
