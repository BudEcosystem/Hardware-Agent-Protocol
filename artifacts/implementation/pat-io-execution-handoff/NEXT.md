# Next: serialized I/O evidence and qualified PAT reuse

The [handoff design](DESIGN.md) joins a Journal reservation to one actual durable supervisor authority and attempt before launch. The isolated candidate retains the existing process execution limits. Its controlled admission/replay results do not establish complete worker execution, public service availability or physical outcomes. Read the exact retained attempt results before using this candidate; the new actual-worker method reached its original deadline before full inspection and later replay.

## Evidence import boundary

Define a versioned finite-I/O evaluation record that carries the source authority, evaluator, configuration receipt, run reservation, supervisor authority, attempt ID, request digest, candidate digest and exact input/output closure. Import should resolve that association through the installed service. A caller-supplied path, successful return flag or matching source hash is insufficient.

Read and independently validate retained worker evidence outside the Journal admission transaction. Require the complete declared scenario matrix and its independently inspected outcomes; preserve simulation as the evidence kind. Publish one bounded canonical evaluation record atomically, with an immutable import identity and exact replay. Lost publication replies resolve that same record. Incomplete, unknown, conflicting or noncanonical evidence cannot become eligible by reclassification. Retained failures remain available for review without entering the qualified catalog.

Separate historical evidence from current eligibility. A valid evaluation can remain readable after a driver, endpoint session or evaluator configuration changes. Fresh use must check the current allowed environment and dependencies. Do not adapt the earlier fan evaluator's fixed callback by hiding the new configuration/run identities. Add a versioned invocation/environment contract and then connect it to the existing catalog and deterministic routing path.

## Capacity and lifecycle

The observed worker and compatibility deadlines remain failures at the original bounds. No failed logical run should be relaunched with a new key, a smaller matrix or longer deadline. Protected CPU, storage and control-service capacity are deployment requirements; current observations do not establish the cause of the timeouts. Any performance correction must identify its mechanism and measure the affected work. The implementation's encoded-data limits remain distinct from aggregate filesystem enforcement.

The [spawn-loss authority challenge](AUTHORITY-FAILURE.md) reports a separate generic unexpected error after 26 cases. Its final recorded public operation is correctly denied, but the wrapper does not retain the underlying error that triggered its generic failure. Preserve operation, evidence-capture and budget errors separately in a future source version. Do not relabel this result as a proven deadline, access bypass or passing refusal test.

The legacy configured-worker attempt stops for `SUPERVISOR_RETENTION_UNKNOWN` with three retained states and an unresolved claim/board owner. The collector maps a retention-scan exception to this reason without retaining its detail. The terminal inventory cannot establish whether a transient file change, permissions, a bound or another condition caused that exception. Future monitoring needs bounded concurrent-snapshot semantics and explicit diagnostic evidence; ignoring scan errors or inferring quiescence from process exit is not a correction.

Real driver and hub management must use the same operation identity, durable receipts, dependency graph and reconciliation model, with separate permission scopes. A driver replacement drains or settles affected resource users and produces a new dependency generation. A hub restart must leave independently hosted reconciliation and endpoint response behavior available. Hardware/OS support is advertised by concrete providers; the standard does not imply that every device supports every administrative operation.

## Prompt-to-PAT integration

The intended application path remains: natural-language intent, capability discovery and context, agent-proposed candidate, measured evaluation, versioned promotion, deterministic applicability checks and execution. The stable path reuses a program with fresh execution identities and current observations. Novel contexts and failed assumptions return structured evidence to the agent. Routine deterministic contention handling does not require another model call.

For Arduino-class devices, provide a reusable commissioned endpoint executor over installed I/O primitives and a bounded program representation. Standing applications need durable trigger identities, explicit start/suspend/update/retire behavior, local control loops and outage behavior. The current finite qualification and procedure profiles do not implement that persistent layer. Learning may propose new versions; it cannot silently broaden a PAT's applicability based only on repeated successful returns.

Public tooling and Harness integration, agent synthesis and trace learning, persistent Arduino applications, actual device I/O, driver lifecycle and hub compute/lifecycle providers, streams, physical timing and microscope commissioning remain required. The [unified control architecture](../../../docs/io-driver-hub-control.md) and [prompt-to-PAT contract](../../../docs/prompt-to-pat.md) retain that full scope. The full HMS goal remains active.
