# Process-secret import attestation: feasibility only

A process-secret authenticated certificate could replace retention of the full
successful reduction in memory, but it does not remove the integrity or restart
requirements. It is not implemented here.

After full trusted reduction, the process could authenticate a closed bounded
statement containing the verifier/reducer code identity, policy/configuration,
evaluator/deployment/run binding, artifact and environment identities, exact
group/input/result digests, complete record/case coverage and closure budgets.
A fresh process-only key would be generated by trusted setup, never supplied in
caller JSON, exported through an API or handed to a worker. HMAC verification
would reject arbitrary DB rewrites of that statement. A stored Boolean or
unkeyed digest would not provide this property.

The key would disappear on restart. Existing statements would become
indeterminate and require full validation before being authenticated under the
new key. Persisting the key instead would introduce a separate secret-storage,
permissions, rotation, rollback and recovery design; it is not a small extension
of a process-only cache. Either design would have to bind all code/config/run
identities explicitly, reject conflicting statements, and distinguish an absent
or invalid certificate from established candidate ineligibility.

Even an authentic statement does not prove the continued presence or integrity
of its referenced bytes. Eligibility would still need bounded reads and hashes
for every required current document. With an authenticated previously validated
closure, raw JSON semantic re-parsing might be avoided after those exact hashes
match, but that is a separate loader/provenance proof. The same optimization
could use the current in-memory validated closure without introducing a secret.
Neither approach can omit complete case coverage or trust unauthenticated DB
import flags.

The present memo has a simpler trust boundary: only executing the unchanged full
pure reducer can create an entry; all current bytes are checked on every use;
restart is explicitly cold. A secret certificate is worth reconsidering only if
measured memory requirements or the remaining read/parse cost make this approach
insufficient. It adds no ability to qualify unseen semantics, accept corrupt
bytes, skip current catalog receipt association, or claim physical success.
