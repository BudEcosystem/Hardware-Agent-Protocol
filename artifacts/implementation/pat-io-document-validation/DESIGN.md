# Reuse exact canonical-document validation during I/O capture

The [preceding run-reservation stage](../pat-io-service-runs/results/README.md) retains four failed process attempts at unchanged supervisor or worker time limits. Their logical runs, partial states and claims remain untouched. This stage investigates one concrete source of repeated pure work. It does not establish the cause of those failures or change their outcomes.

The source-free [retained-document analysis](analysis/retained-document-duplication.json) verifies 1,077 files against the sealed preceding results and walks the 450 configuration snapshots in one complete 30-case group. Its 26 runtime-bearing cases perform 9,000 BLOB-document validations on 13,271,850 input bytes. A per-engine 64-entry/128-KiB LRU would reuse 7,768 exact inputs and 11,799,192 bytes, with a largest observed retained key set of 72,628 bytes. This is a duplication count, not a runtime or causal measurement. The older interrupted profiler separately observes repeated parsing/canonicalization in the configuration cell path; its instrumented timings are not additive or deployment guarantees.

The candidate adds `CanonicalBlobs`, an internal per-trial engine memo. Keys are complete immutable byte strings, not a digest, database identity or row reference. Values assert only that those exact bytes passed the existing `canonical(parse_json(value)) == value` expression. Successful canonical documents may be retained; false results and exceptions never publish entries. The fixed bounds are 64 entries, 128 KiB of retained key bytes and 65,536 bytes per document. This is not an RSS or filesystem quota.

Every configuration snapshot still performs the original SQL schema, count, storage-class and payload-size checks and fetches current rows. Each current BLOB is then compared with exact retained bytes. Changed data must validate independently. The surrounding locks, transaction-state checks, budgets, record bytes, hashes, reservations, exclusive writes, flush/fsync and publication are unchanged. No permission, binding, session, source identity, physical state, database result or effect authorization is cached.

Reuse is allowed only with the original caller parser/encoder and selected unchanged parser/encoder dependencies, function code/default identities, numeric/tree bounds, decoder objects and escape mappings. A changed dependency clears the memo and uses the original expression. The dependency check runs again before publishing a successful miss. These are conservative compatibility guards within the trusted worker process, not complete Python-process attestation or support for arbitrary concurrent code mutation. Original image/source verification remains mandatory and is not memoized. The general parser, JCS encoder, schemas and public interfaces are unchanged.

Only `hms/pat_io_configuration_capture.py` changes among inherited project files, with one import and the BLOB-cell validation branch. The memo initializes lazily per engine so inherited construction fixtures remain valid. All inherited test bytes remain unchanged. In particular, the original test that wraps the caller's parser continues to take the uncached path and observes both validations.

Focused controls cover exact reuse, strict types/numbers/Unicode, unchanged exception details, lowered tree/document bounds, entry/byte eviction, per-engine isolation, caller/helper/code/escape changes, changes during validation, fixed capacity, fresh SQL reads, changed storage metadata, changed BLOBs and failed durable publication. One bounded repeated-document observation counts actual validations and records CPU/wall time without a timing acceptance threshold. It is not a deployment benchmark.

The unchanged 279-method selection must then run against the expanded source identity, including the previously failing reserved-worker and owner-loss methods. Fresh test fixtures have new independently identified attempts; no old run is retried or repaired. The 60-second group/owned-worker limits, 180-second outer bound, complete 30-case matrix and all effect/retention limits remain. An unchanged passing process alone cannot establish reliable performance under arbitrary hub contention.

Primary-agent review only. This isolated host change executes original simulations; no physical port, MCU/emulator, acquired controller, live inference/service or adjacent Harness checkout is used. Durable supervisor-authority handoff, public service mounting, protected compute/storage capacity, evidence import/promotion, prompt learning, persistent Arduino control and actual device/driver/hub providers remain part of the full active goal.
