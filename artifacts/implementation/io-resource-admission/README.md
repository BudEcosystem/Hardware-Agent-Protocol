# Staged resource catalog and real Journal admission

This is an original copied-source implementation and test lane, not the live HMS implementation. It mounts no Runtime, transport, device, OS driver, model, or physical lifecycle worker. Synthetic GPIO pulse, PWM burst and timer configuration action descriptions retain their own names and parameter schemas; no fan primitive or executor is relabeled. The installed-support callback in these tests is explicitly an admission-only fixture.

The accepted design is preserved in `baseline/artifacts/verification/io-driver-hub-resource-design/DESIGN.md` and its lifecycle refinement in `baseline/artifacts/implementation/resource-topology/DESIGN-ADDENDUM.md`. Nineteen baseline inputs are pinned in `baseline/inputs.json`. The copied Journal, contract parser, pure topology parser, schemas, projection helpers and existing vendor closure remain unchanged. Only staged Registry is changed, and staged ResourceCatalog is new. The original Registry binding transaction body is retained exactly in `_bind_in_tx`, with a transaction assertion and input revalidation preceding it; an AST comparison checks the extracted body.

## API and storage contract

`ResourceCatalog(journal, registry, create=True, owner=..., topology=..., generations=..., routes=...)` activates a trusted immutable topology and route-to-instance inventory, requiring initial generation revision 1. The objects must share one Journal. Activation requires admin authority, refuses existing claims on managed instances, and takes the original Journal clock checkpoint before any writes. The initial generation snapshot, token history, route and instance requirements, and storage profile change commit in one transaction. The route inventory is trusted configuration; it is not evidence that a physical or Runtime provider is installed.

The route document is closed: `{"profile":"hms.resource-route-inventory/0.1","adapters":{adapterId:[instanceId,...]}}`, with at most 16 adapters and exactly one route for every topology consumer instance. The topology and typed closure retain the existing bounded schema, exact alias footprints, all required generations and 32-claim limits. Structural containment creates no ordinary exclusive ownership.

`bind(owner, binding)` requires the proof-derived binding and control generation, exact type action coverage, complete abstract resource mapping, and exact registered alias roots for each action. It stores the original Registry binding and its immutable proof atomically. It retains the original binding authorization, envelope validation, generation nonreuse and unresolved-claim guards.

`resolve(context, intent, binding, action, live=...)` is a trusted read-only RegistryPolicy callback. It revalidates saved topology/routes/generation history and persistent requirements, verifies the retained proof and immutable Registry binding, compares the proof to current scoped dependency generations, then returns sorted canonical atom IDs. Both fresh admission and dispatch recheck use this path. `validate_bound` uses the same atoms without asserting current readiness. Historical exact operation replay still precedes fresh binding/resolver checks, using the unchanged Journal order.

An unrelated legacy instance and route may receive an explicit `None` result after catalog integrity validation; RegistryPolicy then uses its original flat mapping formula. Managed instances or routes cannot take this fallback. The ResourceCatalog does not duplicate the legacy formula or clear claims to make a new binding fit.

`publish_generation(owner, target, expected_generation, new_generation, expected_revision=...)` is **quiescent configuration publication**, not an executed driver effect. It supports service/driver generation changes, revision/token compare-and-swap and historical token nonreuse. It expands lifecycle exclusion to every action of every rebound instance, unions their canonical atoms plus the target lifecycle atom, and refuses overflow or any claim in that scope. It also preserves each instance's original unresolved-claim guard. All affected binding/proof publications and the generation snapshot commit atomically. Cancellation is not forced, unknown claims are never cleared, and injected mid-publication failure rolls all business rows back.

`snapshot(owner)` requires admin authority. `history(context, instance, generation)` requires read authority and verifies the retained generation snapshot, proof and original binding bytes. Returned data are detached. The catalog is immutable except generation publication; topology replacement, route migration and unregistration are intentionally unsupported.

## Fail-closed activation and reopening

Legacy authorities retain storage profile `hms.registry/0.1`. Opening them with the staged Registry creates no resource tables and performs no resource conversion. Catalog activation changes the profile to `hms.registry/resource-roots/0.1` in the same transaction as all resource tables and requirements. The pinned original Registry actually executes against an isolated clone in a test and refuses that unknown profile; this is not merely an assertion about a string constant.

The staged Registry accepts exactly those two profiles. Legacy storage with partial resource tables and resource-aware storage with missing required tables refuse reopening. On a resource-aware authority, a resolver is mandatory before *any* fresh resource resolution, including legacy fallback. Omitted or empty process inventory cannot disable persisted requirements. Plain admin Registry rebinding can leave an instance non-executable, but cannot remove its stored managed route/instance obligation or migrate it into legacy flat claims. The persistent catalog validates the complete retained inventory, so deleting a required row does not authorize a legacy fallback. There is no downgrade or migration-away API.

These are trusted single-owner database invariants, not authenticated storage against an administrator who can rewrite the whole SQLite authority and its software. Callback total-change and transaction-state checks are diagnostics for trusted pure callbacks, not a Python or SQLite sandbox. Callbacks may not mutate authority, reenter transactions, perform external I/O, grant authority, or substitute another catalog.

## Evidence and scope

Each `run_tests.py` invocation creates a new immutable numbered attempt, copies its exact executable inputs before importing them, and imports HMS only from those copies. The only additional original source import is the pinned original Registry for downgrade refusal. It records before/after local and installed validation-package hashes, test failures/errors/skips, and import paths. Per-test SQLite backups and decoded rows preserve actual operations, canonical claims/fences, generation/proof history, bindings and requirements. Prior attempts remain intact, including sources that passed before subsequent review fixes.

Attempt 01 established 16 tests before the managed-instance escape was closed. Attempt 02 established 21 tests with persistent instance requirements. Attempt 03 ran 25 tests and retained two loader errors because the attempted original-source import lacked its relative TD schema data file in that attempt's copy. The next revision includes that pinned data file, the original Registry's required clock argument, and a current-profile check on each admission. These historical results do not claim the later revision. The final attempt receipt and review identify the accepted staged revision.

Actual tests cover same-pad GPIO/PWM exclusion, independent-pad admission, cross-route canonical fences, planning/dispatch proof resolution, current-generation mismatch, missing/corrupt history, no resolver after reopen, raw binding migration refusal, historical replay ordering, unknown-claim retention, all-action sibling exclusion, unrelated-instance progress, rollback, clock refusal and authorization. Admitted/dispatch-ticket state is not simulated physical I/O completion; no device effect is executed by this lane.

These tests use an explicit controllable host clock, usually held at 1000 ms. They establish admission/storage transitions, not native-clock availability or latency within a real action deadline. Revalidating the complete topology and historical proof currently occurs inside the authority lock; bounded input sizes do not prove this is fast enough for a deployed provider. Latency measurement and a reviewed identity-preserving cache, if needed, belong before live short-deadline mounting.

## Integration work still required

1. Extend a versioned trusted installation document to pin the topology, route inventory, typed driver profile, supported actions and canonical resource map. The Runtime must derive required route/instance inventory from those installed records, create/open the catalog, attach its same-authority resolver before admitting work, and independently validate executor support for the resolved atoms. Caller-supplied roots are not installed support.
2. Add an original finite synthetic GPIO/PWM executor with typed parameter checks, pin/timer state, endpoint session, canonical fences, exact receipts, cancellation and reconciliation. A pulse must establish its declared safe terminal state before releasing claims. Persistent output requires an explicit lease/controller contract; an admission-only test cannot establish this.
3. Model actual hub/service/driver lifecycle as an admitted operation with the computed full lifecycle footprint, an installed provider, durable intent/receipt, cancellation policy and unknown-outcome reconciliation. Only successful verified lifecycle evidence may justify the appropriate generation publication. The admin configuration method above cannot stand in for that operation.
4. Integrate catalog binding identity into installed-resource/PAT environment evidence. The derived binding/control generation already changes on relevant dependencies and remains stable on unrelated generations, but public qualification, installation APIs, Runtime/IPC/CLI/MCP mounting and general learned PAT outcome contracts remain separate work. The current fan-policy evaluator does not qualify these I/O actions.

No live installation, public interface, complete device/hub solution, physical timing, hardware availability or total research completion is claimed.
