# Proposed wire, ownership and host changes

## A new profile, not extra meaning hidden in OP

Working labels are `hms.endpoint.standing-single/0.1` and `hms.pat.standing-controller/0.1`; neither is implemented, advertised or an allocated interoperability standard. Use an explicitly negotiated new application-payload version with the existing bounded serial framing. Define its feature descriptor and full packet/response layouts before implementation. Preserve version-1 OP/BIND/ARM/QUERY/CANCEL/RETIRE behavior under its existing profile; do not add a loop count or renewable deadline to an old OP.

The new descriptor must declare controller kernel IDs and configuration schemas; max standing/finite slots; two input channels; retained event capacity; parameter/evidence byte limits; observation and ledger semantics; lease/dwell/rate horizons; suspend/stop/quiescence capabilities; reset policy; installed manifest; and separately qualified transport/clock/stop status. Unsupported features refuse before admission. First-profile standing and finite execution are mutually exclusive, including retained terminal records, even for disjoint resource masks. This is an explicit ATmega328P capacity limit, not a general resource-graph rule.

Version-1 HELLO has no field for a standing owner or its claims, and its INHIBITED flag/state cannot be silently reinterpreted. While a standing record exists, a version-1 client must receive an explicit unsupported-profile refusal rather than a misleading free-slot/zero-held-resource snapshot. The version-2 descriptor/status reports finite and standing status and union ownership explicitly. Independent stop/local loss servicing does not depend on the old client understanding that descriptor. A commissioned gateway pins the negotiated profile; arbitrary raw-frame access remains outside ordinary agent authority.

## Proposed operation shapes

These are concrete draft fields, not assigned opcode numbers. All integers are explicit big-endian values, all unused fields must be zero, and every layout remains within the existing 192-byte payload cap. No target struct is transmitted.

| Operation | Required content and effect |
| --- | --- |
| DESCRIBE | Exact new profile/features, installed kernel/configuration identities, capacities and qualified platform flags; no effect |
| BIND / REVOKE | Versioned common context operations with the existing non-wrapping identity/inhibit-before-ack rules; BIND refuses any occupied record, and REVOKE invalidates both standing and finite authority |
| OPEN | Current control generation/handle, new standing number, deployment digest, kernel ID, exact configuration bytes, required resource mask/fences, two expected input epochs, initial absolute lease, evidence/outage policy and maximum activation count; atomic PREPARED reservation before bounded acquisition, no ordinary output |
| START | Exact identity, next mutation sequence, expected lifecycle revision; activates within the current prepared lease after fresh host/local checks; initial lease comes from OPEN, resumed preparation from RESUME |
| RENEW | Same identity/sequence/revision plus new absolute lease; ACTIVE only, before cutoff; no configuration/evidence/counter reset |
| STATUS | Exact retained identity, page selector and optional bounded activation cursor; one bounded explicit page; reports gaps/old-forgotten explicitly |
| ACK | Same identity/sequence/revision plus contiguous durable terminal/known/undisputed activation watermark; frees only acknowledged ledger entries, never claims |
| SUSPEND / RESUME | Same identity/sequence/revision and declared reason/new lease as applicable; suspension retains reservation; RESUME requires durable episode/ledger collection and moves to PREPARED for fresh acquisition, then separate START |
| STOP | Same identity/sequence/revision and declared reason; immediate ordinary inhibition, bounded local draining |
| RETIRE | Exact terminal identity/revision and durable collection watermark; requires quiescence, zero unresolved effects and final resource release |

An OPEN draft needs at most 134 bytes: prefix2 + context6 + standing number4 + digest32 + kernel2 + configuration length1 + fixed configuration32 + mask1 + eight fences32 + initial lease8 + outage policy1 + evidence mode1 + activation cap4 + two expected input epochs8. The implementation must retain those exact immutable bytes, including initial fences/lease/epochs, for duplicate comparison. Hash equality alone cannot excuse changed fields. Expected epochs are exact local non-reused mappings to the installed source bindings, not truncated or hashed external identities. OPEN validates those bindings before reserving resources and beginning acquisition.

A fixed mutation envelope can be 66 bytes: version/opcode2 + context6 + standing number4 + digest32 + mutation sequence4 + expected lifecycle revision4 + absolute lease8 + acknowledgment watermark4 + reason2. Only fields declared for that mutation may be nonzero. The retained comparison is actual version/opcode bytes0..1 plus expected-revision/lease/ACK/reason bytes48..65 (20 bytes). Identity bytes2..43 are compared to immutable OPEN, and sequence bytes44..47 to the last accepted mutation sequence. The old expected revision is retained independently of the current lifecycle revision. Exact accepted duplicates are recognized before today's revision check and return current status/accepted-mutation identity without reapplying effects. Rejected requests do not consume sequence; older bodies are forgotten and cannot mutate. OPEN replay uses the complete immutable OPEN bytes. STATUS has its own read-only layout; it does not consume mutation sequence or renew anything. Response revision and frame sequence remain distinct from activation identity.

STATUS uses explicit pages rather than promising the entire state, observations and event record in one packet. A proposed common 62-byte response prefix covers version/opcode2, result/page2, context6, standing number4, digest32, lifecycle revision4, last accepted mutation sequence4, activation high-water4 and ACK watermark4. A selected state page may contain at most128 explicitly serialized bytes (190 total), an observations page48, or one transition page44. Immutable OPEN bytes are already retained by the host; no duplicate local export buffer or resumable export cursor is added. State-page fields must include loss/witness/ownership and accepted-mutation comparison evidence. Encoding is field-by-field and canonical, never a dump of a C struct. The complete page layouts and independent vectors remain a specification gate before implementation.

Each response is a bounded local snapshot, not an atomic multi-page transaction. Requests supply their own cursor; response identity, revision, activation/ACK watermarks and observation identities let the host detect changes or retain explicitly time-separated evidence. A missing cursor cannot cause an allocation or a fabricated record. Host recovery must not label pages from different states as one historical snapshot. Collection before ACK/RESUME remains a durable host obligation, and the trusted RESUME handoff attests that the separate suspended loss/quiescence summary was committed.

The sealed link currently allows only CANCEL/REVOKE through TX backpressure. The new profile must explicitly admit STOP, authority REVOKE and SUSPEND into a bounded control lane while ordinary responses are busy, without overwriting a partial outgoing frame; acknowledgments may be lost and are later resolved by STATUS. RENEW/ACK/OPEN/START must never bypass freshness, state or durable-host checks because a buffer is full. RX parsing must keep the existing pre-feed deadline and clean-READY linearization point. An interrupted/malformed packet cannot partially install configuration or claim resources.

## One shared local resource authority

The current endpoint stores eight fence floors and one OP's held mask. A higher fence never displaces a holder. Extract or extend that existing admission/ownership logic so both finite and standing entry points consult the same owner discriminator, floors and installed resource map. Do not add a second independent lock table in a controller callback.

A slot-kind discriminator distinguishes EMPTY, FINITE_OP and STANDING_RECORD. The existing 192-byte immutable operation buffer may store the complete OPEN bytes **only when no finite OP/receipt is present**. This is explicit tagged storage reuse in a new core/profile; a finite record is never overwritten. All finite admission paths must reject while STANDING_RECORD owns the slot, including direct core API paths, not only a friendly host wrapper. The standing poll must never interpret OPEN bytes as an OP. The legacy endpoint poll runs only for FINITE_OP; idle/diagnostic bookkeeping remains common. Native/API tests must verify that discriminator and old finite semantics.

OPEN checks every requested fence and expected source epoch before committing any floor, mask or discriminator. It acquires the exact installed transitive footprint: sensor access, fan output, shared PWM timer/pad, bus/address and driver lifecycle atoms as applicable. Raw GPIO/PWM/timer access must conflict with the higher-level controller through the same aliases. During PREPARED and SUSPENDED_QUIESCENT the standing reservation remains owned, so RESUME uses the same fences and cannot steal a resource. Initial preparation has no ordinary output history; resumed preparation retains its prior activation/ACK/accounting history. Either can have owned acquisition effects. Expiry/STOP follow installed settlement and evidence rules, and only eligible RETIRE releases ownership. This first profile accepts aggregate quiescence for the full resource mask; standing partial release is unsupported. All resource floors and the separate standing-number high-water survive retirement and intervening finite OP use.

Host-level arbitration reuses `resource_topology.binding_proof`, alias/consumer closure and generation-change claim derivation. Its ownership model must add standing-deployment owners; it cannot represent a months-long reservation by inventing an ordinary finite operation that has supposedly completed. Driver/service lifecycle changes reserve the complete affected consumer set, inhibit incompatible new work, drain standing and finite owners, retain unknown claims and publish new generations only after qualified settlement. Unrelated devices/instances remain independently admissible.

## Required implementation changes

| Existing location | Reusable behavior | Required new behavior |
| --- | --- | --- |
| `protocol/serial/frame.*` | Fixed 192-byte payload, FCS framing, bounded parser | No new bulk transport for this profile |
| Sealed `avr_runtime`, `avr_uart`, `avr_usart`, `avr_clock`, boot/EEPROM adapters | Clean READY, explicit assembly budget, one-byte TX, fresh ownership/clock snapshots, qualified boot namespace | Sibling standing dispatcher/service with bounded acquisition/feedback scheduling; independently qualified clock-failure service remains separate |
| `protocol/endpoint/endpoint.c,h` | Atomic all-resource validation, fences, current guard/clock checks, possible-effect marking, cancellation/loss/quiescence distinctions | Tagged single record, common arbiter/context authority, standing lifecycle/counters/ledger; preserve finite v1 bytes and outcomes |
| `protocol/endpoint/link.c,h` | Existing feed factorization and response buffer | Explicit profile dispatch and new control-lane opcode rules; no double parsing or fabricated READY |
| `hms/endpoint_wire.py` and compact host binding | Exact codecs, original command retention, correlated query/recovery | Separate versioned standing codec, deployment/mutation/activation mapping, STATUS/ACK and resume/stop recovery |
| `hms/pat_contracts.py`, `pat_compiler.py` | Closed typed finite artifacts, domain checks, explicit semantic bindings and compiler identities | Separate parser/compiler for the narrow standing kernel profile; do not weaken bound-sequence refusals |
| `hms/pat_catalog.py` | Immutable evaluations/decisions, dependency-specific eligibility, evidence unavailability refusal | New standing evaluator/policy and outcome/continuity cases; explicit distinction between catalog eligibility and a running deployment |
| `hms/pat_execution.py` | Exact trigger replay, owner checks and atomic host linkage | New standing-deployment store/API; current `px_instances.procedure_id` and finite procedure linkage cannot represent it unchanged |
| Journal/resource admission and qualification/storage services | Durable owner/replay mappings, shared claims, exact dependency checks | Standing owners, mutation history, activation-prefix evidence, backed control-record capacity, transactional ACK eligibility and restart reconciliation |

Suggested new host store concepts are immutable deployment revisions, current deployment bindings, admitted control mutations, activation/evidence prefixes and resource-owner links. They require closed schema versions and explicit bounds; table names or a SQL sketch are not a durability implementation. OPEN preparation records the full original packet and namespace before a driver can hand off START. ACK is built only after the corresponding bounded evidence prefix commits. Exact replay returns historical deployment state before consulting today's catalog; it never creates a replacement instance because evidence, resolver or clock is temporarily unavailable.

The existing catalog rule of retaining an admitted version remains useful. Suspending a PAT catalog entry inhibits new deployments; it is not proof that an already active controller stopped. Emergency authority withdrawal is a separate explicit control/loss path. New source/driver/calibration/configuration identities invalidate applicability for new starts and renewals according to the deployment policy; ordinary continuation cannot silently adopt changed code. Unknown effects must be reconciled before agent-generated replacement action.

## Placement and broader profiles

The MCU owns timing-sensitive acquisition, bounded local state/feedback, resource checks and loss/stop behavior. A hub owns the durable application and evidence, authority renewal, PAT selection/qualification, agent planning and richer data processing. The local loop cannot depend on a model call or unbounded host job. The host provider being designed separately must own compute job identity, limits, cancel and reconciliation; an inference API return is not device success.

A larger MCU/RTOS profile may add multiple standing slots, shared read inputs, declared scheduling/interference analysis, deeper trace queues and qualified persistent activation journals. It needs its own target allocation and tests. A compact verified instruction/state-machine profile can later support more general local programs over installed capabilities, with instruction/state/iteration/effect limits and explicit version negotiation. Unsupported bytecode or timing semantics cannot be emulated by repeated OPs while claiming equivalence.

GB10, another GPU/SBC hub or an AI-capable endpoint can host planning or pinned perception, but the actual OS/ABI, driver/runtime/model dependency closure, memory quotas, service sessions and outage policy must be qualified for that provider. This design introduces no current GB10 package/version/throughput claim. No role grants the agent unrestricted host, driver, GPIO or bus access.
