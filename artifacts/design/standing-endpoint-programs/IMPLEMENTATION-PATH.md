# One cohesive implementation slice

The first useful slice is a single immutable local hysteresis/feedback deployment with its complete lifecycle, not a generic VM skeleton or a test that repeatedly submits existing finite OPs. It starts with original synthetic drivers and a fixed two-input environment, then cross-links the actual ATmega328P adapter composition. Physical I/O qualification is a separate subsequent step.

1. Freeze a new standing-profile specification and independent vectors: feature negotiation, exact OPEN/mutation/status/record bytes, identities, all states/cutoffs, source freshness rules, finite-vs-standing exclusion and explicit unsupported features. Specify baseline v1 behavior while a standing owner exists, rather than accidentally exposing misleading HELLO flags.
2. Extract/extend the existing resource/context admission core with an enforced slot-kind discriminator. Preserve finite payload/receipt and wire behavior when the slot is FINITE_OP. Add shared checks to every direct finite/standing admission path. Store OPEN bytes in the same immutable buffer only for STANDING_RECORD, with no automatic eviction. Add the capped standing state and exact mutation replay logic.
3. Implement the bounded installed kernel and observation contracts. Two original synthetic providers produce acquisition-time/epoch/sequence/quality records. At most one acquisition/controller/feedback step executes per budgeted scheduler phase. Define the maximum combined per-loop driver service count explicitly; the sealed adapter's current one-callback bound cannot silently become three callbacks. Prefer a single combined controller driver step that advances its own bounded acquisition/feedback phase per call.
4. Implement the two-record transition ledger and sticky loss state, possible-effect marking, exact host ACK watermark, lease renewal, suspension/resume and terminal drain/quiescence. A full ledger cannot overwrite evidence or block the separately installed loss path. No renewal clears a fault or resets accounting.
5. Add a distinct host standing-deployment store, codec and deterministic renewal/collection supervisor. It shares the existing durable authority/resource transaction boundary and uses backed capacity from the storage work. Retain all deployment/control/activation mappings before handoff, and acknowledge evidence only after commit. Exact replay after reopen resolves the same deployment, not another procedure or newly numbered OP.
6. Add a separate PAT parser/compiler/evaluator for this kernel profile. It validates the complete supported parameter domain and exact dependency/environment closure. The current bound-sequence parser remains strict. A qualified standing artifact is instantiated once, then local ticks/transitions occur without planning inference; changes create a new immutable candidate and explicit transition policy.
7. Run one end-to-end synthetic prompted-application scenario: a structured version of “maintain this enclosure within these temperature limits; report ineffective cooling” resolves installed sensor/fan/feedback roles, admits a standing instance, performs many local evaluations and at least several acknowledged transitions, renews without replacing the instance, survives a bounded hub interruption, and handles a deliberately new/out-of-envelope condition through a retained exception and declared local response. Record zero planning-model calls for repeated eligible control cycles. This demonstrates the narrow software lifecycle only; it does not demonstrate natural-language understanding, learned synthesis or physical cooling by itself.
8. Cross-link the same complete controller/core/AVR adapters and real ISR wrappers with every reservation retained. Derive static SRAM/flash, all indirect callback paths and foreground/ISR stack from that exact image; compare the concrete ceilings in [ATMEGA328P-BUDGET.md](ATMEGA328P-BUDGET.md). A fit failure is a retained unsupported-target outcome. No board execution follows automatically.

Fault tests must distinguish the correct declared loss response from successful application completion. All failed/refused/unknown cases remain in the evidence. A reset simulation may preserve an external effect counter solely to expose ambiguity; that is not proof that a physical device has such a durable counter. A compiled target and native register model are not physical qualification.

## PAT learning and the agent boundary

New prompts or observations outside the qualified applicability envelope go to the agent with the exact current application version, dependency state, observed condition and unresolved-effect status. Ordinary contention, transport recovery and unavailable evidence follow deterministic declared handling; they do not automatically authorize a new physical strategy. Before a revision that could cause another effect, reconcile the previous unknown state and ownership.

The candidate PAT/evaluation record pins kernel/driver/firmware/installation identities, observation schema and producer behavior, numeric units/ranges, calibration, resource topology/generations, clock/service/loss policies, host compiler/store/supervisor identities, and any perception/model/hub dependencies. Evidence includes negative contexts, sensor/hub faults, false reuse, escalation behavior, timing and resource bounds, outcomes and trace completeness. Promotion within a previously delegated envelope may be automatic after its installed policy passes; this design adds no universal manual-approval requirement or arbitrary success-count threshold.

The deterministic reuse path must report both planning-model calls and any declared perception/numerical inference calls. A stored program retrieved after an LLM interprets a new free-form prompt is not zero-inference prompt handling. The local standing kernel itself requires neither inference nor repeated host planning to evaluate a supported observation.

## Larger endpoint and hub paths

Multiple independent controllers, full event queues, persistent journals and arbitrary bounded state-machine instructions require another target feature profile and fresh scheduling/resource analysis. A larger MCU or RTOS may supply those capabilities; the ATmega profile must return unsupported rather than approximate their timing or durability.

The hub-provider lane should supply real owned jobs and lifecycle/compute resources under its own execution/evidence profile. It must not run those effects through current simulation-only registry/PAT predicates. Driver/service updates and hub restarts need durable mutation identity, affected-standing-owner drainage, dependency generation publication and reconciliation. GB10/ARM64/GPU execution requires actual deployment evidence; a common protocol and a source review cannot establish its provider compatibility or resource capacity.
